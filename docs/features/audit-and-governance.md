# Audit log and governance

Part of the [Landflow docs](../README.md); the [feature map](../README.md#feature-map) lists every feature page.

**Audit log** (Settings → Audit log, owners and admins; a project's **Audit log** tab for its admins). Every event says who (user or API key, with the key's id, never the key), when, from where (IP, user agent, request id, route pattern; never query strings or bodies), what it touched (target type, id and name, and the target's project) and the outcome (`success`, `failure` or `denied`). Recorded: sign-in, sign-out and failed sign-ins (wrong password, rate-limited, deactivated), password resets, invites, role changes and removed users, API keys created and revoked, workflows created, saved, imported, deleted, published, rolled back and unpublished, publish requests and their decisions, credentials created, changed and deleted, which credentials each run used (`credential.use`: credential, node, workflow and execution ids, never values; off in the settings), settings changes (general, MCP, AI prices, audit, governance, source control), executions stopped, stopped all and deleted, Git push, pull and sync apply, plugins registered and removed, an endpoint added to an existing plugin (`plugin.endpoint_added`: plugin id, endpoint, discovery source, transport) and a plugin's version change (`plugin.updated`), marketplace installs, and what a person approved by the hash of its content (`trust.approve`, `trust.reject`, `trust.revoke`: the subject, the hash and a one-line summary, never tool text or headers; an agent's MCP tools snapshot at publish or a decision on a held change, and a marketplace node plugin's files at install; [agents.md](../agents.md#changed-mcp-tools-are-held), [marketplace.md](../marketplace.md#landflow-node-plugins)). On top of those, the route `handler` records every other change through the API (`api.request`) and every refused request (401/403, `denied`); reads, live events, triggers and plugin traffic are left out.

- **Stored** in `audit_events` (migration 900) with its own retention (default 365 days, 0 keeps them forever; separate from execution retention). Events still waiting for a SIEM destination are kept until delivered.
- **Per project** (migration 1500): an event about a workflow, credential, data table or agent records its home project, one about an execution its workflow's, one about a project that project (instance-wide targets such as users, API keys and settings have none). Events from before the migration have no project (no backfill).
- **Hash chain** (migration 1500): each event stores its place in the chain, the previous event's hash and its own, SHA-256 over a canonical form of every stored field. Changing a stored field, deleting an event (or the newest ones) or slipping one in breaks the chain at that point. On SQLite (and Postgres with one host) an event is chained in its insert transaction, which holds the database's write lock, so processes sharing the file take turns; in queue mode on Postgres events are stored unchained and sealed in Postgres in order under a transaction-level advisory lock (`pg_advisory_xact_lock`) within seconds by whichever process gets there first. **Verify chain** (Settings → Audit log, or `GET /api/audit/verify`) recomputes every hash and link (straight from Postgres in Postgres mode) and says where it breaks; the check is audited (`audit.verify`, a failure when broken). Retention prunes from the oldest end only and keeps the last pruned event's hash as the anchor, so the rest still verifies. Events recorded before the migration stay unchained (counted as legacy).
- **Signed heads and anchoring** (Settings → Audit log → Integrity, migration 1882): the hash chain proves the log wasn't edited, but someone who can rewrite the whole table can rewrite the chain too. The leader therefore verifies the whole chain on a schedule (default hourly, 60 s tick) and signs its newest link (`seq`, `hash`, time, key id) with an Ed25519 key kept sealed with the credential key (`audit_signing_keys`, `audit_heads`; refuses to sign a broken chain). `GET /api/audit/head` (scope `audit:read`) returns the newest signed head and every public key; **Sign and anchor now** and **Rotate key** (old keys keep verifying older heads) are in Settings and `POST /api/settings/audit/anchoring/run` and `/rotate-key`. **Anchors** put each signed head where the log's owner can't rewrite it: an S3 or MinIO bucket (`<prefix><seq, 12 digits>-<hash prefix>.json`, default prefix `audit-heads/`, explicit keys, never the default credential chain) and a webhook (`X-Landflow-Event: audit.head`, with `X-Landflow-Signature` when a secret is set); failures are retried on the next tick and shown in Settings. Secrets are sealed and never returned. `landflow audit verify` checks the chain on the host (exit 9 when broken); `landflow audit verify --head head.json --public-key key.pem` checks a head **offline** with Node's crypto only ([packages/cli](../../packages/cli/README.md)); signing is audited as `audit.sign_head`.
- **SIEM scope per project**: a destination can take every event (the default) or only chosen projects' events, plus instance events (sign-ins, users, settings; those with no project) when asked (`scope: { projectIds, instance }` on create and patch, `null` clears it; unknown project ids are a 400). It applies when an event is recorded, so a destination's outbox only holds events in its scope.
- **OpenTelemetry**: each event is also an OTel log record (`event.name` = `landflow.audit.<action>`, the actor, target and outcome as attributes, inside the request's trace), exported over OTLP/HTTP JSON when `OTEL_EXPORTER_OTLP_ENDPOINT` (or `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`) is set; `OTEL_LOGS_EXPORTER=none` turns that off.
- **Read**: `GET /api/audit` filters by actor (id, name or email), action (`workflow.*` for a category), target, project (`projectId`), outcome, time and text, newest first with a cursor; `GET /api/audit/export?format=csv|json` downloads the same filter (with the project and the chain columns; cells starting with `=`, `+`, `-` or `@` are defused for spreadsheets; the export is audited too). Owners and admins read every event; anyone else the events of the projects they are an admin of (their personal project and team projects where their role is admin), 403 for another project's. API keys need the `audit:read` scope.
- **SIEM streaming** (Settings → Audit log → SIEM streaming): destinations get every new event through a durable outbox (`audit_outbox`, written in the same transaction as the event): batches of up to 100, retried with exponential backoff (2 s doubling to 5 min, with jitter) until delivered, leased so a second host or a restart never sends a batch twice at once. The claim, retry and backoff code is the shared outbox core (`lib/server/outbox/core.ts`) that [event subscriptions](event-subscriptions.md) use too; the audit outbox keeps its table, its delivery from every main and its behaviour. **Send test event** sends one event straight away and says what the receiver answered; **Retry now** skips the backoff. Secrets are encrypted like credentials and never come back from the API. Syslog over TLS and HTTPS destinations can trust a private CA and present a **client certificate** (mTLS) to receivers that require one: the certificate (PEM, may include its chain), its private key and an optional passphrase; the key and passphrase are sealed like the other secrets, the certificate and key are checked to belong together when saved, and Settings shows the certificate's subject and expiry.

| Destination | Settings | What it sends |
|---|---|---|
| Syslog | host, port, UDP / TCP / TLS (certificate check, optional CA, optional client certificate), facility (default 13, log audit), app name, TCP framing (RFC 6587 octet counting or newlines) | RFC 5424 with the event as structured data (`[landflow@32473 id=… action=… outcome=… actorId=… targetType=… projectId=… chainSeq=… hash=…]`), `MSGID` the action and the event's JSON as the message |
| HTTP (JSON lines) | URL, optional signing secret | `application/x-ndjson`, one event per line; `X-Landflow-Timestamp` and `X-Landflow-Signature: sha256=<HMAC-SHA256 of "<timestamp>.<body>">` |
| HTTP (Datadog) | logs intake URL (any site), API key, tags | Datadog's logs API (`DD-API-KEY`, `ddsource: landflow`, `service`, `ddtags`) |
| HTTP (Elasticsearch) | URL, index or data stream, optional API key | `_bulk` `create` with the event id as `_id` (a retried batch never duplicates) |
| Splunk HEC | HEC URL, token, index, source, sourcetype | `/services/collector/event` with `time` from the event |

To try it locally, `docker compose -f deploy/compose.infra.yml --profile siem up -d siem` runs a Vector receiver: syslog on `localhost:55514` (TCP and UDP) and JSON lines on `http://localhost:55080/`; `docker compose -f deploy/compose.infra.yml logs -f siem` prints what arrives.

**Governance** (Settings → Governance; owners and admins change it, everyone sees it). With every rule off, nothing changes.

- **Nodes**: allow only, or block, node types (ids or globs like `messaging.*`) and whole plugins; **Block Code nodes** on its own. **HTTP Request hosts**: allow only or block host names (globs), `host:port`, IPv4 and IPv6 addresses and CIDR ranges (`10.0.0.0/8`, `fd00::/8`, `[::1]:8080`; an IPv4-mapped IPv6 address counts as its IPv4 address), checked for each item's URL. **MCP servers**: allow only these URL patterns or hosts for the MCP Client node and tool and AI agents' MCP servers.
- **Per project and per workflow**: a project's admins can allow only some node types and plugins for its workflows and agents (the project's **Settings** tab → Allowed nodes; `PATCH /api/projects/:id/settings`, migration 1401), and a workflow can narrow that further and ask for four-eyes publishing for itself even when the instance doesn't (Workflow settings → Governance; `PUT /api/workflows/:id/policy`, admins of its project). A project can ask for four-eyes for **all** its workflows (the project page → Governance → *Require four-eyes on publishing*, `fourEyes` in `PATCH /api/projects/:id/settings`), which also turns a promotion that changes one of them into a request (see [Environments](secrets-and-environments.md)). A project's admins can also set what agents do in it: allowed agents, allowed tool kinds, a default model and one knowledge base ([project settings for agents](../projects-and-goals.md#project-settings-for-agents); audited with the rest of `project.settings.update`: the model's provider and name, whether the knowledge base is on and its collection, and each mode with its agent ids and tool kinds). Each level only narrows the one above (instance, project, workflow, and now agents); the checks are the instance's (below), and the error says where the rule was set.
- **Where it applies**: saving a workflow that breaks a rule saves it with a warning (`policyWarnings`); publishing it (editor, API, CLI, Git sync, the instance MCP server) is refused with 422; at run time a blocked node fails with "Blocked by policy: …" and the hint to Settings → Governance, in the host and in queue workers, for manual, trigger, sub-workflow and agent runs. The node creator hides blocked node types, the import report lists them, templates using them are marked unusable. Disabled nodes don't count.
- **Four-eyes publishing**: Publish, a rollback from the version history and (by default) Unpublish become a request (`202 { approvalRequired: true, request }`, migration 901) with the note and what it changes against the live version ("2 nodes changed, 1 added"). Someone else approves (which publishes it, credited to the requester, "approved by …" in the note) or rejects it with a comment; nobody approves their own request. Approvers are any other builder (member, admin or owner) or only owners and admins; project roles plug in through `registerApproverCheck` (`lib/server/governance/approvals.ts`): a project's Settings tab says who approves its workflows' requests (the instance's rule, its admins, its admins and editors, or instance owners and admins only; `lib/server/governance/project-approvers.ts`). A request goes **stale** when the draft or the live version changes before it is decided, and a new request replaces the workflow's pending one. Approvers are emailed (with `LANDFLOW_SMTP_HOST`) and chosen alert channels hear about new requests; the requester hears the decision. Everything is in the audit log. The editor's Publish menu shows "Awaiting approval" with Approve / Reject / Withdraw; Settings → Governance lists every request. The CLI's `workflows publish`, `unpublish`, `activate` and `deactivate` exit with code 8 (`approval_pending`, the request in `details.request`).
- **Scheduled publishes**: publish or unpublish a workflow at a time (Publish menu → *Schedule…*, or Version history → *Schedule…* on a version; `POST /api/workflows/:id/publish` and `/unpublish` with `"at": "<ISO time>"` answer 202 `{ scheduled }`; `landflow publish <wf> --at 2026-11-01T09:00Z|+2h|+1d`, `landflow unpublish <wf> --at …`; `landflow workflows schedules <wf>` lists them and `landflow workflows unschedule <wf> <id>` cancels one; `GET /api/workflows/:id/schedules`, `DELETE …/schedules/:scheduleId`). Schedules live in `scheduled_publishes` (migration 1840): the leader main polls every 5 s, claims a due row, publishes the pinned version (or unpublishes) as the user who scheduled it, and records `done`, or `failed` with the reason (a version pruned by then, a blocked node, a missing workflow); after a crash, rows left running are recovered at start. With **four-eyes** on, scheduling files a request instead (Awaiting approval, with the time): approving *releases* the schedule, which then goes live at its time; a rejected, withdrawn or stale request cancels it, and a schedule made before four-eyes was turned on becomes a request when its time comes. The creator or an admin cancels; schedule changes are audited (`publish_schedule.create`, `.cancel`, `.run`); scheduling is allowed in a protected environment (it publishes later through the same checks).

### Reliability and fail-closed mode

A failing audit insert (disk full, a lock, a schema problem) used to leave only a log line. Now it is also counted, and a
deployment can refuse the change. An event's insert (with its hash-chain link and outbox rows) is all or nothing, even
inside a larger transaction: a swallowed failure leaves no partial rows and no false tamper report.

- **Metrics** (lib/server/audit/metrics.ts): `landflow.audit.write_failures{action}` counts events that could not be
  stored (the generic `api.request` layer counts under that action too); `landflow.audit.outbox.delivery_failures{destination}`
  counts failed SIEM deliveries; the gauges `landflow.audit.outbox.depth` and `landflow.audit.outbox.oldest_age` (seconds)
  are registered at boot (also where `LANDFLOW_AUDIT_OUTBOX=off`), and read the outbox when metrics are collected, so a stuck destination shows as a growing age.
- **`LANDFLOW_AUDIT_FAIL_CLOSED=true`** (default `false`; recommended for regulated deployments): for role changes, API
  key create and revoke, credential create, update and delete, audit settings changes (`PATCH /api/settings/audit` only: retention and credential-use; SIEM destinations, anchoring and key rotation stay fail-open) and SCIM provisioning (users and
  groups), an event that cannot be stored refuses the change with `503` (`AuditUnavailableError`) and nothing changes.
  Where the change is a database write, it and its event share one `auditedTransaction()`, so the insert joins it and a
  failure rolls both back. Credentials live in the files config store, which is no transaction: update and delete record
  the event first and refuse the change if that fails; create needs the new id, so it creates, records, and deletes the
  credential again if the event fails. SCIM user creation does the same (the user is deleted again). Encryption key
  rotation (`encryption.rotate`, route and script) and password changes (`auth.password_change`) are recorded fail-open
  on purpose: rotation is idempotent and reports what it re-sealed, and a person changing their own password must not be
  locked out by an audit outage.
- **Off**, behaviour is as before: the failure is logged and counted and the change goes on. Everything else (sign-ins,
  workflow events, credential use in runs) is never required, in either mode.

### MCP policy hooks

An admin can have a service of their own decide, call by call, whether an outbound MCP request may leave. **Settings → MCP →
Policy hooks** lists the hooks (at most 20); each has a name, a URL, a signing key, a timeout, a failure mode and what it
looks at. Before every MCP request a hook matches, Landflow posts the call to it and goes on only if every matching hook
answers `allow`. It covers every caller that goes through Landflow's MCP client: an agent's MCP tools, the MCP Client Tool,
the MCP Client node and a team member's tools, because the check sits in `callMcpTool`, `readMcpResource` and `getMcpPrompt`.
It runs after the arguments are known and after any person's approval (an approval does not skip it).

- **Matching**: server host (names, `*.suffix`, IPs and CIDR ranges, as the governance host lists) and a path prefix; tool name
  patterns (`create_*`, `?`; for a resource read the URI, for a prompt its name); the method (`tools/call` by default,
  `resources/read` and `prompts/get` optional); projects. An empty list means any. A call no hook matches pays a cached read and a match.
- **What is sent** (`POST`, JSON): `{ requestId, time, server: { url }, method, tool | uri | prompt, arguments, masked, truncated, caller: { executionId,
  workflowId, nodeId, nodeName, agentId, sessionId, userId }, projectId }`, plus `test: true` for the Test button. The server URL
  has no userinfo and no query. `arguments` is **never cut**: a decision on half of an argument is no decision. Known secret values
  are replaced and the values under secret-looking keys (`token`, `password`, `apiKey` …) and auth-header-looking strings become `••••••`;
  `masked` lists every such place as a path (`nested.list[0].apiToken`), so a service that cannot judge what it cannot see can deny it.
  The whole request is capped at 256 KB: a larger one is **not sent** and counts as a failure (the failure mode decides), so `truncated`
  is always `false` (it is there so a service can rely on the field). Never a credential value. Agent version and team are not sent yet.
- **Signing**: by default `X-Landflow-Timestamp` and `X-Landflow-Signature: sha256=<hex>`, the HMAC-SHA-256 of `<timestamp>.<body>`
  keyed by the token of a **Bearer Auth credential** you pick (the same scheme as the alert webhook channel); or the token as
  `Authorization: Bearer` (refused on an `http:` URL in the production profile); or none. **A receiver must reject** a request whose
  `X-Landflow-Timestamp` is more than 5 minutes old and any `requestId` it has already seen, or a captured request can be replayed.
- **The answer**: `{ "decision": "allow" | "deny", "reason"?: string (500), "ruleId"?: string }` with a 2xx status. Anything else, a non-2xx
  status, a body over 64 KB, a redirect or no answer within the timeout (100 ms to 5 s, default 2 s) is a failure.
- **Failure mode**: `closed` blocks the call ("policy service unavailable"), `open` lets it through. A new hook is `closed` in the production profile
  and `open` otherwise; the choice is stored and editable. With several hooks the first deny, in the order of the list, is the one named.
- **A deny** is the tool's result: "Blocked by policy <hook>: <reason>", which the model reads and can work around; it does not fail the run.
  The MCP Client node fails its item with that text (so *Continue on fail* applies). The server receives nothing.
- **Run Trace and audit**: each decision is a `policy` check on the call's span (allow: pass; deny: warn; the service down with `open`: warn,
  with `closed`: fail, which shows in Needs you); a deny is the audit event `mcp.policy.denied` and a failure `mcp.policy.failed`
  (actor the run's user or the system, target the MCP server, details the hook, tool, rule id and execution; never the arguments);
  hook changes are `mcp.policy_hook.create`, `.update` and `.delete`. The counter `landflow.mcp.policy.decisions` counts by `decision` and `hook`.
- **Unreadable hooks**: if the stored hooks cannot be read or one is invalid, that is logged and counted (`landflow.mcp.policy.store_errors`), and in the
  production profile every MCP call is blocked ("policy service unavailable", audited as `mcp.policy.failed`); elsewhere calls go ahead. Saving a hook recovers it.
- **A cancelled run** stops the check: the abort goes up as it is, with no check, audit event or failure mode (an `open` hook never lets a cancelled call through).
- **The Run Trace says only** "policy service unavailable"; the network detail (addresses, errors) is in the audit event and the log.
- **An allow is reused for 60 s** for the same call (hook, tool, arguments, caller) in the same run, in that process. A deny and a failure never are.
- **Outbound rules**: the hook is called through `safeFetch`; saving a hook on a private address in the production profile is
  refused unless `LANDFLOW_OUTBOUND_ALLOW` lists it. **Test** sends one sample request (`tool: "example_tool"`) and shows the answer; it is not audited.
- **Not covered**: kagent agents' own MCP calls and calls through the agentgateway (it has its own policies), inbound calls to
  Landflow's own MCP server (grants and MCP approvals), non-MCP tools, and a standalone agent's chat with no workflow node
  (the model still reads the denial, and the audit event and counter still record it, but there is no check on a span).
  A hook cannot rewrite arguments.

### Outbound requests

The host allow and block list above matches host names before a call. Below it sits an address policy for everything a
user, a webhook or a model can point at a URL: **`safeFetch`** (`lib/server/net/safe-fetch.ts`). With
`LANDFLOW_OUTBOUND_BLOCK_PRIVATE` on (the default in the production profile; off in development, so local fakes and tests
on 127.0.0.1 keep working) a request is refused when the address it would reach is loopback, private, link-local, CGNAT,
multicast, unspecified or a cloud metadata address (`169.254.169.254`, `fd00:ec2::254`); an IPv6 address that carries an
IPv4 one (IPv4-mapped, NAT64 `64:ff9b::/96`, IPv4-compatible `::a.b.c.d`, 6to4 `2002::/16`) counts as that IPv4 address,
and the local-use NAT64 prefix `64:ff9b:1::/48` is refused. The check sits in the socket's DNS lookup, so the address that is checked is the one connected
to, and a name with any blocked address among its answers is refused. A literal IP is checked before connecting.
Redirects are followed by `safeFetch` itself (at most 10) and every hop gets the same checks, plus the governance host list
for the HTTP Request node and the MCP server list for remote MCP servers, so an allowed host cannot send a request on to a
blocked one. Only `http:` and `https:` URLs are fetched, in development too (`data:` and `blob:` URLs, which the platform
fetch read, are refused).

A refusal reads "Blocked: <host> resolves to a private address (LANDFLOW_OUTBOUND_ALLOW lists exceptions)" (an
OpenAI-compatible model call shows it as the error, with the server it could not reach below). Exceptions:
`LANDFLOW_OUTBOUND_ALLOW` (host names, `*.suffix` globs, IPs and CIDR ranges); the exact endpoints (host and port) of `OLLAMA_URL` (or its default),
`LANDFLOW_CODE_RUNNER_URL`, `OPENAI_BASE_URL`, `LANDFLOW_LLM_GATEWAY_URL`, `LANDFLOW_MCP_GATEWAY_PUBLIC_URL`, `LANDFLOW_GITHUB_MCP_URL` (or its in-cluster default), `LANDFLOW_OIDC_DISCOVERY_URL` and `LANDFLOW_TOOL_POLICY_URL` are allowed without listing (another port on the same host is not). Covered: the HTTP
Request node and other in-process nodes (their `ctx.http`), alert channels, HTTP SIEM destinations (not syslog), remote MCP
servers, RAG embeddings and rerank, OpenAI-compatible model calls (the credential's Base URL), in-process plugins' load-options and credential tests, OIDC and SAML metadata. Every call has a client span (`HTTP <method>`, URL without its
query). Not covered, by decision, and listed in [limitations.md](../limitations.md): plugin processes, databases, brokers,
S3, the marketplace's git and a few follow-ups. A production host that calls internal services must list them.

- **SCIM provisioning**: every change an identity provider makes through `/scim/v2` is a domain event, recorded as the SCIM token's user with the token's API key id, the request id, address and user agent: `user.provision` (email, name, role, active, external id), `user.update` (`nameFrom`/`nameTo`, `emailFrom`/`emailTo`, `roleFrom`/`roleTo`, `externalIdFrom`/`externalIdTo`, only the ones that changed; a role change a group mapping causes is one too), `user.deactivate` and `user.reactivate` (`activeFrom`/`activeTo`), `user.remove`, `group.create`, `group.update` (name and external id before and after), `group.members_change` (`added` and `removed` user ids) and `group.remove` (with the member ids). A rejected token (missing, unknown, expired, wrong scope, not an owner or admin) is `scim.auth_failed` with outcome `denied`, at most once per client address per minute (the addresses are held in memory, up to 10,000) and at most 60 a minute in all, so an identity provider retrying in a loop, or a caller rotating its address, can't flood the log. A 403 (a valid key without the `scim` scope, or whose user is not an owner or admin) carries the key id and user id in its details. A bulk sync records one event per change, which is intended. The generic `api.request` event doesn't cover `/scim/v2`.

**Permission, secret and access events** (wave 3, P12). The library functions record them, so the UI, API, CLI, MCP tools, SSO and SCIM group mapping all produce the same event, once each (the generic layer stays out of a request that recorded one). `from` and `to` are flat details; no value of a variable, secret, credential or password is ever stored.

| Action | Recorded when | Details |
|---|---|---|
| `project.create`, `project.update`, `project.delete` | a team project is made (also by SSO/SCIM group mapping), renamed or re-described, deleted | `name`; `nameFrom`/`nameTo` (also `description…`, `icon…`) for what changed; `transferredTo` and `moved` (`kind:count`) on delete |
| `project.member_change` | a member is added, removed or has their role changed (the members page, project creation, group mapping) | `change` (`added`, `removed`, `changed`), `userId`, `email`, `from`, `to` (roles; null when absent), `source` (`saml`, `scim`) |
| `resource.share`, `resource.unshare` | a workflow or credential is shared with a project or user (new, or its role changed), or a share is removed | `kind`, `resourceId`, `withProjectId`, `withProject`, `from`, `to` (share roles) |
| `resource.transfer` | "Move to project" for a workflow, credential, data table or agent | `kind`, `resourceId`, `from`, `to` (project ids), `toName`, `keepAccess`, `sharedCredentials`; the access a move keeps or the credentials it shares are `resource.share` events of their own |
| `variable.create`, `.update`, `.delete` | an instance variable or a project's | `scope` (`instance`/`project`), `projectId`, `key`, `from`/`to` on a rename, `valueChanged` (never the value); a change to per-environment values is a `variable.update` with `environments` (names that got a value) and `cleared` (names that lost theirs), recorded only when something differs |
| `secret_provider.create`, `.update`, `.delete` | an external secrets provider | `provider`, `kind`, `enabledFrom`/`enabledTo`, `fieldsChanged` (setting names only) |
| `auth.mfa_added`, `auth.mfa_removed`, `auth.mfa_recovery_regenerated` | you add or remove a second factor, or make new recovery codes ([second factor](authentication.md#second-factor)) | `kind`, `factorId`, `count`; never a secret or a code |
| `auth.mfa_reset` | an owner or admin resets another person's second factors (high-value: stored in the same transaction, 503 under `LANDFLOW_AUDIT_FAIL_CLOSED` when the audit log is down) | `kinds`, `count`, `by` (the actor's id) |
| `auth.mfa_flagged` | a passkey's signature counter went back (a possible clone): the sign-in is refused and the key flagged | `kind`, `factorId`; never the credential id or key |
| `auth.mfa_recovery_used` | a recovery code signs someone in | `left` |
| `auth.password_change` | someone changes a password (Settings, profile; an admin); a reset link has `auth.password_reset` | `reason` (`self`, `admin`) |
| `auth.sign_in_failed` | a SAML or OIDC sign-in is refused or fails | `method` (`saml`, `oidc`), `reason` (`not_configured`, `provider_error`, `refused`, `bad_request`, `error`; no assertion or claim contents); at most one a minute per client address |
| `api.denied` | a GET or HEAD is refused with 401/403, also on paths the change log skips (binary files, agent sessions, MCP, assistant) | one per minute per (user, or client address when nobody is signed in) and route pattern, from an in-memory map of up to 10,000 keys, and at most 60 a minute in all (a caller rotating addresses can't flood the log); a refused change is still `api.request` with outcome `denied`.
