# Audit log and governance

Part of the [Landflow docs](../README.md); the [feature map](../README.md#feature-map) lists every feature page.

**Audit log** (Settings → Audit log, owners and admins; a project's **Audit log** tab for its admins). Every event says who (user or API key, with the key's id, never the key), when, from where (IP, user agent, request id, route pattern; never query strings or bodies), what it touched (target type, id and name, and the target's project) and the outcome (`success`, `failure` or `denied`). Recorded: sign-in, sign-out and failed sign-ins (wrong password, rate-limited, deactivated), password resets, invites, role changes and removed users, API keys created and revoked, workflows created, saved, imported, deleted, published, rolled back and unpublished, publish requests and their decisions, credentials created, changed and deleted, which credentials each run used (`credential.use`: credential, node, workflow and execution ids, never values; off in the settings), settings changes (general, MCP, AI prices, audit, governance, source control), executions stopped, stopped all and deleted, Git push, pull and sync apply, plugins registered and removed, an endpoint added to an existing plugin (`plugin.endpoint_added`: plugin id, endpoint, discovery source, transport) and a plugin's version change (`plugin.updated`), marketplace installs. On top of those, the route `handler` records every other change through the API (`api.request`) and every refused request (401/403, `denied`); reads, live events, triggers and plugin traffic are left out.

- **Stored** in `audit_events` (migration 900) with its own retention (default 365 days, 0 keeps them forever; separate from execution retention). Events still waiting for a SIEM destination are kept until delivered.
- **Per project** (migration 1500): an event about a workflow, credential, data table or agent records its home project, one about an execution its workflow's, one about a project that project (instance-wide targets such as users, API keys and settings have none). Events from before the migration have no project (no backfill).
- **Hash chain** (migration 1500): each event stores its place in the chain, the previous event's hash and its own, SHA-256 over a canonical form of every stored field. Changing a stored field, deleting an event (or the newest ones) or slipping one in breaks the chain at that point. On SQLite (and Postgres with one host) an event is chained in its insert transaction, which holds the database's write lock, so processes sharing the file take turns; in queue mode on Postgres events are stored unchained and sealed in Postgres in order under a transaction-level advisory lock (`pg_advisory_xact_lock`) within seconds by whichever process gets there first. **Verify chain** (Settings → Audit log, or `GET /api/audit/verify`) recomputes every hash and link (straight from Postgres in Postgres mode) and says where it breaks; the check is audited (`audit.verify`, a failure when broken). Retention prunes from the oldest end only and keeps the last pruned event's hash as the anchor, so the rest still verifies. Events recorded before the migration stay unchained (counted as legacy).
- **Signed heads and anchoring** (Settings → Audit log → Integrity, migration 1882): the hash chain proves the log wasn't edited, but someone who can rewrite the whole table can rewrite the chain too. The leader therefore verifies the whole chain on a schedule (default hourly, 60 s tick) and signs its newest link (`seq`, `hash`, time, key id) with an Ed25519 key kept sealed with the credential key (`audit_signing_keys`, `audit_heads`; refuses to sign a broken chain). `GET /api/audit/head` (scope `audit:read`) returns the newest signed head and every public key; **Sign and anchor now** and **Rotate key** (old keys keep verifying older heads) are in Settings and `POST /api/settings/audit/anchoring/run` and `/rotate-key`. **Anchors** put each signed head where the log's owner can't rewrite it: an S3 or MinIO bucket (`<prefix><seq, 12 digits>-<hash prefix>.json`, default prefix `audit-heads/`, explicit keys, never the default credential chain) and a webhook (`X-Landflow-Event: audit.head`, with `X-Landflow-Signature` when a secret is set); failures are retried on the next tick and shown in Settings. Secrets are sealed and never returned. `landflow audit verify` checks the chain on the host (exit 9 when broken); `landflow audit verify --head head.json --public-key key.pem` checks a head **offline** with Node's crypto only ([packages/cli](../../packages/cli/README.md)); signing is audited as `audit.sign_head`.
- **SIEM scope per project**: a destination can take every event (the default) or only chosen projects' events, plus instance events (sign-ins, users, settings; those with no project) when asked (`scope: { projectIds, instance }` on create and patch, `null` clears it; unknown project ids are a 400). It applies when an event is recorded, so a destination's outbox only holds events in its scope.
- **OpenTelemetry**: each event is also an OTel log record (`event.name` = `landflow.audit.<action>`, the actor, target and outcome as attributes, inside the request's trace), exported over OTLP/HTTP JSON when `OTEL_EXPORTER_OTLP_ENDPOINT` (or `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`) is set; `OTEL_LOGS_EXPORTER=none` turns that off.
- **Read**: `GET /api/audit` filters by actor (id, name or email), action (`workflow.*` for a category), target, project (`projectId`), outcome, time and text, newest first with a cursor; `GET /api/audit/export?format=csv|json` downloads the same filter (with the project and the chain columns; cells starting with `=`, `+`, `-` or `@` are defused for spreadsheets; the export is audited too). Owners and admins read every event; anyone else the events of the projects they are an admin of (their personal project and team projects where their role is admin), 403 for another project's. API keys need the `audit:read` scope.
- **SIEM streaming** (Settings → Audit log → SIEM streaming): destinations get every new event through a durable outbox (`audit_outbox`, written in the same transaction as the event): batches of up to 100, retried with exponential backoff (2 s doubling to 5 min, with jitter) until delivered, leased so a second host or a restart never sends a batch twice at once. **Send test event** sends one event straight away and says what the receiver answered; **Retry now** skips the backoff. Secrets are encrypted like credentials and never come back from the API. Syslog over TLS and HTTPS destinations can trust a private CA and present a **client certificate** (mTLS) to receivers that require one: the certificate (PEM, may include its chain), its private key and an optional passphrase; the key and passphrase are sealed like the other secrets, the certificate and key are checked to belong together when saved, and Settings shows the certificate's subject and expiry.

| Destination | Settings | What it sends |
|---|---|---|
| Syslog | host, port, UDP / TCP / TLS (certificate check, optional CA, optional client certificate), facility (default 13, log audit), app name, TCP framing (RFC 6587 octet counting or newlines) | RFC 5424 with the event as structured data (`[landflow@32473 id=… action=… outcome=… actorId=… targetType=… projectId=… chainSeq=… hash=…]`), `MSGID` the action and the event's JSON as the message |
| HTTP (JSON lines) | URL, optional signing secret | `application/x-ndjson`, one event per line; `X-Landflow-Timestamp` and `X-Landflow-Signature: sha256=<HMAC-SHA256 of "<timestamp>.<body>">` |
| HTTP (Datadog) | logs intake URL (any site), API key, tags | Datadog's logs API (`DD-API-KEY`, `ddsource: landflow`, `service`, `ddtags`) |
| HTTP (Elasticsearch) | URL, index or data stream, optional API key | `_bulk` `create` with the event id as `_id` (a retried batch never duplicates) |
| Splunk HEC | HEC URL, token, index, source, sourcetype | `/services/collector/event` with `time` from the event |

To try it locally, `docker compose -f deploy/compose.infra.yml --profile siem up -d siem` runs a Vector receiver: syslog on `localhost:55514` (TCP and UDP) and JSON lines on `http://localhost:55080/`; `docker compose -f deploy/compose.infra.yml logs -f siem` prints what arrives.

**Governance** (Settings → Governance; owners and admins change it, everyone sees it). With every rule off, nothing changes.

- **Nodes**: allow only, or block, node types (ids or globs like `messaging.*`) and whole plugins; **Block Code nodes** on its own. **HTTP Request hosts**: allow only or block host names (globs), `host:port`, IPv4 and IPv6 addresses and CIDR ranges (`10.0.0.0/8`, `fd00::/8`, `[::1]:8080`; an IPv4-mapped IPv6 address counts as its IPv4 address), checked for each item's URL. **MCP servers**: allow only these URL patterns or hosts for the MCP Client node and tool and AI agents' MCP servers.
- **Per project and per workflow**: a project's admins can allow only some node types and plugins for its workflows and agents (the project's **Settings** tab → Allowed nodes; `PATCH /api/projects/:id/settings`, migration 1401), and a workflow can narrow that further and ask for four-eyes publishing for itself even when the instance doesn't (Workflow settings → Governance; `PUT /api/workflows/:id/policy`, admins of its project). A project can ask for four-eyes for **all** its workflows (the project page → Governance → *Require four-eyes on publishing*, `fourEyes` in `PATCH /api/projects/:id/settings`), which also turns a promotion that changes one of them into a request (see [Environments](secrets-and-environments.md)). Each level only narrows the one above; the checks are the instance's (below), and the error says where the rule was set.
- **Where it applies**: saving a workflow that breaks a rule saves it with a warning (`policyWarnings`); publishing it (editor, API, CLI, Git sync, the instance MCP server) is refused with 422; at run time a blocked node fails with "Blocked by policy: …" and the hint to Settings → Governance, in the host and in queue workers, for manual, trigger, sub-workflow and agent runs. The node creator hides blocked node types, the import report lists them, templates using them are marked unusable. Disabled nodes don't count.
- **Four-eyes publishing**: Publish, a rollback from the version history and (by default) Unpublish become a request (`202 { approvalRequired: true, request }`, migration 901) with the note and what it changes against the live version ("2 nodes changed, 1 added"). Someone else approves (which publishes it, credited to the requester, "approved by …" in the note) or rejects it with a comment; nobody approves their own request. Approvers are any other builder (member, admin or owner) or only owners and admins; project roles plug in through `registerApproverCheck` (`lib/server/governance/approvals.ts`): a project's Settings tab says who approves its workflows' requests (the instance's rule, its admins, its admins and editors, or instance owners and admins only; `lib/server/governance/project-approvers.ts`). A request goes **stale** when the draft or the live version changes before it is decided, and a new request replaces the workflow's pending one. Approvers are emailed (with `LANDFLOW_SMTP_HOST`) and chosen alert channels hear about new requests; the requester hears the decision. Everything is in the audit log. The editor's Publish menu shows "Awaiting approval" with Approve / Reject / Withdraw; Settings → Governance lists every request. The CLI's `workflows publish`, `unpublish`, `activate` and `deactivate` exit with code 8 (`approval_pending`, the request in `details.request`).
- **Scheduled publishes**: publish or unpublish a workflow at a time (Publish menu → *Schedule…*, or Version history → *Schedule…* on a version; `POST /api/workflows/:id/publish` and `/unpublish` with `"at": "<ISO time>"` answer 202 `{ scheduled }`; `landflow publish <wf> --at 2026-11-01T09:00Z|+2h|+1d`, `landflow unpublish <wf> --at …`; `landflow workflows schedules <wf>` lists them and `landflow workflows unschedule <wf> <id>` cancels one; `GET /api/workflows/:id/schedules`, `DELETE …/schedules/:scheduleId`). Schedules live in `scheduled_publishes` (migration 1840): the leader main polls every 5 s, claims a due row, publishes the pinned version (or unpublishes) as the user who scheduled it, and records `done`, or `failed` with the reason (a version pruned by then, a blocked node, a missing workflow); after a crash, rows left running are recovered at start. With **four-eyes** on, scheduling files a request instead (Awaiting approval, with the time): approving *releases* the schedule, which then goes live at its time; a rejected, withdrawn or stale request cancels it, and a schedule made before four-eyes was turned on becomes a request when its time comes. The creator or an admin cancels; schedule changes are audited (`publish_schedule.create`, `.cancel`, `.run`); scheduling is allowed in a protected environment (it publishes later through the same checks).

- **SCIM provisioning**: every change an identity provider makes through `/scim/v2` is a domain event, recorded as the SCIM token's user with the token's API key id, the request id, address and user agent: `user.provision` (email, name, role, active, external id), `user.update` (`nameFrom`/`nameTo`, `emailFrom`/`emailTo`, `roleFrom`/`roleTo`, `externalIdFrom`/`externalIdTo`, only the ones that changed; a role change a group mapping causes is one too), `user.deactivate` and `user.reactivate` (`activeFrom`/`activeTo`), `user.remove`, `group.create`, `group.update` (name and external id before and after), `group.members_change` (`added` and `removed` user ids) and `group.remove` (with the member ids). A rejected token (missing, unknown, expired, wrong scope, not an owner or admin) is `scim.auth_failed` with outcome `denied`, at most once per client address per minute (the addresses are held in memory, up to 10,000) and at most 60 a minute in all, so an identity provider retrying in a loop, or a caller rotating its address, can't flood the log. A 403 (a valid key without the `scim` scope, or whose user is not an owner or admin) carries the key id and user id in its details. A bulk sync records one event per change, which is intended. The generic `api.request` event doesn't cover `/scim/v2`.

**Permission, secret and access events** (wave 3, P12). The library functions record them, so the UI, API, CLI, MCP tools, SSO and SCIM group mapping all produce the same event, once each (the generic layer stays out of a request that recorded one). `from` and `to` are flat details; no value of a variable, secret, credential or password is ever stored.

| Action | Recorded when | Details |
|---|---|---|
| `project.create`, `project.update`, `project.delete` | a team project is made (also by SSO/SCIM group mapping), renamed or re-described, deleted | `name`; `name_from`/`name_to` (also `description_`, `icon_`) for what changed; `transferredTo` and `moved` (`kind:count`) on delete |
| `project.member_change` | a member is added, removed or has their role changed (the members page, project creation, group mapping) | `change` (`added`, `removed`, `changed`), `userId`, `email`, `from`, `to` (roles; null when absent), `source` (`saml`, `scim`) |
| `resource.share`, `resource.unshare` | a workflow or credential is shared with a project or user (new, or its role changed), or a share is removed | `kind`, `resourceId`, `withProjectId`, `withProject`, `from`, `to` (share roles) |
| `resource.transfer` | "Move to project" for a workflow, credential, data table or agent | `kind`, `resourceId`, `from`, `to` (project ids), `toName`, `keepAccess`, `sharedCredentials`; the access a move keeps or the credentials it shares are `resource.share` events of their own |
| `variable.create`, `.update`, `.delete` | an instance variable or a project's | `scope` (`instance`/`project`), `projectId`, `key`, `from`/`to` on a rename, `valueChanged` (never the value) |
| `secret_provider.create`, `.update`, `.delete` | an external secrets provider | `provider`, `kind`, `enabledFrom`/`enabledTo`, `fieldsChanged` (setting names only) |
| `auth.password_change` | someone changes a password (Settings, profile; an admin); a reset link has `auth.password_reset` | `reason` (`self`, `admin`) |
| `auth.sign_in_failed` | a SAML or OIDC sign-in is refused or fails | `method` (`saml`, `oidc`), `reason` (`not_configured`, `provider_error`, `refused`, `bad_request`, `error`; no assertion or claim contents) |
| `api.denied` | a GET or HEAD is refused with 401/403 | one per minute per (user, or client address when nobody is signed in) and route pattern, from an in-memory map of up to 10,000 keys; a refused change is still `api.request` with outcome `denied` |
| `sync.export`, `datatable.export` | `GET /api/sync/export`; a data table's CSV | files and the summary counts (workflows, variables, tables, credentials), `values`; rows, columns, bytes |
| `credential.test` | `POST /api/credentials/test` (it decrypts and sends the credential) | `type`, `credentialId`, `ok` |
| `agent.tool_approval` | a person approves or denies a paused tool call (`POST /api/agents/:id/sessions/:sid/approvals`) | `decision`, `tool`, `sessionId`, `callId` |
