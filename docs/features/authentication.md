# Authentication

Part of the [Landflow docs](../README.md); the [feature map](../README.md#feature-map) lists every feature page.

Everything except the public routes below needs a signed-in user or an API key.

- **Owner**: a fresh instance opens on **/setup**, which creates the owner. For Docker and CI, set `LANDFLOW_OWNER_EMAIL` and `LANDFLOW_OWNER_PASSWORD` (and optionally `LANDFLOW_OWNER_NAME`) and boot creates the owner instead, if no user exists yet. Once anyone exists the variables are ignored.
- **Passwords and sessions**: passwords are hashed with scrypt (N=16384, r=8, p=1, a random salt per user). Signing in starts a session: a random token in the `landflow_session` cookie (HttpOnly, SameSite=Lax, and Secure over https or behind a proxy that sends `X-Forwarded-Proto: https`), kept only as its SHA-256 hash with an expiry (14 days, `LANDFLOW_SESSION_TTL_HOURS`). **Sign out** (user menu, bottom of the sidebar) deletes it. Failed sign-ins are limited to 10 per email and 30 per IP address (see Client addresses below) in 15 minutes (`LANDFLOW_LOGIN_MAX_ATTEMPTS`); setup, invite, reset and forgot-password forms to 30 per IP. Cookie-authenticated changes from another origin are refused.
- **Session hardening**: a session unused for `LANDFLOW_SESSION_IDLE_HOURS` (72 in production, off in development, `0` = off) is signed out the next time it is used; the absolute limit stays `LANDFLOW_SESSION_TTL_HOURS`. A tab left open is not use: the live event stream re-checks the session every 30 s without marking it used, and closes once the idle limit passes; the requests the browser makes on its own (the editor's edit-lock heartbeat every 10 s, the polling of the executions pages, Run Trace, run controls, agent sessions, the notebook, workers and MCP settings, and the reloads after a live event) send `X-Landflow-Background: 1` (`api(path, { background: true })` in `lib/client/api.ts`), and the guard resolves those, and `GET /api/events`, without marking the session used. The header can only make a session end sooner, so it is trusted as sent. Page loads and anything a person does (a save, a run, a click that calls the API) count as use. Changing a password (your own through Settings; an admin-set password is covered by the same rule, though no route does that yet) ends that user's other sessions and keeps the one you are using; the `auth.password_change` audit event carries `sessionsRevoked`. A cookie-authenticated change with no `Origin` header is refused when the browser's `Sec-Fetch-Site` says `cross-site` (`same-origin`, `same-site` and `none` pass). Passwords keep a minimum of 8 characters with no breached-password check (that would need an external call); the minimum is not configurable because the forms check it from a shared constant.
- **Local sign-in modes** (`LANDFLOW_LOCAL_SIGN_IN`): `all` (default), `owner` (only the owner signs in with a password, the break-glass account if SSO breaks) or `off` (SSO only: OIDC or SAML, which bring the identity provider's MFA). With `off` the login route answers 403 after a correct password and the login page hides the password form (or, with no SSO configured, says so). The check comes after the password on purpose, so a refusal does not tell a stranger which emails have an account; the price is that a 403 (rather than 401) tells the caller the password was right. Such an attempt is audited as `auth.sign_in_failed` (reason `local-sign-in-disabled`), and a wrong password still counts against the sign-in limits. Landflow's own second factor (below) is optional; `off` is still the way to rely on an identity provider's MFA alone; use `owner` rather than `off` until SSO is proven, because `off` with broken SSO locks everyone out. The same rule covers password resets: Forgot password sends nothing to a user the mode refuses (the answer is unchanged), and a reset link, an admin's included, is refused with 403 (the reset page says so before it shows a form) rather than setting a password and signing in. Settings → Users still lets an admin make a reset link for such a user; the link is then refused. Two one-off paths still sign in with a password: first-run setup and invite acceptance (an admin-authorised account, session up to 14 days); under `off` the first-run owner cannot sign in with a password once that session ends, so start with `owner`.
- **Roles**: one **owner**, **admins** and **members**. Owners and admins manage users, settings, credential sharing, plugins, variables and the instance MCP server, and can take over a workflow someone else is editing; members build and run workflows. Only the owner manages admins, and nobody changes or removes the owner. The rules live in one place, `can(user, action)` in `apps/web/src/lib/shared/auth.ts`, and the server checks them on every route.
- **Projects and sharing**: every workflow, credential, data table and agent belongs to one **project**. Each user has a **personal project** (what they create goes there); owners and admins create **team projects** (sidebar → project switcher → **New project**, or `/projects`) and give members a role there: **admin** (manages members, shares and moves its items), **editor** (creates, edits and runs them) or **viewer** (opens them and their executions). Members see only their projects' items and what is shared with them; the owner and admins see everything, so a single-user install works as before. **Share** (a workflow's or credential's menu) grants a person or a team project access: workflows as editor or viewer, credentials as "can use", which lets their workflows' nodes use them while the secret stays hidden and unchangeable; agents are shared the same way (an agent can also be shared with **All projects**), and members of a project that only uses an agent never read its sessions, evaluations or live events. **Move to project** changes the home project (admins of the current project, editors of the target); moving a workflow can share the credentials it uses with the new project, and a moved credential can stay usable by the old one. The checks run in the route guard on every resource route (`lib/server/auth/policy.ts` `resourceRule`, `lib/server/projects/access.ts`), in lists, search, the node panel's credential picker and live events, and in runs: a workflow only resolves credentials its project owns or was shared, so a run with another project's credential fails at that node. API keys act as their user. Removing a user asks who or which project gets what their personal project owns (moved and removed in one transaction); deleting a team project moves what it owns to another. On upgrade, migration 800 gives every user a personal project and puts existing workflows and data tables in the owner's personal project; boot adopts existing credentials and agents the same way. `projectRole(user, projectId)` in `lib/server/projects/access.ts` is the one helper that says what someone may do in a project. A project also has a brief and serves goals: see [projects-and-goals.md](../projects-and-goals.md).
- **Project page** (`/projects/<id>`): four tabs, Overview (the counts of workflows, credentials, data tables and agents, each opening its page for the project; a **New ▾** that makes one in it; its data tables and agents with Move to project…), Members, Settings (name, allowed nodes, publish approvers, MCP, Variables, delete) and Audit log. Links with the earlier `?tab=workflows|credentials|dataTables|agents` open the Overview and `?tab=variables` opens Settings. **Credentials**: **New credential** opens a searchable list of types grouped by app; `/credentials?project=<id>` shows one project's (a project the viewer can't read says so in place of the list). The invite page shows only the message when the link is invalid, used or expired.
- **Users** (Settings → Users): invite by email with a role; the invitee picks a name and password at `/invite/<token>` (7 days, used once). With `LANDFLOW_SMTP_HOST` set the link is emailed; without it Settings shows the link to copy. Admins change roles, remove users (signing them out and deleting their API keys; what their personal project owns moves to the person or project chosen) and make password reset links (1 hour). With SMTP, **Forgot password?** on the sign-in page emails a reset link; resetting signs you out everywhere else.
- **Single sign-on (OIDC)**: set `LANDFLOW_OIDC_ISSUER`, `LANDFLOW_OIDC_CLIENT_ID` and `LANDFLOW_OIDC_CLIENT_SECRET` and the sign-in page gets a **Sign in with SSO** button (authorization code flow with PKCE; register `<public URL>/api/auth/oidc/callback` as the redirect URI). First-time users get an account (just in time); an existing account with the same verified email is linked. `LANDFLOW_OIDC_ROLE_MAP` maps values of the role claim (`LANDFLOW_OIDC_ROLE_CLAIM`, default `roles`, dotted paths like `realm_access.roles` work) to Landflow roles, e.g. `landflow-admin=admin,landflow-editor=member`; the mapping is applied at every sign-in (never to the owner). Users without a mapped role get `LANDFLOW_OIDC_DEFAULT_ROLE` (`member`; `none` refuses them). Settings → Security shows the configuration and checks discovery. The infra stack's Keycloak is set up for this ([deployment.md](../deployment.md#sign-in-email-and-sso)).
- **Single sign-on (SAML 2.0)**: set `LANDFLOW_SAML_IDP_METADATA_URL` (or `LANDFLOW_SAML_ENTRY_POINT`, `LANDFLOW_SAML_IDP_ISSUER` and `LANDFLOW_SAML_IDP_CERT`) and the sign-in page gets a **Sign in with SAML** button (Okta, Entra ID, ADFS, Keycloak…). Give the IdP this instance's metadata at `<public URL>/api/auth/saml/metadata` (entity id `<public URL>/api/auth/saml/metadata`, ACS `<public URL>/api/auth/saml/acs`, HTTP-POST). Assertions must be signed by the IdP's certificate (`LANDFLOW_SAML_WANT_ASSERTIONS_SIGNED=false` accepts a signed response instead); the audience, issuer, `InResponseTo`, time window (`LANDFLOW_SAML_CLOCK_SKEW_SECONDS`, 120) and RelayState are checked and each response and assertion is accepted once. Users are found by their NameID (persistent), then linked by email, or created just in time (`LANDFLOW_SAML_JIT=false` requires an invite or SCIM first); deactivated users are refused. `LANDFLOW_SAML_ROLE_MAP` maps values of the role attribute (`roles`) to Landflow roles at every sign-in (never the owner), `LANDFLOW_SAML_PROJECT_MAP` maps values of the group attribute (`groups`) to team projects (`data-team=Data:editor`). Signing out also signs out at the IdP when it offers single logout, and an IdP-initiated logout ends the user's sessions. Sign-ins in flight (RelayStates), the request ids `InResponseTo` must match (one use) and each SAML session's NameID and SessionIndex for logout live in the database (`saml_state`, migration 1501) with an expiry, so a sign-in can start on one main and finish on another, a logout reach any main, and restarts forget nothing; on Postgres, taking a request id and recording a replay id are decided in Postgres, so of two mains given the same response only one accepts it. **Encrypted assertions**: in Settings → Security → SAML, generate a decryption key (RSA 2048, self-signed, ten years) or upload a certificate and RSA key (PEM, an encrypted key with its passphrase); the key is sealed like credentials, the certificate goes into our metadata as a `use="encryption"` KeyDescriptor (AES-GCM and AES-CBC offered), and copying it to the IdP lets it encrypt assertions (RSA-OAEP or RSA 1.5 key transport). The decrypted assertion's signature and id are checked like a plain one's. **Require encrypted assertions** refuses responses whose assertion arrives in the clear. `LANDFLOW_SAML_DECRYPTION_KEY` and `LANDFLOW_SAML_DECRYPTION_CERT` set the key pair from the environment instead (Settings then shows it read-only). **Key rotation with two certificates**: stage a *next* decryption key beside the current one (**Generate next key**, or `POST /api/settings/security/saml/encryption {"action":"upload","slot":"next",…}`; or `LANDFLOW_SAML_DECRYPTION_NEXT_KEY` / `_NEXT_CERT`). Our metadata then publishes both certificates as `use="encryption"` KeyDescriptors and a response decrypts with whichever key opens it, so the IdP can pick up the next certificate at its own pace. **Switch over** (`{"action":"switch"}`) makes the next pair the current one and keeps the old key as *retired*: it still decrypts what the IdP encrypted to it but is no longer in the metadata, until you discard it (`{"action":"discard","slot":"previous"}`); each step is audited. The signing key rotates the same way: set `LANDFLOW_SAML_NEXT_CERT` to the next certificate and the metadata publishes both signing certificates (Settings shows them); when the IdP has the new one, move the next key and certificate into `LANDFLOW_SAML_PRIVATE_KEY` / `LANDFLOW_SAML_CERT`. Settings → Security shows what to give the IdP, what was read from its metadata and when its certificate expires.
- **API keys** (Settings → API keys, or the user menu): keys for scripts, CI and the CLI, sent as `Authorization: Bearer lf_…` or `X-Landflow-API-Key: lf_…`. A key acts as its user, limited to its scopes: `workflows:read`, `workflows:write`, `executions:read`, `executions:write`, `run`, `brain:read` (your own briefing and asking the brain) and `brain:write` (record your own work; includes `brain:read`), both for any member's own key and reaching nothing else ([work-and-briefings.md](../work-and-briefings.md)), `audit:read` (the audit log: owners and admins read every event, project admins their projects') and `admin` (everything; only owners and admins can create one, and admin-only routes still need an admin user). Every role makes keys with the brain and workflow scopes, from Settings → API keys or from **Connect your harness** (`/connect`, [connect-your-harness.md](../connect-your-harness.md)); the route refuses `admin` and `scim` to anyone else with the reason. Keys have a label and an optional expiry (no default: "never" stays a choice), are shown once and stored as a SHA-256 hash, and can't manage API keys. **Limits, fixed at creation** (changing one means a new key, then delete the old: there is no rotate button): an **allow-list** of up to 50 IPv4/IPv6 addresses or CIDR ranges (`10.0.0.0/8`, `2001:db8::/32`, `localhost`; an IPv4-mapped IPv6 caller counts as its IPv4 address; every entry is checked and a bad one answers 400 naming it) and a **use cap** of 1 to 1,000,000. The caller's address is the one `clientAddress()` yields under `LANDFLOW_TRUSTED_PROXIES` (the rule rate limits and webhook allow-lists use): with one or more proxies counted, only the entry your own proxy appended counts and a forged leftmost hop is ignored; with none counted (unset or 0) the caller's own `X-Forwarded-For` is taken, so a list can be got around. In production, creating a key or SCIM token with an address list is therefore refused (400) until `LANDFLOW_TRUSTED_PROXIES` is set on purpose (0 for direct clients); elsewhere the form warns under the box. A caller with no address (a blank header) is refused by any list. A range that allows everyone (`0.0.0.0/0`, `::/0`, `::ffff:0:0/96`) is refused: leave the list empty. SCIM tokens take the same list and cap in their form, and a used-up token shows it. A key used from outside its list gets 401 "This API key can’t be used from this address" (never the list); the call that would pass the cap gets 401 "This API key has used all its uses", and neither falls back to a session cookie. A **use** is a request the guard let through and that reaches its handler (after the rate limiter): requests refused for a scope, a role or the limiter are free, a key with no cap writes nothing. The count is exact across processes: one conditional write in the `api_key_uses` table (`INSERT … ON CONFLICT … WHERE uses < cap` in Postgres, one `BEGIN IMMEDIATE` transaction on SQLite), a Postgres round trip per request of a capped key. An exhausted key stays listed as "used up" until deleted. Each refusal writes `api.denied` with `reason` `ip_not_allowed` or `uses_exhausted` and the key's id and label (never the key), once a minute per key and route; the create event records the list and the cap. Every key records the **address it was last used from** next to "last used" (written with that once-a-minute touch, so it can lag a minute); only the key's owner sees it in Settings → API keys, and instance admins find callers' addresses in the audit log. The same rules hold for **SCIM tokens** (a SCIM error document) and the instance **MCP** endpoint (`/api/mcp`, a bearer challenge); keys made before the change have no list and no cap and behave as before. **Settings → API docs** lists the endpoints with the scope each needs; the OpenAPI 3.1 document is at `GET /api/openapi.json`.
- **Provisioning (SCIM 2.0)**: Okta, Entra ID and other identity providers create, update, deactivate and remove users, and push groups, at `<public URL>/scim/v2` (`Users`, `Groups`, `ServiceProviderConfig`, `Schemas`, `ResourceTypes`; filters such as `userName eq "…"`, `externalId eq`, `emails[type eq "work"].value eq`, `and`/`or`; `startIndex`/`count` paging; PATCH as both providers send it). Authenticate with a **SCIM token** from Settings → Security: an API key with only the `scim` scope (owners and admins create them; an `admin` key isn't one, and a SCIM token can do nothing else), sent as the bearer token. `userName` must be the user's email address (the default for both providers); new users are members without a password, so they sign in through SSO. `active: false` deactivates: the user is signed out everywhere and can't sign in or use API keys until reactivated (the owner can't be deactivated). Deleting a user moves what they own to the owner's personal project. Groups give access through `LANDFLOW_SCIM_GROUP_MAP`, e.g. `Landflow Admins=role:admin,Data Team=project:Data:editor`: `role:admin`/`role:member` sets the instance role of users the provider manages (admin while in an admin group, member otherwise; only when the map has a `role:` entry), `project:<id or team project name>[:admin|editor|viewer]` makes the group's members members of that team project (created if missing), and a group the map doesn't name but that has a team project's name makes its members editors there. Memberships SCIM adds go when the user leaves the group; ones people added stay. `/scim/v2/*` is public to the proxy and the guard and checks the token itself; the discovery documents need no token. Errors are SCIM error documents; an unexpected failure is a 500 whose `detail` is `Internal error (request <id>)`, the id the `X-Request-Id` header and the host's log carry.
- **Editing together**: one editor tab at a time edits a workflow. Others see "<name> is editing" and a read-only canvas, which follows the editor's saves; the workflow becomes editable when that tab closes (or 30 s after it stops heartbeating). Owners and admins can **Take over**, and you can move editing to another tab of your own. A save from a tab that lost the lock is refused (423). Workflows record `createdBy` and `updatedBy` (from the person saving, never from the saved body; a save with no person behind it that changes the graph or its pin data clears `updatedBy`), every version records who saved it, and every execution a person starts records `startedBy` (manual and chat runs, MCP calls, agent tool calls (the agent's caller: the run it works in while that run is running or waiting, or the person in its test chat; never the request around it, and nobody once the run has ended, as when an approval is decided later), re-runs, retries they ask for, and sub-workflows of these; an automatic retry keeps the starter of the run it retries); trigger, poll and webhook runs record nobody.
- **Plugins** keep registering at `/api/plugins/announce` and the gRPC registry without a user. Set `LANDFLOW_REGISTRY_SECRET` on the host to require a shared secret there; set the same variable on the plugins (the TypeScript, Go and Python SDKs send it as `X-Landflow-Registry-Secret` or gRPC metadata, and host-managed node plugins get it automatically). Plugins found by Kubernetes discovery prove they hold it instead: the host challenges them on GetManifest and the SDKs answer with an HMAC (docs/protocol.md §13).

Public without credentials: `/api/health`; the sign-in pages (`/login`, `/setup`, `/invite/*`, `/forgot-password`, `/reset-password/*`) and `/api/auth/*` except `/api/auth/me`; triggers with their own auth: `/api/webhook/*`, `/form/*`, the test URLs `/api/webhook-test/*`, `/form-test/*` and `/mcp-test/*` (only while an editor listens), `/api/waiting/*`, `/mcp/*` (MCP Server Triggers), `/api/mcp` (the instance MCP server's token) and `/scim/v2/*` (a SCIM token); `/api/oauth2/callback`; `/api/slack/*` (verified with Slack's signing secret); `/api/teams/*` (the Bot Framework JWT is validated); `/api/approvals/email/*` (signed, single-use approval links); hosted chat pages (`/chat/*`); `/api/binary/*` with a plugin's per-call token; `/api/plugins/announce` (with the registry secret when set); Next.js static files. `/api/metrics` needs a session or an API key with `executions:read` unless `LANDFLOW_METRICS_PUBLIC=true`. The list is `PUBLIC_ROUTES` in `apps/web/src/lib/shared/auth-paths.ts`; the Next.js proxy (`apps/web/src/proxy.ts`) redirects pages to `/login` and answers 401 for API routes, and the route guard in every handler checks sessions, keys, scopes and roles.

**SCIM audit**: every provisioning change and every rejected SCIM token is an audit event (`user.provision`, `user.update`, `user.deactivate`, `user.reactivate`, `user.remove`, `group.create`, `group.update`, `group.members_change`, `group.remove`, `scim.auth_failed`), credited to the token's user and key id; see [Audit log](audit-and-governance.md).

## Second factor

A local account can add passkeys and an authenticator app (TOTP) under **Sign-in & security** (user menu, `/account/security`). It is optional for everyone: `LANDFLOW_MFA_REQUIRED` defaults to `off` in every profile, production included.

- **Enrol**: Add authenticator app shows a QR code (an SVG data image) and the setup key as text; a current code confirms it. The secret is sealed with the key ring (re-sealed by key rotation) and never shown again. The first factor makes ten **recovery codes** (`XXXXX-XXXXX`, 50 bits each), shown once with Copy and Download; each works once, a new set replaces the old, and they are stored as keyed hashes (HMAC-SHA-256 under a key derived from the vault's). The secret is sealed on the default seal purpose, the only one key rotation re-seals. Starting an authenticator app asks for the account's current password (so a stolen session can't enrol its own app), and an enrolment left unconfirmed for 15 minutes is dropped. One authenticator app per account; accounts with no password (single sign-on only) use their provider's factor.
- **Sign in**: after the password (and every check the login route makes) a user with a factor gets `202 { mfaRequired, methods, challenge }` and no cookie. The challenge is a random single-use token (its SHA-256 is the row id in `mfa_challenges`), valid 5 minutes, bound to the user, and good only for `POST /api/auth/mfa/verify`; five wrong codes burn it. A right code starts the session (`password+totp`, `password+recovery`); using a recovery code says how many are left, is audited as `auth.mfa_recovery_used` and is emailed to the person when SMTP is set up. A password reset by mail link sets the password and then asks for the factor too. Setup and invite acceptance make accounts with no factor.
- **Passkeys** (WebAuthn, `@simplewebauthn/server` and `/browser`): **Add a passkey** asks for the account's current password (as the authenticator app does), a name and then the browser's prompt (fingerprint, face, screen lock or a security key). A person can have up to ten, each named (the eleventh is a 409); the first second factor of any kind brings the recovery codes. The relying party id is the host of the public URL and the expected origin is its origin, both from `LANDFLOW_PUBLIC_URL` and never from a request header: **WebAuthn only works when `LANDFLOW_PUBLIC_URL` is the address in the browser** (`localhost` is allowed over http; anything else needs https). Attestation is `none` (nothing trusts the device's maker), user verification is `preferred`, and the credential is not discoverable (a passkey is a second factor here, not a passwordless login). Every ceremony runs on a challenge held in `mfa_challenges` (so any main can verify): the sign-in challenge (`POST /api/auth/mfa/options` gives the browser's options, `POST /api/auth/mfa/verify` with `method: 'webauthn'` answers; the five-answer limit counts passkey answers too) and one made for adding a passkey or a step-up (`POST /api/me/mfa/passkeys/options`, purpose `register` or `step-up`): a challenge works once, only for the person it was made for and only for its purpose, and a failed answer burns the WebAuthn challenge so the next try asks for new options. A session that may only enrol (the policy asks for a factor) can add a passkey. The sign-in is `password+webauthn`. A passkey also answers a step-up.
- **Signature counter**: a passkey's counter is stored and may only move forward, decided in one conditional write (`takeOnce`, so two mains agree). An authenticator that never counts (always 0) is allowed. A counter that is lower than, or equal to, the stored non-zero one (or 0 after it had counted) refuses the sign-in, flags the key (Sign-in & security shows **flagged**), records `auth.mfa_flagged` and stops offering that passkey until it is removed: a cloned key signs from its own count. Credential ids are unique across the instance.
- **Codes**: RFC 6238, SHA-1, 6 digits, 30 seconds, one step either side (so a device clock within about 30 seconds works). A code is accepted once: the factor's `last_step` only moves forward, decided in the database (`takeOnce`, a conditional write on Postgres in queue mode), so two mains agree. Compared in constant time. Wrong codes count against the sign-in limits (per email and per IP, 429) and are audited as `auth.sign_in_failed` with reason `mfa`; a user with a factor keeps their failed-attempt count until the second step succeeds.
- **Policy** (`LANDFLOW_MFA_REQUIRED`): `off`, `admins` (owners and admins) or `all`. A covered local account without a factor can only enrol: every other route answers 403 `mfa_enrolment_required` and pages redirect to `/login/second-factor?enrol=1`. It is computed on each request, so sessions made before the mode was switched on are caught. A covered account cannot remove its last factor (409). Single sign-on sessions (OIDC, SAML) are never asked; API keys, MCP tokens, SCIM tokens and CI tokens are not affected, and `/api/me/mfa*` is session-only.
- **Step-up**: removing a factor and making new recovery codes need a second-factor check from the last five minutes (`POST /api/me/mfa/step-up`; 403 `mfa_step_up_required` otherwise). Enrolling, signing in with a factor and a step-up all record `mfa_verified_at` on the session.
- **Reset**: Settings → Users shows a "2-step" badge and a Reset second factor button. The owner resets anyone's but their own; an admin resets members' and other admins', never the owner's. It removes the factors and codes, ends the person's sessions and records the high-value `auth.mfa_reset` in the same transaction (503 and no change when `LANDFLOW_AUDIT_FAIL_CLOSED` is on and the audit log is down).
- **Audit**: `auth.mfa_added`, `auth.mfa_flagged`, `auth.mfa_removed`, `auth.mfa_reset`, `auth.mfa_recovery_used`, `auth.mfa_recovery_regenerated`; details hold ids and kinds, never a secret, code, challenge, credential id or public key.
- **Not covered**: passkeys as the only factor (passwordless sign-in), attestation checks or an allow-list of authenticator makers, renaming a passkey, SMS or email codes, "trust this browser", a password-change screen, a second factor for SSO accounts.

## Client addresses and emailed links

The address used for per-IP sign-in limits, session and audit records and webhook IP allow-lists comes from
`X-Forwarded-For`, trusted only up to `LANDFLOW_TRUSTED_PROXIES` hops (default 0). Next.js sets the header to the socket
address when the request has none, so with 0 the last entry is used: behind no proxy that is the real client, but a
client that connects directly can still send the header, and the address is not verified. With N >= 1 the entry N from the
end is the client (the address the outermost trusted proxy saw; the leftmost when the list is shorter), entries before it are
ignored, and `X-Real-IP` is read only when the header is absent. Ports, IPv6 brackets and `::ffff:` prefixes are removed. In
the production profile an unset `LANDFLOW_TRUSTED_PROXIES` logs one warning that addresses are unverified.

`X-Forwarded-Host` and `-Proto` build the host's own origin (redirects, SCIM URLs) only with `LANDFLOW_TRUSTED_PROXIES` >= 1.
Without them and without `LANDFLOW_PUBLIC_URL` the origin is the address Next.js is bound to (`http://localhost:3000`),
not the name the browser used: set `LANDFLOW_PUBLIC_URL` when the host is reached by another name (`127.0.0.1`, a LAN
address, a phone), or OIDC and SAML redirects, single logout, the OpenAPI server URL, SCIM locations and invite links
point at `localhost`.

Invite and password-reset links use `LANDFLOW_PUBLIC_URL`. In the production profile without it, Forgot password, an
invite and an admin's reset link answer 503 ("Set LANDFLOW_PUBLIC_URL to send links") before any account is looked up or
