# Engine

Part of the [Landflow docs](../README.md); the [feature map](../README.md#feature-map) lists every feature page.

- **Data model** (n8n's): items `{ json, pairedItem }`, nodes return one array per output, and an empty output stops that branch.
- **Scheduling**: n8n v1 "depth-first by branch", with siblings ordered by canvas position. Multi-input nodes (Merge) wait for every connected input, or run with what they have once the stack drains.
- **Expressions**: `{{ $json.x }}`, `$('Node').item`, `$input`, `$now`, `$workflow`, `$execution`, `$itemIndex`, `$vars.NAME`. They are resolved by the host per item, so plugins only ever see concrete values. An expression sees one item; `$input.all()` gives every item (the Code node's `items` isn't defined there, and the error says so).
- **Errors**: `onError: continue` (sent to the plugin as `continueOnFail`, so integrations turn a failing item into `{ error }` and keep the rest), `retryOnFail`/`maxTries` (a fixed wait between tries, `waitBetweenTriesMs`, or `retryBackoff: exponential`, which doubles it after each failed try up to a minute; the node's Settings show both), a per-node `timeoutSeconds` (an attempt that takes longer fails with "Node timed out after N s" through the node's abort signal; retries and `continue` apply), disabled nodes pass data through, plus pin data, `executeOnce` and `alwaysOutputData`.
- **Live events**: `execution.started`, `node.started`, `node.finished` (with item counts and the run), `node.log`, `node.progress` (what a running node reports with `ctx.sendProgress`, in-process nodes: `{ executionId, nodeId, nodeName, parentNodeId?, data, at }`, at most twice a second per node, the last one always sent; `parentNodeId` is the root node of a tool sub-node run), `node.record` (an artifact or check a node reported with `ctx.artifact` / `ctx.check`; a remote node's come with its response) and `execution.finished`, streamed over SSE to light up the canvas. A tool sub-node's `node.started` carries the arguments it was called with (`input`). The host turns them into each run's journal ([run-trace.md](../run-trace.md)).
- **Waiting executions**: a node can suspend the run (`ctx.putExecutionToWait`, in-process nodes). The engine returns status `waiting` with a JSON resume state; the host saves it under the same execution id and resumes it on the workflow version it started with, when its time comes (timers are re-armed at boot), on a call to `/api/waiting/<id>`, on a form submission, or when the sub-execution it waits for finishes. Waiting runs show as **Waiting** in the executions lists; `DELETE /api/executions/:id` cancels one. The result's `wait.since` is when the node asked to wait, not when it started: a Run a Team node works for a while before a member's tool needs an approval (before, the Run Trace dated that wait from the node's start).
- **Loops**: an edge back to an earlier node runs it again (Loop Over Items keeps per-node state for the execution, also across waits); `$('Node')` sees that node's latest run. Partial runs and "run up to here" work inside loops.
- **Workflow settings**: `timeoutSeconds` fails a run with "Workflow timed out after N s" (time spent waiting doesn't count); `saveSuccessfulExecutions`, `saveFailedExecutions` and `saveManualExecutions` (default on) drop runs from the history, though their events still stream; `errorWorkflowId` runs that workflow's Error Trigger when a non-manual run fails (unless an automatic retry follows); `timezone` is the Schedule trigger's zone; `callerPolicy` / `callerIds` decide which workflows may run this one; `concurrencyLimit`, `singleton`, `concurrencyOverflow`, `concurrencyQueueSize`, `retryMaxAttempts` and `retryBaseDelaySeconds` are the durable runtime's (below).

## Durable runtime

- **Store**: workflows, executions, poll state, versions, folders, settings, variables, waits, checkpoints, idempotency keys, retries and Data Tables live in SQLite at `<data dir>/landflow.db` (WAL mode, versioned migrations recorded in `schema_version`, `lib/server/db/`). `LANDFLOW_DB=postgres` with `DATABASE_URL` uses Postgres instead: the host loads the whole database into an in-memory copy at boot, serves reads from it and writes to Postgres in order through a queue that is spooled to `<data dir>/postgres-queue.jsonl` first (replayed at the next boot), so the store API stays synchronous; a batch Postgres keeps rejecting blocks writes instead of being dropped ([Postgres write queue](postgres-write-queue.md)). An advisory lock allows one host per database in regular mode; queue mode shares it between mains and workers (below). Credentials, the encryption key, insights and the agent files stay files. The first boot on a data directory with the JSON files of older versions imports them once and renames each to `<name>.imported-<date>` (nothing is deleted; the import is idempotent).
- **Saved as it runs**: an execution is saved when it starts, with the workflow version it runs (`versionId`; an unsaved editor draft keeps its graph instead), then every node run and a checkpoint after each main-flow node under a stable step id (`<nodeId>#<runIndex>`). At boot, executions left `running` by a crash or restart continue from their last checkpoint on the same version (tagged **Resumed after restart**; nodes before the checkpoint don't run again). Those that can't (their version is gone, a debug session, no checkpoint yet) are saved as failed with the reason.
- **Idempotency**: an `Idempotency-Key` header on a webhook or form call (or `idempotencyKey` on `POST /api/workflows/:id/run`) starts at most one run per workflow and key within `LANDFLOW_IDEMPOTENCY_TTL_HOURS` (default 24); a repeat gets the first run's answer with `Idempotent-Replayed: true`. Every Execute request also carries a per-step `idempotencyKey` (`<executionId>:<nodeId>:<runIndex>`, the same for retries of that step and after a restart) that plugins can pass to the APIs they call ([docs/protocol.md](../protocol.md)).
- **Concurrency**: `concurrencyLimit` caps a workflow's production runs (webhook, form, schedule, poll, error-workflow and agent-tool runs) at once, and `singleton` allows one, waiting runs included. A trigger run with no free slot waits in the workflow's FIFO queue (status **Queued**, at most `concurrencyQueueSize`, default 100; it survives a restart) or, with `concurrencyOverflow: 'skip'`, is skipped (webhooks and forms answer 429). Manual and chat runs from the editor, debug runs, sub-executions, re-runs and retries are never held back.
- **Retries**: with `retryMaxAttempts` of 2 or more, a failed production run is retried automatically after `retryBaseDelaySeconds` (default 30), doubling per attempt up to 6 hours; retries survive a restart. Each retry is a new execution linked to the failed one (`retryOf`, `retryAttempt`, and `retriedBy` on the failed run) that continues from the failed node, reusing what ran before it. **Retry** on a failed execution (`POST /api/executions/:id/retry`) does the same by hand, or from the start.
- **Stop all**: the Executions page's **Stop all** (`POST /api/executions/stop-all`) aborts running executions, cancels waiting and queued ones and drops pending automatic retries. It is instance-wide, so it is for owners and admins only (members get 403 and don't see the button); an API key needs the `executions:write` scope, as for the CLI's `landflow executions stop --all`.
- **Failure alerts** (Settings → Alerts): hear about failed runs without an error workflow. **Channels** are where alerts go: email (through the host's `LANDFLOW_SMTP_*` settings, one message per address), a Slack incoming webhook, a **Microsoft Teams** webhook (an Adaptive Card, for a Teams Workflows webhook or an incoming webhook connector) or **Discord** webhook (an embed), a webhook (a JSON POST signed with `X-Landflow-Signature: sha256=<HMAC-SHA256 of "<X-Landflow-Timestamp>.<body>">` when it has a secret) or a Telegram chat through a saved Telegram API credential; each has **Test**, and shows its last delivery. Slack, Teams and Discord URLs and webhook secrets are encrypted with the vault key and never returned. **Rules** pick workflows (all, selected, or by tag), events (**failed** after the last automatic retry, **timed out**, **retries exhausted**, **waiting too long** past N minutes; a Wait timer that isn't due doesn't count) and channels; editor runs only with **Include editor runs**, sub-executions are left to their parent. A rule's throttle allows one alert per workflow per window (default 10 min); what it holds back goes out as one digest ("Orders sync: 4 more failures in the last 10 min") when the window ends. Every alert names the workflow, the failing node and the error, and links to the execution (`LANDFLOW_PUBLIC_URL`). Rules have a **kind**: *Runs* (the events above), *Failure rate* (per workflow: at least N production runs started in a window and more than X% of them failed, defaults 5 runs, 50%, 15 min; one alert per workflow per window, and a workflow still failing when the window ends alerts again), *Plugin* (a plugin whose endpoints have all been offline for longer than a grace period, default 120 s, so a restart never alerts; optionally a message when it is back; chosen plugins or all, in-process plugins are never watched), *AI cost* (a cap at a threshold, see AI usage and cost in [Observability](observability.md)) and *Evaluation score* (see Evaluations). The time-based kinds are evaluated by the alerts ticker on the leader, from the database and the plugin registry, so in queue mode one process checks them whichever process ran the workflows; what a rule remembers (`alert_state`, migration 1820) survives a new leader. A workflow's **Settings → Notify on failure** makes such a rule for that workflow in one click (members may use it; channels are set up by admins). API: `/api/settings/alerts` (channels, rules, `channels/:id/test`) and `/api/workflows/:id/alert`.

## Queue mode, workers and high availability

Regular mode (the default) runs every execution in the process that started it, one host per database. Queue mode spreads production runs over worker processes and runs several mains with failover:

```bash
# Every main and worker: the same Postgres, Valkey, encryption key, file-link secret, binary store and data directory
export LANDFLOW_EXECUTIONS_MODE=queue LANDFLOW_DB=postgres DATABASE_URL=postgres://… LANDFLOW_VALKEY_URL=redis://127.0.0.1:56379
export LANDFLOW_ENCRYPTION_KEY=… LANDFLOW_BINARY_SECRET=… LANDFLOW_BINARY_STORE=s3 LANDFLOW_S3_ENDPOINT=…
LANDFLOW_INSTANCE_ID=main-1 pnpm dev        # a main: UI, API, webhooks (start more on other ports)
LANDFLOW_INSTANCE_ID=worker-1 pnpm worker   # a worker: runs executions; /healthz and /metrics on :5690
```

- **Mains and workers**: mains serve the UI, API, webhooks, forms and hosted chat. They create the executions and put production runs (webhooks, forms, chat, schedules, polls, MCP, app webhooks, agent tools, error workflows, retries, resumed waiting runs) on a Valkey stream; workers (`pnpm worker`, in Docker `node worker.mjs`) take up to `LANDFLOW_WORKER_CONCURRENCY` at once (default 10) and run them through the same runner. Editor runs stay in the main that started them unless `LANDFLOW_OFFLOAD_MANUAL_EXECUTIONS=true`; debug sessions, and sub-executions their parent waits for, stay with their parent. Callers see no difference: the worker sends the main its live events, a Respond to Webhook reply and the result over Valkey pub/sub, and the editor's live view and the Executions list show runs on any worker.
- **Why Valkey Streams** (not lists or a broker): a consumer group hands each job to one worker and keeps it pending until acknowledged, and XAUTOCLAIM lets another worker take the jobs of one that stopped: at-least-once delivery with crash recovery on the Valkey the stack already has (`lib/server/cluster/coordinator.ts`).
- **One process per run**: a run holds a lease (`lease:<execution>`, renewed by every heartbeat). A worker that dies stops renewing; after `LANDFLOW_STALLED_SECONDS` (default 30) another worker claims its jobs and continues the runs from their last checkpoint (the node that was running runs again), and a run that loses its worker 5 times fails. On SIGTERM a worker takes no new jobs, gives runs `LANDFLOW_WORKER_SHUTDOWN_SECONDS` (default 30) to finish and puts the rest back in the queue. Mains drain the same way now (`lib/server/lifecycle.ts`, [deployment.md](../deployment.md#stopping-the-host)): the leader lease is released, so another main takes over at once instead of after the lease runs out.
- **Across processes**: Stop, Stop all, idempotency keys, concurrency limits and singletons (slots and the FIFO queue in Valkey), automatic retries, node rate limits and trigger debounce / batching (under a Valkey lock) behave as in regular mode. So does an Execute Workflow parent waiting for several children (once per item) whose children resume on other workers: each child puts its result into the parent's saved wait under a Valkey lock, and the last one resumes the parent, once. Test URLs too: the editor's listener is registered in Valkey, a test call that reaches another main claims it there (one call per listen; an MCP Server Trigger's test URL takes many, each pushing the deadline on in Valkey) and runs in that main, and the bus relay streams the run to the editor's main, so they need no sticky sessions. Listening again for the same trigger on another main (another tab, a reload) ends the earlier stream with `stopped` over the control channel.
- **Leader election**: the mains elect a leader through a Valkey key with a time to live and a fencing token (`LANDFLOW_LEADER_TTL_SECONDS`, default 10). Only the leader runs schedules (picking up where the last leader left them, catching up on the seconds a failover took), poll triggers, IMAP IDLE, app webhook registration, wait, retry and held-event timers, alerts, agent triggers and retention, and every 15 s it hands runs whose process died to a worker. If it crashes, another main leads within about 13 s (TTL + TTL/3); a main that stops resigns and the next leads within about 3 s. A leader whose lease may have run out steps down by itself, so two mains never lead at once.
- **Shared state**: Postgres (each process keeps its in-memory copy and follows the others' writes through `LISTEN/NOTIFY`), the plugin registry (registrations kept in Postgres; workers connect to the plugins themselves), files in S3 or MinIO (the filesystem store logs a warning: hosts can't read each other's disks), and the data directory for the rest (a per-process insights rollup, agent files). Queue mode refuses SQLite unless every process runs on one host with one file (`LANDFLOW_QUEUE_ALLOW_SQLITE=true`).
- **Credentials and settings files in the database**: in queue mode (or anywhere with `LANDFLOW_CONFIG_STORE=database`) credentials live in the `credentials` table and `mcp.json`, `marketplaces.json`, `skill-library.json` and `agent-channels.json` in `config_files` (migration 1300), and agent definitions, sessions (with their summaries and channel conversation keys) and memory in the `agent_definitions`, `agent_sessions` and `agent_memory` tables (migration 1881; the first start imports the `agents/`, `agent-sessions/` and `agent-memory/` directories once, sessions that were running as idle), so processes need no shared data directory for them and two mains changing different credentials no longer overwrite each other. The first start imports each file once (recorded in `meta`; rows written since win) and leaves the file where it is; the encryption key stays `LANDFLOW_ENCRYPTION_KEY` or `<data dir>/encryption.key`. `LANDFLOW_CONFIG_STORE=files` keeps the files (every process then shares the data directory, last writer wins); regular mode keeps them unless told otherwise (`lib/server/config-store.ts`).
- **Plugin restarts**: a plugin restarted with the same version announces a new `instanceId`; the main pulls its manifest again and writes the instance and a manifest hash to `plugin_registrations`, and every worker that sees the row change pulls it again too, so new nodes, icons or descriptors reach the workers without a version bump (`lib/server/cluster/plugins.ts`).
- **Marketplace node plugins** run in every main and worker, each its own copy on 127.0.0.1, registered in that process's registry only (never in `plugin_registrations`) and started without announcing. The install records a revision and a hash of the downloaded files (a GitHub branch or tag pinned to its commit); a process that can't see the installed directory downloads the same source into `<data dir>/marketplace/instances/<instance id>/`, checks the hash and prepares it. Installs, updates and removals reach the others over the control channel and through the `config_files` row, and each process checks every minute. A source whose files changed since the install is refused there (reinstall it). Several processes on one host can get their own port ranges with `LANDFLOW_MARKETPLACE_PORTS` (default `7250-7299`).
- **Valkey Sentinel**: `LANDFLOW_VALKEY_SENTINELS=host:port,…` (with `LANDFLOW_VALKEY_MASTER_NAME`, default `mymaster`; `LANDFLOW_VALKEY_SENTINEL_PASSWORD` / `_USERNAME` when the sentinels require AUTH, `LANDFLOW_VALKEY_SENTINEL_TLS=true` when they speak TLS) makes every Valkey connection (commands, pub/sub, the workers' blocking reads, rate limits) ask the sentinels for the primary, check it with `ROLE`, and reconnect on `+switch-master` or a `READONLY` reply; `LANDFLOW_VALKEY_URL` then only gives the primary's credentials, database and TLS. Runs in flight carry on through a failover (calls that fail meanwhile are retried by their loops; a lease missed for a few seconds is renewed or the run taken over). Replication is asynchronous, so a job enqueued in the last moment before the primary crashed can be lost. [deploy/compose.sentinel.yml](../../deploy/compose.sentinel.yml) has a primary, a replica and three sentinels; `LANDFLOW_INTEGRATION=sentinel` kills the primary under a running cluster (`test/valkey-sentinel.integration.test.ts`).
- **Valkey Cluster**: `LANDFLOW_VALKEY_CLUSTER=host:port,…` (seed nodes; one or more) works because every key, the three priority streams included, carries one hash tag (`{<prefix>}`), so the multi-key Lua scripts (the leader and its epoch counter, a workflow's slots and its FIFO, instances, leases) run on one slot. That is the limit: the queue sits on one node (primary plus its replicas), so Cluster gives failover and managed hosting, not scale-out; one Valkey handles far more queue traffic than the workers can run. The client asks `CLUSTER SLOTS` for the slot's primary, follows `MOVED` and `ASK` redirects and retries through a failover (`CLUSTERDOWN`, `TRYAGAIN`, `READONLY`). Behind NAT or Docker port mappings, `LANDFLOW_VALKEY_CLUSTER_NAT=announced:port=reachable:port,…` maps the addresses the nodes announce. Sentinel and Cluster together are a configuration error. `deploy/compose.infra.yml` has a six-node `valkey-cluster` profile for trying it ([deployment.md](../deployment.md#queue-mode-two-mains-two-workers)); a test stops the slot's owner under a main and a worker and both carry on after the failover.
- **No sticky sessions**: a debugger command (Continue, Step, Stop, breakpoints) that reaches a main not holding that debug session is sent over the control channel to the one that does, which answers into the asker's inbox (404 after 3 s when no main holds it); each main follows the others' pause events, so a run paused elsewhere shows where (`lib/server/cluster/debug.ts`). A pending SSO sign-in (OIDC state, PKCE verifier, nonce) is kept in Valkey, sealed with the encryption key, for 10 minutes and taken once, so the provider may send the browser back to any main.
- **Watching it**: **Settings → Workers** (read-only) shows the leader and its fencing token, the queue and every main and worker with its runs and last heartbeat. Metrics: `landflow.queue.depth`, `landflow.queue.active`, `landflow.queue.jobs` (by outcome: processed, failed, claimed, recovered, requeued), `landflow.cluster.instance`, `landflow.cluster.workers`, `landflow.worker.active_jobs` and `landflow.cluster.leader.elections`.
- **Docker**: [deploy/compose.queue.yml](../../deploy/compose.queue.yml) runs two mains behind a small load balancer and two workers on the infra stack, with an end-to-end check ([deployment.md](../deployment.md#queue-mode-two-mains-two-workers)).
- **Sign-in rate limits are shared**: failed sign-ins, password resets, setup and invitation attempts are counted in Valkey (`signin:<name>:<key>`), so a limit holds however the load balancer spreads the attempts; if Valkey errors the main counts locally for that request. **Evaluation runs** heartbeat (`evaluation_runs.heartbeat_at`, migration 1880); one that stops heartbeating for 30 s is settled as interrupted, so opening Evaluations on one main no longer fails a run on another.
- **Kubernetes**: `deploy/k8s/overlays/orbstack-queue` runs two mains and two workers with Postgres, Valkey and MinIO, with PodDisruptionBudgets; `deploy/k8s/examples/keda` autoscales workers on the stream's backlog ([deployment.md](../deployment.md#queue-mode-on-kubernetes)).
- **Limits**: a leader that crashes may fire a schedule second twice (its state is saved every 2 s). With `LANDFLOW_CONFIG_STORE=files`, credentials, settings files and agent files in the shared data directory are last-writer-wins between processes.

## Expressions run in a sealed realm

`{{ ... }}` expressions are evaluated synchronously (the executor and nine host modules call the resolver synchronously, and
V8 semantics including `Intl` such as `toLocaleString` stay as they were) in a **sealed realm**
([`packages/engine/src/sandbox/`](../../packages/engine/src/sandbox)): a fresh `node:vm` context with code generation from
strings and WebAssembly off, a null-prototype global and a 250 ms timeout per evaluation.

- **What is reachable**: only what the bootstrap defines inside the realm (`$json`, `$input`, `$('Node')`, `$node`,
  `$itemIndex`, `$now`, `$today`, `$workflow`, `$execution`, `$parameter`, `$vars`, `$composite`, `$secrets`, `$fromAI`) and
  the language's own builtins. V8 gives every context a `console` of its own: `console.log` from an expression prints
  nothing on the host (checked on Node 22) and stays so an expression that calls it does not fail. Data arrives lazily through one host function that takes and returns JSON text (the current
  item, all input items, one node's output, tool arguments, a secret the host fetched); the realm caches what it parsed
  for the life of the resolver, so an item is copied once however many parameters read it. Nothing the expression changes
  (`$json.x = 1`, `Object.prototype.polluted = 1`) reaches the host's data or prototypes. Items cross as JSON, so a host
  `Date` an in-process node left in an item reads as an ISO string, and a BigInt or circular value fails the expression.
- **What is not**: `process`, `require`, `globalThis.process`, the host's `Function` (`$json.constructor.constructor(...)` finds
  the realm's own, which cannot compile), `eval`, `new Function`, `WebAssembly`, `FinalizationRegistry`, `WeakRef` (their callbacks would run on the host's loop outside the timeout), `import()`, and any Promise: `async`,
  `await` and `import(` are refused in an expression's source, the realm's promises are inert, and the builtins that
  return one are removed (`Promise`, `Array.fromAsync`, `Atomics.waitAsync`, and on Node 24+ `AsyncDisposableStack`),
  because a rejected promise in any context is an unhandled rejection that ends the host process. A test walks the
  realm's globals for any other such name, so a Node upgrade that adds one fails the suite. `Error.prepareStackTrace` and
  `stackTraceLimit` are locked so a stack trace cannot expose host frames.
- **Results** come back as tagged JSON the host parses, so what an expression returns is made of host-realm objects and
  arrays (`Array.isArray`, `instanceof Object`) and no getter or Proxy it built can run outside the timeout. Dates come back as
  Dates, `undefined` (also inside arrays and objects), `NaN`, `Infinity` and `-0` as themselves, a BigInt as a string and a
  function as `undefined`. An error thrown by an expression is read inside the realm; one that escapes it (the timeout, a
  stack overflow) is reported without reading the thrown value.
- **Remaining risks** (realm): a V8 or `vm` bug (the realm is a context in the host process, not a process boundary), and
  memory exhaustion inside the 250 ms window. For an instance that lets untrusted people write expressions, choose the
  isolate backend below.

### The isolate backend (optional)

`LANDFLOW_EXPRESSION_SANDBOX=isolate` runs the same bootstrap and bridge in an [isolated-vm](https://github.com/laverdet/isolated-vm)
isolate ([`sandbox/isolate.ts`](../../packages/engine/src/sandbox/isolate.ts)) instead of a `node:vm` context. The default
stays `realm`.

- **What changes**: one isolate per process with its own V8 heap capped at `LANDFLOW_EXPRESSION_MEMORY_MB` (default 64), and a
  context per resolver. A V8 bug inside an expression now reaches an isolate, not the host's heap, and an expression that
  exhausts memory fails with "The expression used more than N MB of memory": the isolate is disposed and rebuilt
  (the resolvers that shared it get a fresh context on their next evaluation), and the process keeps running for every
  memory bomb the tests try (below). Semantics (V8, `Intl`), the 250 ms timeout, the tagged-JSON results and the
  `async`/`import(` refusal are the realm's, and the whole realm test suite runs against it (its test checks that it does).
  Evaluating through the isolate is faster than the realm for a resolver that evaluates many times, and about 1.3 times
  slower for a fresh resolver per evaluation, which is what the executor makes per node execution
  (`test/expression-isolate.test.ts` measures both).
- **Contexts are released by the engine, not the garbage collector**: the host cannot see the isolate's heap, so the 32
  most recently used contexts stay and older ones are released at once (their resolver builds a new one on its next
  evaluation); the bootstrap and each expression are compiled once per isolate (a few hundred expressions are kept, fewer
  with a smaller cap). An isolate disposed through no fault of the expression being evaluated is rebuilt and the
  expression tried once more. A churn test runs thousands of short-lived resolvers with no failure.
- **Guards on top, and what they cannot promise**: V8 aborts the whole process when a single allocation is larger than the
  heap limit, before isolated-vm can end the isolate (about 150 single-step bombs were tried; they come only from builtins
  that allocate from a length the caller gives). In an isolate, `Array.from` on an array-like longer than 32,768 times the cap in MB
  elements, `Array.prototype.fill` and `join` on an array longer than that, and `String.prototype.repeat`, `padStart` and
  `padEnd` past 262,144 times the cap in characters throw a `RangeError` (as an oversized one does anyway). Everything that
  grows in steps reaches the cap and ends the isolate. This is a list of the builtins found to allocate that way, and
  **a list cannot be shown to be complete**: isolated-vm gives no hook to turn an oversized allocation into an error, so
  an allocation path that was not found still aborts the process. The test runs each bomb in a process of its own, so an
  abort fails the test. The guards also refuse sizes the realm allows (`new Array(3e6).fill(0)` fails at 64 MB).
- **When to choose it**: people you do not trust write workflows or expressions (shared instances, builders you do not
  review), or a memory bomb in an expression must not take a worker down. Keep `realm` otherwise.
- **Requirements**: `isolated-vm` is an optional dependency of `@landflow/engine` (a native addon: an install without a
  prebuilt binary or a compiler skips it and the realm keeps working) and needs `NODE_OPTIONS=--no-node-snapshot` on
  Node 20+ in every process that evaluates expressions: `next start`, `pnpm worker`, the Docker image (set there). Where it
  cannot load, the production profile refuses to start and development logs a warning and uses the realm
  ([deployment.md](../deployment.md#expression-sandbox)). The cap is for the process, not per expression.

## Triggers and flow nodes

- **Webhook** (`/api/webhook/<path>`): **Respond** immediately (202 with the execution id), when the last node finishes (its output as JSON), or using a **Respond to Webhook** node (first item, all items, JSON, text, no data or a redirect, with status code and headers; sent when that node runs while the run goes on). A run that starts waiting before it answers returns `{ status: "waiting", executionId }`. An `Idempotency-Key` header makes retried calls safe (see [Durable runtime](#durable-runtime)); a workflow at its concurrency limit queues the call's run (`status: "queued"`) or answers 429.
- **On Form Submission** (`core.formTrigger`) and **Form** (`core.form`): server-rendered forms (text, textarea, number, email, password, date, dropdown, checkboxes, radio buttons; required fields, placeholders, button label) at `/form/<path>` while the workflow is active. A submission becomes `{ <field>: value, submittedAt, formMode }`. The trigger answers on submit or when the workflow finishes; each Form page makes the run wait at `/form/waiting/<executionId>`, and a Form ending shows a message or redirects.
- **Test URLs** (`/api/webhook-test/<path>`, `/form-test/<path>`, `/mcp-test/<path>`): they answer only while an editor listens for that trigger (`POST /api/workflows/:id/listen`, an SSE stream), and 404 with a hint otherwise. A test webhook takes one call (any method the trigger is set to), then stops listening; a test form shows the form until it is submitted and stays until the run finishes, multi-page forms included; an MCP Server Trigger's test URL serves every MCP request (`tools/list` unrecorded, each `tools/call` a manual run `<listen id>-<suffix>` with its own `result` on the stream) until Stop. Listeners time out after 120 s (MCP: 120 s after the last request). A test call is traced like the production call, with `landflow.trigger.test=true`; the listening is a `trigger.listen` span. The call runs the workflow the editor sent when it started listening, as a `manual` run (out of production Insights, never queued, debounced or deduplicated) that the editor streams live, with the trigger's authentication and IP allow-list, its Respond setting (immediately, last node, Respond to Webhook, streaming) and file uploads as in production. One workflow per test URL at a time (409 for another). In queue mode the listener is registered in Valkey, so the call may reach any main: it is claimed there and runs in that main, and the bus relay streams it to the editor (`apps/web/src/lib/server/test-webhooks.ts`).
- **Webhook and form authentication** (n8n's **Authentication** on the Webhook and Form triggers): **Basic Auth** (a Basic Auth credential), **Header Auth** (a header name and value) or **JWT Auth** (an HS256/384/512 secret, a PEM public key or a JWKS URL, with optional issuer and audience checks; the verified claims reach the run as `jwtPayload`), plus **IP(s) Allowlist** (addresses and CIDR ranges, IPv4 and IPv6). A caller that fails gets 401 (with `WWW-Authenticate`) or 403 before the body is read and starts no run; secrets are compared in constant time and the headers that carried them are left out of the item. The credential must be one the workflow's project may use (owned by it or shared with it), like any credential a run uses: otherwise every call gets 403 without naming the credential (the host logs which one), and saving the workflow warns. The same holds for the MCP Server Trigger's Bearer and Header Auth. The caller's address is the first `X-Forwarded-For` entry, else `X-Real-IP`, so put a proxy that overwrites those headers in front of a public install.
- **App webhook triggers** (`triggerSource: "appWebhook"`, e.g. the productivity plugin's **GitHub Webhook Trigger** and **Stripe Trigger**, the messaging plugin's **Slack Trigger**): publishing asks the plugin to register a hook at the service for `/api/webhook/app/<workflowId>/<nodeId>` (`checkExists`, then `create`), unpublishing or deleting the workflow removes it (`delete`), and each delivery goes to the plugin (`ReceiveWebhook`) to verify its signature and turn it into items, a reply and an idempotency key. A service without a registration API (Slack's Events API) is set up by hand: publishing only verifies the credential, and the node's Request URL from the Publish menu is pasted into the Slack app. What the plugin keeps (hook id, secret) is the node's static data, stored per workflow and node. Registrations that fail are retried every minute (`LANDFLOW_APP_WEBHOOK_RETRY_MS`) and shown in the publish menu. See [docs/protocol.md §12](../protocol.md#12-app-webhook-triggers).
- **Email Trigger (IMAP)** (`core.emailReadImap`, an **IMAP** credential): polls a mailbox every **Poll Interval** seconds or, with **Listen: IDLE**, keeps a connection open and runs as soon as mail arrives (the poll stays as the fallback). Each new message (unread only, by default) becomes an item with from, to, cc, subject, date, text, HTML, message id and headers; attachments become binary files of the run (**Download Attachments**). **Search Criteria** (an option) narrows what is emitted with IMAP SEARCH text, ANDed with **Only Unread** (on by default; switch it off to match read mail too): `FROM "billing" SINCE 1-Oct-2026 NOT SUBJECT "spam"`, `OR FROM a FROM b`, `LARGER 10000`, `HEADER X-Foo bar`, `KEYWORD x`, `UID 100:*`, with parentheses and any nesting of `NOT`/`OR` (FROM, TO, CC, BCC, SUBJECT, BODY, TEXT, HEADER, KEYWORD, the SINCE/BEFORE/ON and SENT* dates as `1-Oct-2026` or `2026-10-01`, LARGER/SMALLER, the flag keys). Landflow parses it itself and fails the run with a clear message on an unknown key, unbalanced parentheses or quotes, a bad date or number, or a line break; the same filter applies to polls, IDLE and manual runs, and messages that don't match are skipped for good (the per-folder UID baseline moves past them). **Output Raw Email (.eml)** adds the whole RFC 822 message as a binary `message-<uid>.eml` file (property `eml`, renamable; held to the binary store's limits like attachments), and **Include Raw Source in JSON** adds it as the string field `raw` (messages over 5 MB leave it out and say so in `rawSkipped`). Afterwards it marks messages read, moves them to a folder or leaves them. The first poll records a baseline, so old mail doesn't start runs; **Execute** in the editor shows the latest five messages without changing them.
- **Schedule**: n8n's Trigger Rules (every N seconds, minutes, hours at a minute, days, weeks on weekdays or months on a day, at a time of day, or a five- or six-field cron), in the workflow's time zone, else the server's. Older "every N seconds / minutes / hours" schedules keep counting from activation.
- **Error Trigger**: the start of an error workflow; it receives n8n's `{ execution: { id, url, error, lastNodeExecuted, mode, retryOf? }, workflow: { id, name } }`.
- **When Called by a Workflow or Agent** (`core.workflowTrigger`): defined arguments or "accept all data"; called by an agent tool or by **Execute Workflow**, which runs the workflow once or once per item, maps arguments or passes items through, waits for it (or not) and returns its last node's output. The child is its own execution linked to the parent (`parentExecutionId`), at most 10 levels deep; if it starts waiting, the parent waits too and resumes with its output. Once per item, the children run four at a time (**Options → Sub-Workflows at Once**, 1–32; the first failure stops the others), and the parent waits for every child that waits and resumes when the last one finishes, with the outputs in item order (`pairedItem` kept). Children's outputs are kept in the parent's wait up to 256 KB in all; past that the wait names the child execution and its output is read from it on resume (deleted by then: the parent fails, naming the child). A child that writes files writes them into its parent's binary scope, and that link is kept in the database (`binary_scope_links`, migration 1200) so it holds after a restart or on another worker. What it waits for and the results so far are saved with its wait, so this survives a restart; a failed or canceled child fails the parent (the children still waiting are canceled) or, with **On Error → Continue**, becomes `{ error }` for its item. Stopping a waiting parent cancels the children it waits for. The execution view shows "Waiting on N of M sub-workflows" with a link to each child, and a child links back to its parent ("Sub-execution of …").
- **Signed resume URLs**: where `LANDFLOW_RESUME_SIGNATURES` is `required` (the production default), `$execution.resumeUrl` and `resumeFormUrl` end in `?sig=<32 characters>` (an HMAC of the execution id under a key derived from the vault key) and the wait is saved with `signed: true`; calling `/api/waiting/<id>` or `/form/waiting/<id>` without a valid `sig` answers 403 "This resume URL is not valid" (signed-in people can open form pages from the editor and Run Trace without it, on a workflow they may read, and submit them on one they may run). A wait saved before signing existed resumes without one, and the host logs that. With `optional` (the development default) URLs stay unsigned and unsigned calls work, but a wrong `sig` is refused. Form pages keep `?sig=` in their form action; the signature is not copied into the run's data.
- **Wait**: a time interval, a date and time, a webhook call (`$execution.resumeUrl`) or a form (`$execution.resumeFormUrl`), with an optional time limit. Waits up to ~65 s stay in memory; longer ones suspend the run.
- **Ask a Person** (`core.confirmDraft`, Flow): sends a draft to a person and waits for the answer (a daily summary, a message to a customer). Parameters: **Draft** (an expression, read from the first input item), **Title**, **Ask In** (Chat / Execution View, Slack with a Slack credential to a channel or member, or Email), **Who May Answer** (emails of signed-in people and Slack member ids; empty: anyone who can see the request), **Allow Editing**, and **Timeout (Minutes)** with **If Nobody Answers** (Reject, Approve or Fail the Run). It asks once per run, not once per item, and outputs one item `{ approved, edited, text, originalText, comment, by, at, channel }` on **Approved** or on **Rejected** (a timeout that rejects or approves carries `by: "timeout"`). `text` is what the person approved, edited or not; `by` is the signed-in user's email, `slack:<member>` or `email:<address>`; `channel` is where the answer came from. It waits the way an AI Agent waits for a tool approval ([agents.md](../agents.md#tool-approvals)): the execution is saved as `waiting`, so it survives a restart, and the answer arrives through `POST /api/executions/:id/approvals` (call id `confirm`, body `{ approved, text?, comment? }`). Where it shows: the Run Trace's Needs you and the runs list read "Waiting for <person>: <title>" with the draft, an editable box when editing is allowed, a comment and Approve / Reject; the editor's chat panel shows the draft with Approve / Reject. In Slack the message has **Approve**, **Edit** (a modal with the draft and a comment; needs the Slack app's Interactivity URL, as the tool approvals do; drafts over 3,000 characters can't be edited in Slack) and **Reject**, and after an answer, from anywhere, it is replaced by the draft as approved and who answered (a timeout says how it settled). By email the person gets signed single-use Approve and Reject links (no editing; edit in the execution view).
- **Loop Over Items** (Split in Batches v3): batches on its "loop" output, everything that came back on "done".

## Debounce, batching and rate limits

- **Debounce** (a trigger node's Settings, as Inngest's `debounce`): events with the same key (an expression over the event, e.g. `{{ $json.body.userId }}`; empty = one key) within the window collapse into one run, started once the key has been quiet for **Window** seconds, or at the latest **Max Wait** seconds after its first event. The run gets the last event, or all of them (**Mode: All**).
- **Batch** (Inngest's `batchEvents`): events are collected until **Size** of them arrived or **Timeout** seconds after the first, then one run gets them all as items.
- Production starts only (webhooks, schedules, polls, app webhooks, public chats); manual and chat-panel runs are never held. A held webhook call answers **202** `{ status: 'debounced' | 'batched', count, runsAt }`; held events live in SQLite (`trigger_buffers`) and their timers are re-armed at boot. The execution records how many events it took (`buffered`).
- **Rate limit** (every node's Settings, next to Retry on Fail): at most **Limit** calls per **Interval** seconds, a sliding window shared by every run in the process; calls over it wait their turn in a queue (logged on the node run) instead of failing.
- **Rate limit per credential** (the credential dialog's **Rate limit**: calls per N seconds): every use of the credential by a node run attempt or an AI sub-node (model, tool, memory, embedding) goes through the same sliding-window limiter under the key `credential:<id>`, on top of the node's own limit, and waits its turn (logged as `Rate limit of credential "<name>" …`). Workflows, nodes and agents sharing one API key share its budget. In queue mode the limit holds across workers (Valkey). `rateLimit: { limit, intervalSeconds }` (or `null` to clear it) is accepted by `POST /api/credentials` and `PATCH /api/credentials/:id`.
- **Run priority** (workflow Settings, **Priority**: `high`, `normal`, `low`): decides who goes first when production runs have to wait. Each workflow keeps its own concurrency slots, so priority matters across workflows in two places. With `LANDFLOW_MAX_RUNS=N` (default `0`, no cap) a regular-mode process runs at most N production runs (webhook, trigger, poll; manual and tool runs are never held) and queues the rest; the queue is drained high first, with `normal` runs aging by 15 s and `low` runs by 60 s so nothing starves. In queue mode the jobs go to three Valkey streams (`jobs:high`, `jobs`, `jobs:low`) and a worker takes high before normal before low; after eight jobs in a row from the higher streams it takes one `low` job first, so low runs still make progress. Within a priority the order is first in, first out.

## Code node

JavaScript or Python, run once for all items or once for each item, as in n8n. Code can run in two places:

- **Sandbox**: the code runner ([services/code-runner](../../services/code-runner)), a fresh locked-down process per run, normally in its own container with no network. JavaScript gets n8n's globals: `$input.all()`, `.first()`, `.last()`, `.item`, `$json`, `$('Node').all()/.first()/.item`, `$vars`, `$execution`, `$workflow`, `$now`/`$today` and Luxon's `DateTime`, plus `await`. Python (CPython, standard library only) gets `_input`, `_json`, `_('Node')`, `_vars`, `_execution`, `_now` and so on. `console.log`/`print` go to the node's logs, and errors carry the line (`TypeError: … [line 3, for item 0]`). Python always runs here. The node helpers behave the same in both places (the expression engine's rules): `$('Node').item` follows the current item by position (the first item when the other node has fewer), `.itemMatching(i)` is its item `i` (an error when there is none), `.first()`, `.last()`, `.all()`, `.isExecuted` (false for a node that has not run; reading anything else from it fails with "has not run yet"), `.json` and `.binary`, and the legacy `$node['Name'].json` / `$node.Name.items`; in Python `_('Node').item_matching(i)` and `.is_executed`.
- **In-process**: JavaScript in a `node:vm` context of the host with the same globals as the sandbox (`items`, `$json`, `$input`, `$('Node')`, `$node`, `$vars`, `$execution`, `$workflow`, `$now`; no Luxon), as before, and `await` works. It isn't isolated (its context holds the host's Buffers and async helpers, so it is for trusted workflows; `eval` and `new Function` from strings are off as defence in depth). It is on by default in the development profile and off in production unless `LANDFLOW_CODE_IN_PROCESS=true`.

**Files.** `$input.item.binary` (Python `_input.item.binary`) is the item's file metadata (`{ fileName, mimeType, fileSize, fileExtension, id }`, no bytes). `await this.helpers.getBinaryDataBuffer(itemIndex, 'data')` reads a file as a `Buffer` (Python `_helpers.get_binary_data_buffer(item_index, 'data')`, `bytes`), and `await this.helpers.prepareBinaryData(buffer, 'report.csv', 'text/csv')` makes one to put on an output item (`{ json, binary: { data } }`; Python `_helpers.prepare_binary_data(data, file_name, mime_type)`); `assertBinaryData` checks that an item has a file. The file lands in the host's binary store (filesystem or S3) like any node's output and the type is taken from the name when you leave it out. The sandbox has no network, so the host sends the bytes of the input files with the request (only when the code mentions the read helper) and the snippet returns created files as base64 for the host to store. Everything the code reads (all files together) and everything it creates is capped by `LANDFLOW_CODE_BINARY_MAX_BYTES` (6 MiB; the runner has its own `CODE_RUNNER_MAX_BINARY_BYTES`, and the request and output caps apply too); a file over the cap fails with a message that names it, and the binary store's own limit (`LANDFLOW_BINARY_MAX_BYTES`) still applies. See "Files and binary data" below.

With `LANDFLOW_CODE_RUNNER_URL` and `LANDFLOW_CODE_RUNNER_SECRET` set, **Run In: Default** means the sandbox; `LANDFLOW_CODE_IN_PROCESS=false` turns in-process code off altogether, as the Docker stack does, and the production profile does the same when the variable is unset (a Code node then fails, saying to configure the runner or set `LANDFLOW_CODE_IN_PROCESS=true` knowingly). Start a runner with `CODE_RUNNER_SECRET=dev pnpm --filter code-runner dev` (port 7300) or the Docker one (`127.0.0.1:53300`). How it is locked down, and how to check that, is in [deployment.md, "Code runner"](../deployment.md#code-runner).
