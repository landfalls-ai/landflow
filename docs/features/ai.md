# AI agents

Part of the [Landflow docs](../README.md); the [feature map](../README.md#feature-map) lists every feature page.

The **AI Agent** is a root node with typed sub-node ports (`ai_languageModel` required/max 1, `ai_memory`, `ai_tool`), following n8n's cluster nodes. Models are provider-neutral `LanguageModel` adapters:

- **Ollama Chat Model** works locally with no API key, and its model list loads live via `loadOptions`.
- **Anthropic Chat Model** defaults to `claude-opus-5-5` with effort control and server-side refusal fallback. It uses `ANTHROPIC_API_KEY` or an `ant auth login` profile, and replays Claude's content blocks verbatim across tool turns.

**Any `usableAsTool` node becomes a tool, including remote plugins in any language.** The tool schema comes from the plugin's `toolInputSchema`, from n8n-style `{{ $fromAI('key', 'description', 'type') }}` placeholders, or from a heuristic. Tool calls in a turn run concurrently, and each call is recorded as its own sub-node run, so tool nodes light up on the canvas and the timeline shows model, tool and memory calls.

**Streamed replies**: the Anthropic, OpenAI-compatible and Ollama adapters stream tokens, and the AI Agent and the Basic LLM Chain send them as `node.chunk` events (text, plus the agent's tool calls as they start and finish). The editor's chat panel shows them live; the Chat trigger and the Webhook trigger's **Respond: Streaming** answer with them as SSE (`Accept: text/event-stream`) or NDJSON, n8n's chunk format (`{ type: 'begin' | 'item' | 'end' | 'tool', content, metadata: { nodeId, nodeName, itemIndex } }`), ending with `{ type: 'done', executionId, status, output }`.

**Files and images as model inputs**: **Include Binary as Input** (Options of the AI Agent, the chains and the OpenAI node) sends the item's images, PDFs and text files with the prompt: Anthropic image and document blocks, OpenAI `image_url` and `file` parts, Ollama `images` (PDFs and text files are read into the prompt; use a vision model such as `qwen3.8`). **Binary Fields** picks which ones. The editor's chat panel and the hosted chat attach files to a message (`data0`, `data1`… on the Chat trigger's item).

**Audio and video inputs**: with **Include Binary as Input**, audio goes to models that take it (`input_audio` for wav and mp3 on OpenAI-style audio, omni and Gemini models) or is **transcribed** first through an OpenAI-compatible `/audio/transcriptions` endpoint (**Audio Handling**: auto, send, transcribe; transcription URL and model, default `whisper-1`); video (**Video Handling**) is sent as `video_url` to models that accept it (Gemini, Qwen-VL, omni…) and otherwise fails with an error naming the model. There is no ffmpeg step. On the AI Agent, **Re-attach Files from Memory** keeps the files of earlier turns with the session memory and sends the newest ones again (up to **Max Size (MB)**, default 10); files are read back from the binary store, so they are gone once their execution is pruned.

**Tool approvals**: the AI Agent's **Tools Requiring Approval** (all tools or selected ones) pauses the execution before a tool runs (status *Waiting*); the person approves or rejects each call in the editor's chat panel or the execution view (`POST /api/executions/:id/approvals`), with buttons in a Slack channel (**Ask In: Slack**, a bot token or an installed OAuth2 app, optional approvers and timeout), or by email (**Ask In: Email**: each approver gets signed, single-use Approve and Reject links over the host's SMTP, the first decision counts). Approved calls run, rejected ones are reported to the model, and the agent continues where it stopped.

**Token and cost tracking with caps**: every model call is priced and recorded ([docs/observability.md](../observability.md#token-and-cost-tracking)); Workflow settings → **AI usage limits** caps tokens or dollars per execution and per workflow per day, and agents have daily and monthly limits. A run that goes over stops with *AI usage cap reached: … used X of its Y limit (where to change it)*.

**Model fallback**: the AI Agent, Basic LLM Chain, Text Classifier, Information Extractor and Question and Answer Chain have n8n's **Enable Fallback Model** switch. It shows a second chat-model slot (`ai_languageModel` port 1); when a call to the first model throws, the same call is retried on the fallback, logged as a warning and marked with a `landflow.ai.fallback` span event. The agent's output says which model answered (`model`, `fallbackUsed`).

## Hosted chat and widget

Turn on **Make Chat Publicly Available** on a Chat Message trigger and publish the workflow: the chat answers at `/chat/<path>` (the trigger's **Path**, else the workflow id) with the trigger's title, subtitle, initial messages and input placeholder, optional **Basic Auth**, **Custom CSS**, thumbs up / down on replies, **Load Previous Session** (transcripts per session id, kept in SQLite) and **Allow File Uploads** (MIME types such as `image/*,application/pdf`, up to 10 files of 20 MB). **Response Mode: Streaming** streams the reply; *When Last Node Finishes* answers once. To put the chat on another site:

```html
<script src="https://landflow.example.com/chat/widget.js" data-workflow="support"></script>
```

The widget renders a chat bubble in a shadow root (no style clashes) and talks to `/chat/<path>` with CORS: only the trigger's **Allowed Origins (CORS)** (comma-separated, `*` for any) may call it. With **Basic Auth** on, the widget shows a sign-in form (the browser's challenge can't be used from another origin): it sends the credentials as an `Authorization` header (allowed over CORS) and keeps them in `sessionStorage` only, per chat, until **Sign out** or the tab closes; a sub-path call without valid credentials answers `401` with JSON `{ authRequired: true, title, subtitle, customCss }` and no `WWW-Authenticate` header, while the hosted page still gets the browser's challenge. Public chat runs are production runs (webhook mode: counted in Insights, held by concurrency limits, debounce and batching).

- **Feedback**: every assistant reply in the hosted page and the widget has thumbs up / down (a thumbs down also asks for an optional comment of up to 2000 characters; pressing the same thumb again clears the rating). The widget calls `POST /chat/<path>/feedback` `{ sessionId, executionId, rating: 'up' | 'down' | null, comment? }`, which checks that the execution belongs to the chat's workflow and that the session is the one that started it (404 / 403 otherwise). Ratings are stored in `chat_feedback` and show up on the execution (`execution.chatFeedback`, a chip in the execution preview), on the agent session timeline (Sessions tab), and in the online evaluation panel: a graded run shows the user's rating beside the judge's score, the judge sees it in its prompt, and a thumbs down on a graded workflow or agent triggers a grade for that run whatever the sample rate. They are deleted with their execution or session. API: `GET` / `PUT /api/executions/:id/feedback`, `GET /api/workflows/:id/chat-feedback` (filters `rating`, `sessionId`, `limit`; totals `up` / `down`), `GET` / `PUT /api/agents/:id/sessions/:sid/feedback`.
- **Custom CSS** (a Chat trigger property, up to 20 000 characters): applied inside the widget's shadow root and on the hosted page, for the colours, fonts and radii of the chat. The easy hooks are the variables on `.lf` (`--bg`, `--fg`, `--muted`, `--line`, `--bubble`, `--accent`, `--accent-fg`) and the classes `.panel`, `.toggle`, `.msg` (`.bot`, `.user`), `.send`, `.thumb` and `.signin`. It is sanitized: `@import`, `@charset`, `@namespace`, comments and `<` / `>` are dropped (CSS escapes are decoded first, so `\40import` doesn't slip through), `url()` becomes `none` except inline `data:image/(png|jpeg|gif|webp|avif);base64`, and `image-set()`, `cross-fade()`, `src()`, `element()`, `expression()`, `javascript:`, `-moz-binding` and `behavior:` are removed. The hosted page also sends a Content-Security-Policy that blocks scripts from elsewhere and remote images and fonts.

## Retrieval (RAG)

n8n's RAG cluster nodes, with the same names and modes:

- **Vector stores**: **In-Memory** (`core.vectorStoreInMemory`, until the server restarts), **SQLite** (`core.vectorStoreSqlite`, `vectors.sqlite` in the data folder) and **Postgres PGVector** (`core.vectorStorePGVector`, a `Postgres` credential; it creates the extension, table and index). Each works in four modes, and its ports follow the mode: **Insert Documents** and **Get Many** in the main flow, **Retrieve Documents (As Tool for AI Agent)** on `ai_tool`, and **(As Retriever for Chain)** on `ai_retriever`. Documents live in named collections; searches are by vector (cosine) or **hybrid** (vector plus BM25 / Postgres full-text, fused with reciprocal rank fusion, k = 60), with exact-match metadata filters.
- **Embeddings Ollama** (nomic-embed-text, mxbai-embed-large…, with optional `search_document:` / `search_query:` prefixes) and **Embeddings OpenAI** (any OpenAI-compatible API) on `ai_embedding`.
- **Default Data Loader** (`ai_document`): all input data, one expression per item, or **Load Binary Files** (PDF per page, DOCX, text, Markdown, HTML, CSV, JSON, up to 50 MB; metadata `fileName`, `mimeType`, `page`, `chunk`), metadata per item, and a built-in splitter or a **Recursive Character** / **Token Text Splitter** (`ai_textSplitter`, with code and Markdown presets).
- **Reranker (LLM)** (`ai_reranker`): the attached chat model scores the candidates and the store keeps the best; turn on **Rerank Results** on the store.
- **Reranker Cohere** (`ai_reranker`, a `Cohere API` credential): Cohere's `/v2/rerank` scores the candidates; options for tokens per document and keeping the vector order when Cohere fails.
- **Question and Answer Chain** (`core.chainRetrievalQa`): answers from what its retriever finds, optionally with the source documents.

A vector store dropped on an agent's Tool slot switches itself to "As Tool". Agents (below) take a collection as a **knowledge base**, and documents (PDF, DOCX, text…, up to 25 MB) are uploaded to it from the agent builder's knowledge dialog (`GET/POST/DELETE /api/agents/:id/knowledge/:toolId/documents`).

## Guardrails

The **Guardrails** node (`core.guardrails`) follows n8n's: **Check Text for Violations** sends each item to **Pass** or **Fail**, **Sanitize Text** replaces what it finds and sends every item on. Checks: PII (email, phone, Luhn-checked card numbers, checksum-verified IBANs, IPv4/IPv6, US SSN, crypto wallets), secret keys (known key formats, assignments, high-entropy strings, at three strictness levels), keywords, URLs outside an allow-list (schemes, subdomains, credentials in URLs), custom regex, jailbreak / prompt-injection heuristics, and checks the optional chat model judges (jailbreak, topical alignment, NSFW, custom rules) with a threshold. Sanitizing redacts (`<EMAIL_ADDRESS>`) or masks (`j***@example.com`, `****-****-****-4242`). Reports carry masked matches only, and a model check that can't run counts as a violation. Standalone agents have the same checks as a setting (Build tab → Guardrails): per stage, **input** (before the model sees the message) and **output** (the final answer), each **block** (the person gets a reply you write; the model isn't called for a blocked input) or **sanitize** (pattern checks only, the cleaned text is stored and sent). Blocks and sanitizing show in the session view and as `landflow.guardrails` spans with the stage.

## Evaluations

**Offline**, after n8n's evaluations: the **Evaluation Trigger** (`core.evaluationTrigger`) reads test cases from a Data Table (the default) or from an uploaded **CSV or JSON file** (the trigger's Dataset: Uploaded file; the file is uploaded on the Evaluations tab, up to 10 MB, kept in the binary store, JSON as an array of objects or JSONL, the first 1000 rows used per run) and the workflow runs once per row (sequentially, each an execution marked with the run and the case). The **Evaluation** node (`core.evaluation`) has three operations:

- **Set Outputs**: records what the workflow answered (to the run, or written back to the row);
- **Set Metrics**: scores the answer: Exact Match, Contains, Regex, JSON Equality, Numeric Closeness (absolute / relative tolerance), String Similarity (edit distance), Tools Used (which tools an AI Agent called), the LLM judge's **Correctness**, **Helpfulness** and **Faithfulness** (1–5, with its reasoning, on a Chat Model slot), and **Custom** metrics from expressions;
- **Check If Evaluating**: sends items to an Evaluation or a Normal output, so the same workflow serves production and tests.

The workflow's **Evaluations** tab starts a run, lists runs with per-metric averages, shows each case's inputs, expected answer, outputs and metrics (with the judge's reasoning) linked to its execution, and **compares two runs**: metric deltas and the cases that improved or regressed. Runs and cases are stored in the database (`evaluation_runs`, `evaluation_cases`). Evaluation executions are left out of Insights and the production run counts. A **schedule** on the Evaluations tab (a five-field cron and time zone, `GET/PUT/DELETE /api/workflows/:id/evaluations/schedule`; the file at `…/evaluations/dataset`) starts runs by itself; the leader runs it in queue mode, and the tab shows the last run, last error and next run. An **Evaluation score** alert rule fires when a finished run's metric average falls below a minimum or drops by more than X% against the previous successful run, through the alert channels (migration 1822 `evaluation_settings`).

**Online**: an LLM judge grades a sample of finished conversations of a standalone agent (the agent's **Evaluations** tab) or of a workflow's AI Agent node (**AI Agent grading** on the workflow's Evaluations tab). Per agent: on/off, sample rate, rubric, judge model (default: the agent's own model, or the node's chat model) and the score at or below which a reply is flagged. Scores (1–5, reasoning, the tools called) are stored with a 30-day trend; evaluation and debug runs are never graded. "Grade a session" scores one now.

## Agents (Preview)

**Agents** (sidebar) are standalone assistants modelled on n8n's Agents tab ([docs/agents.md](../agents.md)). An agent has:
- a model (Anthropic, any OpenAI-compatible API, or Ollama) and instructions;
- [skills](https://docs.claude.com/en/docs/agents-and-tools/agent-skills) it loads on demand;
- capabilities: any plugin action node, workflows that start with **When Called by an Agent**, other agents as sub-agents, MCP servers (each tool the server lists), and knowledge bases (a vector store collection searched with a tool). Each capability can require a person's approval.
- session memory, plus optional cross-session memory per user.

You test it in a chat that streams tool calls and approval cards, then publish it as a version. The published version runs on schedules (cron, in a time zone), answers in Telegram, Slack (mentions and DMs through the Events API, slash commands, replies in threads, approval buttons; see [docs/agents.md](../agents.md#slack)) and Microsoft Teams (a Bot Framework bot with Adaptive Card approvals; [docs/agents.md](../agents.md#microsoft-teams)); tools that need approval can also be approved from an emailed link ([docs/agents.md](../agents.md#approvals-by-email)), and is callable from workflows through the **Message an Agent** node. Every run is an `invoke_agent` trace with `execute_tool` and `gen_ai.chat` children.

## MCP

Landflow speaks the [Model Context Protocol](https://modelcontextprotocol.io) both ways, with the official TypeScript SDK. Node and credential names follow n8n's.

- **MCP Client Tool** (`core.mcpClientTool`, an `ai_tool` sub-node) gives an AI Agent the tools of an MCP server: Streamable HTTP or the older SSE transport, no auth, a **Bearer Auth** or a **Header Auth** credential, and all tools, the selected ones or all except some (the pickers load the server's tool list). Each MCP tool becomes an agent tool with the server's name, description and JSON schema. Connections are pooled per server and credential, closed after 30 s idle, and reconnected once when the server forgot the session.
- **MCP Client** (`core.mcpClient`) has an **Operation**: **Call Tool** (one tool per item, outputs `{ tool, text, content, structuredContent? }`; what nodes without an operation do), **List Resources** (one item per resource and resource template), **Read Resource** (`{ uri, mimeType, text }` per content part; binary parts as their size), **List Prompts** and **Get Prompt** (`{ name, description, messages, text }` with the prompt's arguments filled in). The pickers load the server's resources and prompts.
- **Agents** take MCP servers as a capability (Capabilities → **Add MCP server**), with the same settings. The MCP Client Tool's **Also Offer** option (and the same field of an agent's MCP server) adds `list_resources`, `read_resource`, `list_prompts` and `get_prompt` as agent tools next to the server's own tools.
- **MCP servers that sign users in (OAuth)**: choose **MCP OAuth2** as the Authentication of the MCP Client, MCP Client Tool or an agent's MCP server, with an **MCP OAuth2 API** credential (`core.mcpOAuth2Api`: the server URL, optionally a client ID and secret and a scope). **Connect** follows the MCP authorization spec: the server's 401 `WWW-Authenticate` (or `/.well-known/oauth-protected-resource`) leads to the protected resource metadata (RFC 9728), then to the authorization server's metadata (RFC 8414, OpenID Connect discovery); without a client ID Landflow registers itself dynamically (RFC 7591, a public client, again when the redirect URL changes), else the ID (and secret) is used as given. The sign-in is authorization code with PKCE (S256 required), the `resource` parameter (RFC 8707) goes on the authorization and every token request, and the token is stored encrypted and renewed before it expires and once after a 401 (also mid-run inside an agent). A server with no metadata is treated as its own authorization server; one with neither registration nor a client ID says what to register (`apps/web/src/lib/server/mcp/oauth.ts`). Tried against a fake server and the dev Keycloak (`LANDFLOW_INTEGRATION=oauth2`).
- **MCP Server Trigger** (`core.mcpTrigger`) serves the tools attached to its `ai_tool` input (any tool sub-node, or a node used as a tool such as **Execute Workflow**, whose arguments come from `$fromAI()`) at `/mcp/<path>`, over Streamable HTTP, with optional bearer or header auth. Only published workflows answer there. `tools/list` runs the trigger alone and isn't recorded; each `tools/call` is an execution with mode `mcp`. The node panel shows the Production URL and the **Test URL** (`/mcp-test/<path>`): **Listen for test event** serves the tools of the workflow as it is in the editor, and each tool call is a manual run shown live on the canvas (see Test URLs in [Triggers and flow nodes](engine.md#triggers-and-flow-nodes)). Its **Resources** and **Prompts** parameters add what clients can read and use besides tools: a URI or name, a description, and content that is text written in the node or the last output of a sub-workflow (a workflow with a **When Called by Another Workflow** trigger). Listing runs nothing; static text is served as it is, and text with an expression (`$json.resource`, or `$json.arguments.<name>` for a prompt's arguments; a prompt argument followed by `?` is optional) or a sub-workflow is an execution with mode `mcp`, a manual run on the test URL.
- **Instance MCP server** at `/api/mcp`, for coding agents such as Claude Code: list, read, create, update and validate workflows; list and search node types and read a type's parameters; execute a workflow with input and get the result (the draft by default, or `version: "published"` for what production runs); list executions and read one. It is off by default. **Settings → MCP** turns it on, shows the access token once (regenerate for a new one) and the client config, for example:

  ```bash
  claude mcp add --transport http landflow http://localhost:3000/api/mcp --header "Authorization: Bearer <token>"
  ```

**Per project**: `/api/mcp/projects/<projectId>` is the same server limited to one project (its workflows only; what it creates lands there). A **Landflow MCP token** issued for a project (Settings → MCP → **Project** when issuing) is scoped the same way wherever it is used, and 403s at another project's URL. A project's admins can also put it on the gateway (the project's **MCP** card, or `PATCH /api/projects/:id/mcp { gateway }`): one route `/mcp/projects/<name>` per enabled project, with its own protected resource metadata at `/.well-known/oauth-protected-resource/api/mcp/projects/<id>`.

Both servers are stateless (a fresh server per request, JSON responses), so they need no session affinity; GET and DELETE answer 405.
- **Plugins as MCP servers** ([docs/transports.md](../transports.md), "MCP: every plugin is also an MCP server"): behind the bundled gateway (agentgateway, `LANDFLOW_MCP_GATEWAY_PUBLIC_URL`, `/mcp` for every plugin and `/mcp/plugins/<id>` for one) the host serves one MCP endpoint per plugin at `/api/mcp/plugins/<id>`. **Who may call** (`apps/web/src/lib/server/mcp/identity.ts`): through the gateway, the call carries the gateway secret (`x-landflow-gateway` = `LANDFLOW_MCP_GATEWAY_SECRET`, compared in constant time) and the caller's `iss`/`sub` the gateway validated; without the secret those headers are ignored. Directly, `Authorization: Bearer` with a **Landflow MCP token** (Settings → MCP → Tokens: a signed ES256 JWT, `iss` = the instance URL, `sub` = the user, `aud` = `<instance>/api/mcp` and the gateway's `/mcp`, `jti` checked for revocation on every call, keys at `GET /api/mcp/jwks`), an **access token of the identity provider** (`LANDFLOW_OIDC_ISSUER`; verified against its JWKS with an audience check, mapped to the user who signed in with that identity), or a Landflow API key. A 401 carries `WWW-Authenticate: Bearer resource_metadata="…"` pointing at the protected resource metadata (RFC 9728) at `/.well-known/oauth-protected-resource/api/mcp[/plugins/<id>]`, which lists the identity provider and this host as authorization servers.
- **Tool grants** (Settings → MCP → Grants, owners and admins; `GET/POST /api/mcp/grants`, `PATCH/DELETE /api/mcp/grants/:id`): who (a user, a SCIM group, everyone in a project, a role, or the holder of one MCP token) may list and call which tools of which plugin (`*`, names, `!name` excludes), and which credential each credential type binds. A caller's tools are the union of the grants that apply to them, minus the governance allow-lists (a project grant also applies that project's allowed nodes); a tool with no grant is not listed and cannot be called. Owners and admins browsing from the UI see every tool, to write grants. Audited as `mcp.token.issue/revoke` and `mcp.grant.create/update/delete`.
- **Triggers as MCP resources** (a plugin endpoint, 2026-07-28 clients): a plugin's poll and app-webhook triggers show up in `resources/templates/list` as `landflow://triggers/<plugin>/trigger_<name>{?parameters}` for callers whose grant covers `trigger_<name>` (or `*`; governance and credential binding apply as for tools). `subscriptions/listen` with that URI in `resourceSubscriptions` starts the trigger for the caller (a poll every `pollInterval`, at least `LANDFLOW_MCP_TRIGGER_MIN_INTERVAL_SECONDS`, 10 s; or an app webhook registered with the service); the first poll is a baseline, later news arrives as `notifications/resources/updated` and `resources/read` returns the buffered events (`LANDFLOW_MCP_TRIGGER_BUFFER`, 50; files as signed `files` links). The trigger stops when the last stream ends, the grant or token goes, or nobody reads for `LANDFLOW_MCP_TRIGGER_IDLE_SECONDS` (1 h); events stay readable for `LANDFLOW_MCP_TRIGGER_RETAIN_SECONDS` (10 min). 2025-11-25 clients can `resources/read` a poll trigger once (the node's manual mode). Audit: `mcp.resource.subscribe`, `.unsubscribe`, `.read`.
- **Through the gateway**: the sync also registers the instance server (when Settings → MCP turned it on) at `/mcp/landflow` and each published workflow's enabled MCP Server Trigger at `/mcp/workflows/<name>`, and removes them when the server is turned off or the workflow is unpublished or deleted. A signed-in gateway caller runs as that user under their project access; an anonymous one falls back to the trigger's own authentication (the gateway strips `Authorization`, so a Bearer Auth trigger must be called directly).
- **The catalog**: a `server.json` per exposed plugin (the MCP Registry schema 2025-12-11: `<LANDFLOW_MCP_NAMESPACE, default local.landflow>/<pluginId>`, the plugin's version, `remotes[]` = its gateway URL and its direct endpoint), the read-only registry API `GET /api/mcp/registry/v0.1/servers` (`?limit`, `?cursor`, `?search`, `?version=latest`; `/{name}/versions`, `/{name}/versions/{version|latest}`; status `active` / `deprecated` / `deleted` as plugins come and go) and Server Cards at `/api/mcp/plugins/<id>/server-card` and `/.well-known/mcp/server-card.json`, all open to the same callers as `tools/list`.
