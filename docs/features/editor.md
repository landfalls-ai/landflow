# Building and debugging a flow

Part of the [Landflow docs](../README.md); the [feature map](../README.md#feature-map) lists every feature page.

The editor follows n8n's layout, in Landfall's monochrome style. Colour comes from the nodes, the plugins' brand colours and run states. A screen-by-screen comparison with n8n, including what is still missing, is in **[docs/ui-review.md](../ui-review.md)**.

**Start a flow fast**
- **Describe it**: on an empty canvas, Spotlight (the bar at the bottom) takes a sentence such as "score review sentiment, keep the negative ones and hash them". A local Ollama model drafts the flow from the live node catalogue. The host validates the draft and lays it out, and sample items are pinned on the trigger so it can run straight away (one item when the flow runs an agent or a team, since each item is a whole agent run). This takes about 10 s on `qwen3-coder:30b`.
- **Templates**: four starter flows on the empty canvas (plugins pipeline, branch and merge, webhook with test data, AI agent).
- **Templates library** (**Templates** in the sidebar): 18 built-in templates (AI agents with Ollama, OpenAI or Anthropic, RAG support, Slack, Telegram, Gmail, GitHub and HubSpot flows, webhooks, forms, schedules, Data Tables, Postgres sync, error alerts…) with search, categories and cards showing the nodes they use. A template's page has a read-only canvas preview, its description, setup steps, the credentials and data tables it needs, and **Use template**: name the workflow, pick a folder and pick or create a credential for each **credential slot** (only credentials of the slot's type are offered); missing data tables are created, webhook / form / chat paths are made unique, and the new inactive workflow opens. **Save as template** (workflow menu) keeps a workflow as a template on this instance, in a project (its members see it; the workflow's project is picked first) or, for owners and admins, the whole instance: credentials become slots, and pinned data, the folder, tags and publication state are left out. **Edit** on a saved template's page changes it in place (name, description, categories, setup steps, its project, or its workflow replaced from a saved workflow; `PATCH /api/templates/:id`), for the editors of its project (owners and admins for instance-wide ones). **Export** downloads a template file that **Import** on the Templates page adds elsewhere. Templates whose nodes are missing (plugin not installed) or blocked by the governance policy say so and can't be used. Templates can also come from a marketplace plugin's flows ([Marketplace](../marketplace.md#flows)): installing the plugin adds them instance-wide with an origin, their card names the plugin, their page links to the flow's read-only share page, and uninstalling removes them. The **Security** and **Incident response** categories hold the [triage and Landfall](../triage.md) flows. With `LANDFLOW_TEMPLATES_URL` (off by default) an n8n-compatible templates API (`https://api.n8n.io/api`) is searched too: its workflows go through the n8n importer and the template page shows the import report; results come 30 at a time with **Load more**. The project picker on the Templates page (`?project=`, else the project worked in last) shows that project's saved templates and the instance-wide ones, counts its allowed nodes in "usable", and **Use template** creates the workflow there (or in the folder's project), with its data tables: a table of the same name is reused only from that project. Saved templates belong to a project (migration 1401 `templates.project_id`; existing ones stay instance-wide). The Workflows page's empty state (and an empty folder's) suggests them. A team page's **Save as template** makes a [team template](../templates.md): the team, its agents and a flow that runs it.
- **Node creator** (`+`, `Tab` or `N`): n8n's side menu. It asks "What triggers this workflow?" first, then "What happens next?" with AI, Data transformation, Flow and Core, followed by **one segment per plugin**. Each segment shows the plugin's own icon and colour, an online dot, and its language and transport. New nodes chain onto the selected node, a "+" on an edge inserts into it, and the node opens ready to configure.
- **Tidy up** (`⇧⌥T`) lays the graph out in layers: each column as wide as its widest node (an agent is wider than a tile) with the same room between columns, so outputs' names and the + never crowd the next node. A chain stays level with the node before it, siblings spread around their parent, and sub-nodes sit centred under their agent, far enough apart for their names.
- **Connections** go from an output on a node's right to an input on the left. One back to an earlier node (a loop, such as a send-back) leaves its output to the right, runs along a lane under every node it spans and comes into the input from the left, so it never cuts through a node; its item count sits on the lane. Sub-node connections run from the bottom of an agent to the top of its model, memory and tools. An agent-shaped node is wide enough for its slot names not to touch, and output and input names sit on the canvas colour, so a line passing under them stays readable. Nodes that stand for an agent show its [avatar](../agents.md#avatars).

**See that it works**
- **Execute workflow** (`⌘↵`): nodes light up as they run, edges turn green with item counts, and dots travel along edges while items flow. A node that reports progress gets a live caption above it in plain words ("Planner · Running the tests", the exact step on hover), and a Run a Team node becomes the member working now, with its last steps, a ribbon of turns and the moments that matter, and keeps a summary after the run ([agent-teams.md](../agent-teams.md#watching-a-team-work)). A finished node's duration reads "6m 32s" rather than milliseconds. While a node that reports progress grows past the visible canvas (above the top or under Spotlight's bar), the view moves to keep it in sight, never zooming in, until you pan or zoom. **A run outlives the editor**: closing or reloading the page leaves it running, and the editor opened again shows it live (its nodes, a team's member at work) and follows it to the end; a dropped connection does the same. **Stop** asks the server (`POST /api/executions/:id/stop`). A debug run is the exception: it stops with the page, since nobody would be left to step it. A run that ends **waiting** marks the node it waits at (a blue **Waiting** chip whose tooltip says what for: "Waiting until 14:05", "Waiting on 2 of 3 sub-workflows", "Waiting for a webhook call", "Waiting for a form submission"); the editor follows it in the background, so the count goes down as sub-workflows finish and the rest of the run shows once it resumes. Opening a waiting execution in the editor marks it the same way.
- **Logs panel**: every node run in order, with a mini waterfall, sub-node calls (model, memory, tools) nested under the node that made them, and the selected run's input and output as **Schema, Table or JSON**. **Re-run task** runs one node again with its earlier input. **Run from here** reuses the upstream results. **Events** shows the raw stream.
- **Node details**: Input | Parameters | Output. Drag a field from the input schema into a parameter to insert `{{ $json.path }}`. Expressions show their **resolved value** for the first input item as you type. You can pin output or set test data on a trigger.
- **Debug**: breakpoints (`F9`), Step (`F10`), Continue (`F8`) and Stop. While paused, the node glows amber and its waiting input can be inspected.
- **Test URLs** (n8n's **Listen for test event**): the Webhook, Form and MCP Server trigger panels show a **Test URL** and the **Production URL**, each with a copy button. **Listen for test event** (a 120 s countdown and **Stop**; also started by **Execute** when the workflow starts at such a trigger without pinned data, and by the Form trigger's **Open test form**) makes `/api/webhook-test/<path>`, `/form-test/<path>` or `/mcp-test/<path>` answer; the call runs the workflow as it is in the editor, saved or not, as a manual run that lights up the canvas like Execute, and the trigger's output shows what arrived. An MCP Server Trigger keeps listening while an MCP client uses it (120 s past its last request): each tool call is a run of its own on the canvas. See [Triggers and flow nodes](engine.md#triggers-and-flow-nodes).
- **Assistant** ([docs/assistant.md](../assistant.md)): after a node runs, its panel shows **✨ Suggestions** from the local model: fixes for the error, parameter tweaks, data problems and the next node to add, each with Apply / Dismiss. **Spotlight**, the bar at the bottom of the canvas (`⌘I`), is the builder chat: bubbles above it suggest what to ask and complete `@` nodes and node types as you type, and the assistant searches the node catalog, reads node docs, the workflow and the last run, then proposes changes as diffs you apply, with an undo. It uses only the node types the workflow may use, and changes are validated against the registry before you see them.
- **Executions tab** (Editor | Executions): n8n's list of runs with a read-only canvas, an error banner, the Logs panel, Debug in editor, and Retry/Re-run with the saved or the original workflow. The canvas shows groups as they were saved: a collapsed group is a box with its run status ("1 failed" with a red outline when a node inside failed, "Running", "Waiting until 14:05", "3 of 4 ran", "Did not run"), and its chevron (or a double-click) expands it in the preview only, without changing the workflow; the waiting node is marked as in the editor. The canvas fits again when a node grows after it opened (a team node's summary arriving), until you pan or zoom. On a desktop the newest execution opens beside the list; on a phone the list and an open execution are one screen at a time, with a back arrow to the list. The global **Executions** page is a filterable table of every run.
- **Evaluations tab** (Editor | Executions | Evaluations): run the workflow over its test cases, see each run's metric averages and per-case results (each linking its execution), and compare two runs. See [Evaluations](ai.md#evaluations).

**Edit and organise**
- **Sticky notes** (`⇧S` or the note button on the canvas): Markdown notes behind the nodes. Double-click to edit, drag the corners to resize, and pick one of seven colours from the toolbar above a selected note. They are saved in `workflow.stickyNotes` (never as nodes) and show read-only in the Executions tab.
- **Groups** (`⌘G`, or right-click a selection → **Group**): a labelled frame around nodes. Dragging the frame's header moves its nodes; resize it from the corners, rename it (double-click the name or the toolbar), pick one of seven colours, **collapse** it to a compact box (edges in and out stay visible, merged per neighbour with a count), duplicate it with its nodes, and **Ungroup** (`⇧⌘G`). Drop a node onto a frame to add it, drag it out to take it out. Groups **nest**: `⌘G` on a selection that includes frames (or right-click → **Put in a new group**) wraps them in a new group, and dropping a frame onto a bigger one puts it inside. A selection can span **different parents**: nodes and groups from sibling groups, from different depths or from different branches get a new group inside the lowest group that holds all of them (the top level when they share none); the picked groups move in with what they hold, the picked nodes leave their groups for it, and the groups around it grow to fit. Moving or resizing a parent moves everything in it and grows it to fit, collapsing a parent hides its child groups too (edges merge onto the outermost collapsed box), and ungrouping or deleting a group hands its nodes and child groups to its parent. Groups are saved in `workflow.groups` (`{ id, name, color?, collapsed?, parentId?, nodeIds, position, width, height }`, where `nodeIds` are a group's own nodes and `parentId` the group it sits in; never as nodes, so the engine ignores them; workflows without `parentId` load as before) and go through undo / redo, copy and paste (a group brings its nodes and child groups), duplicate, import and export, the version diff ("Groups changed"), Git sync and templates; frames are focusable with a label such as "Group Ingest, 3 nodes, 1 group".
- **Composites** ([composite nodes](../composites.md)): a group typed by a contract (a composite type from a plugin, core's **AI step**, or one saved here). The node creator's **Composites** section drops one with its starter nodes; the frame's header badge counts its errors and warnings and opens the contract panel (slots, free members, properties, where failures go, rules, issues with fixes); empty required slots show as dashed placeholders that open the node creator filtered to what fits; a node dropped in binds to the slot it obviously fills; nodes in a locked slot can't be deleted. **Composite…** on a group's toolbar types it by an existing type or saves a new type from it. Errors block Publish, never Save.
- **Copy, cut, paste, duplicate** (`⌘C` `⌘X` `⌘V` `⌘D`): selections, with the connections between them, sticky notes and pinned data, go through the system clipboard as JSON, so they move between workflows and browser tabs. Pasted nodes get new ids and n8n-style names when a name is taken (`HTTP Request` → `HTTP Request1`). `$('Name')` references between pasted nodes follow the rename; references to nodes outside the selection keep pointing at the original. Pasting **n8n clipboard JSON** converts it with the importer and reports nodes that became placeholders.
- **Undo / redo** (`⌘Z`, `⇧⌘Z`): canvas edits, parameter typing (coalesced per node), pasting, deleting and tidying up, and the workflow's name (one step per rename, when the title loses focus or gets Enter), tags (one step per tag added or removed) and settings (one step per Save of the settings dialog) in the same history. Undoing back to what was last saved shows **Saved** again. `?` lists every shortcut.
- **Expressions**: inside `{{ }}` the parameter field highlights the expression and suggests `$json` fields from the node's input, upstream nodes (`$('Node').item.json.…`), `$input`, `$now`, `$today`, `$workflow`, `$execution`, `$itemIndex`, `$vars` and methods for the value's type (↑↓, Enter or Tab, Esc; `⌃Space` opens the list). Typing `{{` closes the braces.
- **Code editor**: the Code node (JavaScript, Python) and the other `code` and `json` parameters get syntax highlighting (keywords, strings and template literals, numbers, comments, regular expressions, the workflow globals, JSON keys and `{{ expressions }}`) in light and dark mode, **line numbers** in a gutter that scrolls with the text, **bracket matching** (the bracket next to the caret and its partner are marked, a lone one in red; brackets inside strings and comments don't count), **auto-close** of brackets and quotes (typing one with a selection wraps it, typing the closer steps over it, `Backspace` between an empty pair takes both, nothing inside strings and comments or after a word character), **find and replace** (`⌘F` / `Ctrl-F`; `⌘H` / `Ctrl-H` or `⌥⌘F` with the replace row; `⌘G` / `F3` for the next match, `⇧⌘G` for the previous; match case, whole word and regular expression toggles with `$1` / `$&` / `$<name>` in the replacement, a match counter, **Replace** and **All**, undoable with `⌘Z`; `Esc` closes the bar), `Tab` / `⇧Tab` to indent and outdent, `Enter` keeping the indentation, `⌘/` to comment lines, and in code the same suggestions as expressions (`$json.…` fields of the node's input, `$input`, `$('Node')`, or `_json`, `_input`, `_('Node')` in Python; `⌃Space` opens the list). The value stays a plain string; there is no editor dependency, the field is a textarea under a highlight layer (`components/editor/code-editor.tsx`, `code-highlight.ts`, and the editing logic in `code-editing.ts`, `code-search-bar.tsx`).
- **Workflow menu** (`…` in the top bar): **Settings** (error workflow, **Notify on failure** (see Failure alerts in [Durable runtime](engine.md#durable-runtime)), time zone, timeout, which workflows may call this one, which executions to save), **Version history**, **Download** as JSON, **Save as template**, and **Import** from a file or pasted JSON into the open workflow (Landflow, n8n or Flowise).
- **Version history**: every save that changes the workflow records a version (the last 50 per workflow, identical saves are skipped) in the database. The panel lists them with a summary of what changed, previews a version read-only on the canvas, and restores it (the restore is a new version, so it can be undone the same way).
- **Draft and publish**: saving keeps a draft; **Publish** (top bar, with an optional note) puts a saved version live. Production starts (webhooks, forms, schedules, polls, app webhooks, IMAP, MCP Server Triggers, error workflows and Execute Workflow from production runs) run the published version, while the editor runs the draft. The top bar shows "Unpublished changes" when the draft moved on, the version history marks the published version and can publish an older one (a rollback), **Unpublish** stops production triggers, and an execution says which version ran ("ran version 7 (published)"). `active` means "has a published version": workflows that were active before draft and publish were published on their newest version at the upgrade (migration 200), and an API client that still saves with `active: true` publishes what it saved. The API, the CLI (`workflows publish/unpublish`) and Git sync go through the same publish functions (`apps/web/src/lib/server/publish.ts`).
- **Tags** in the top bar, and **folders** on the Workflows page: nested folders with a breadcrumb, create / rename / delete (only when empty), move a workflow from its menu or by dragging it onto a folder or breadcrumb step, search by name, filter by tag and sort by last updated, name or created. Folders belong to a **project** (migration 1400 puts each existing folder tree in the project most of its workflows are in, else the owner's personal project): the project picker (`/workflows?project=<id>`, or **Folders** on a project page) shows one project's folders and creates there, subfolders stay in their parent's project, only the project's editors change them, and a workflow only goes into a folder of its own project (**Move to project** takes a `folderId` of the target, else the workflow goes to its top level). **Import** on the Workflows page creates a workflow from a Landflow, n8n or Flowise JSON file and shows what was mapped, what became a placeholder and any warnings.

## Importing from n8n and Flowise

Import (Workflows page, the workflow menu, `POST /api/workflows/import`, `landflow import`) tells the format apart by its shape and returns the same report: nodes mapped, placeholders (disabled No Operation nodes keeping the original type and parameters in their notes), connections, sticky notes and warnings.

- **n8n**: triggers, flow and core nodes, the Code node in JavaScript and **Python**, Schedule Trigger **cron** expressions as trigger rules, AI Agent, chains and chat models, the **RAG** nodes (vector stores in every mode, Ollama / OpenAI embeddings, the Default Data Loader, the Recursive Character / Character / Token splitters, the Question and Answer Chain, `toolVectorStore` / `retrieverVectorStore` wrappers folded into their store), **Guardrails**, **Call n8n Workflow Tool** and the **Evaluation Trigger** / **Evaluation** nodes.
- **Flowise** chatflows and agentflows (v2): chat models, memory, tools, prompt templates folded into their chain, conversation and LLM chains, the Tool Agent, document loaders, splitters, embeddings and vector stores (split into an upsert branch with its own manual trigger and a retrieval branch, as a retriever or an agent tool), and agentflow Start / Agent / LLM nodes. The chat input becomes a Chat Trigger. **Credentials**: Flowise exports never carry secrets, so the report lists the credential slot each model, embeddings and Postgres node needs (OpenAI and its compatible providers, Azure OpenAI, Groq, Mistral, DeepSeek, OpenRouter, LocalAI → OpenAI API; Anthropic; Postgres; Cohere) and the importer fills the slot when exactly one saved credential of that type is visible, else marks it *choose* or *create*. **Custom JS Function** nodes (and the agentflow node) become Code nodes (JavaScript, once per item): `$flow` and the `$variable` inputs are defined from the item and `$vars`, the original code runs inside, and the result is in `output`; `$flow.state`, chat history, `require` and `process.env` get a note and a warning. **Document stores** defined in the file (next to a chatflow, or a standalone store export) expand into loaders, splitter, embeddings and vector store with an Upsert trigger and one insert node per loader; a store the file doesn't define stays a reference to a collection of the same name. File loaders (PDF, DOCX, CSV, JSON, text) map to the Default Data Loader's **Load Binary Files** mode. The Flowise test fixtures (`apps/web/test/fixtures/flowise`) are synthetic, written from Flowise's node definitions.
