# Git sync

Part of the [Landflow docs](../README.md); the [feature map](../README.md#feature-map) lists every feature page.

Workflows as files you review and version in Git, like Windmill's `wmill sync` and n8n's source control. One layout (`landflow-sync/v1`, `apps/web/src/lib/server/sync/format.ts`) serves the CLI and the server's own Git:

```
landflow-sync.json                    { "format": "landflow-sync/v1" }
variables.json                        { "variables": [{ "key": "API_BASE" }] }   (values, and per-environment `environments`, only when asked for)
credentials.json                      { "credentials": [{ "name", "type" }] }   what the workflows reference, never data
data-tables/<slug>.schema.json        a table's id, name and columns (no rows)
workflows/<slug>.workflow.json        a workflow at the top level
workflows/<folder>/.folder.json       { "id", "name" }: one directory per folder, nested
workflows/<folder>/<slug>.workflow.json
```

- **Files**: pretty-printed with a fixed key order (`id`, `name`, `description`, `active`, `tags`, `settings`, `nodes`, `connections`, …; node parameters keep their order) and a final newline, so the same state always writes the same bytes and diffs stay small. Timestamps and the folder id are left out (the directory is the folder). Nodes reference credentials as `{ "name", "type" }`; on the way in they are matched to the instance's credentials by name and type (a missing one is a warning, and the node shows it unset).
- **CLI** (`landflow sync … --dir <path>`): `pull` writes the instance into the directory (managed files only; a README or `.git` is left alone) and refuses to overwrite files edited since the last pull without `--force`; `push` creates and updates by stable id (a file without an `id` gets one from its path), deletes only with `--prune`, and refuses changes the instance made since the directory last synced with it (409, exit 5) unless `--force`; `status` is a dry-run push plus the locally edited files; `diff` is a unified diff from the instance (`a/`) to the files (`b/`). Each directory remembers per instance URL what it last synced in `.landflow/state.json` (git-ignored by its own `.gitignore`). Files that don't validate stop a push before anything changes. An active workflow is published when its file says `active: true` and unpublished when it turns false.
- **Server-side Git** (Settings → Source control, owners and admins): a repository (absolute path, `file://`, `https://`, `ssh://` or `user@host:path`), a branch and optionally a sub-directory. **Push** exports the instance into a working copy under the data directory (`source-control/repo`), commits with your message and pushes the branch; **Pull** fetches and applies the branch (preview first; conflicts with edits made on the instance since the last push or pull, overridable; **Delete missing** prunes). Git runs as the `git` CLI without a shell, with the host account's git configuration, hooks, credential helpers and the `ext::` transport turned off; repository strings starting with `-`, remote helpers and URLs with user info are refused. An HTTPS token comes from a saved credential (its `token`, `accessToken`, `password`, `apiKey`, `value` or `key` field) or `LANDFLOW_GIT_TOKEN` and reaches git only through `GIT_ASKPASS` and the child's environment, never the URL, the command line or the repository config. SSH (`ssh://`, `user@host:path`) uses the **SSH key of a credential** when one is chosen: create a *SSH private key* credential (`core.sshPrivateKey`: the key as PEM or OpenSSH, an optional passphrase) and pick it in Settings → Source control. The key is written to a private temporary directory for the one git call and deleted after it; ssh runs with `IdentitiesOnly`, no agent and no password prompts, `-F /dev/null`, and **`StrictHostKeyChecking=yes` against a pinned `known_hosts`**: **Fetch host key** (`POST /api/source-control/host-keys`, `ssh-keyscan`) shows the host's keys with their SHA256 fingerprints, and **Pin these keys** saves them; a host whose key changed is refused with a message naming the host. Without a credential, SSH uses the host account's keys (batch mode). **Per-workflow commits**: *Only some workflows* in Settings → Source control (or `source-control push --workflow <ids>`, or **Git history…** in a workflow's menu → *Commit and push this workflow*) commits and pushes just those workflows and their folders, and a later pull still sees the others' state as it was. **Git history** (`GET /api/workflows/:id/git-history`, with `/<commit>?path=` for the diff and `POST …/<commit>/restore {path}`) lists the commits that changed a workflow's file in the pushed repository (across renames and moves) with the diff of each, and *Restore as draft* puts that version back as a new draft, keeping its folder and whether it is published.
- **Endpoints**: `GET /api/sync/export` and `POST /api/sync/apply` (dry run, prune, force, base hashes) do the work for both; see the API table.
- **Projects**: a pull files each new top-level folder in the project of the workflows (by the ids in their files) that sit in it, subfolders follow their parent, and a new workflow filed in another project's folder is created in that project; a workflow already on the instance is never moved into another project's folder (it stays where it is, with a warning), and a folder only moves under a folder of its own project. Tables a pull creates go to the default project, and a table is matched by name only among that project's (names are unique per project).
- **Format additions** (still `landflow-sync/v1`; older versions ignore them): a variable may carry `"environments": { "staging": "…" }` (its per-environment values, written with values); promotion commits carry `Landflow-Promoted-From` / `Landflow-Promoted-Commit` trailers; a pull takes `publish` (below).
