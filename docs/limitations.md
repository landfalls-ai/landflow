# Known limitations

What Landflow does not do yet, or does only partly. [roadmap.md](roadmap.md) records what each wave built and the
items still open (its "Wave 6" section); this page is the short list to check before relying on a feature.

- **Isolation**: expressions and in-process Code nodes run in `node:vm` with timeouts. That is not a security boundary. Code you don't trust belongs in the code runner's container (see [deployment.md](deployment.md#code-runner)); started with pnpm, the runner only has OS limits.
- **Scaling out**: [queue mode](features/engine.md#queue-mode-workers-and-high-availability) runs several mains and workers, but every process keeps the whole database in memory (Postgres mode), Valkey Sentinel and Valkey Cluster give failover but not scale-out (every queue key shares one hash tag, so the queue lives on one node), and with `LANDFLOW_CONFIG_STORE=files` the files in the shared data directory are last-writer-wins. Checkpoints add a write per node run (Postgres mode also appends it to the spool). The SQL Data Tables storage still caches a table's rows in memory when it is used (50,000 rows per table).
- **Sign-in**: without queue mode, sign-in rate limits and edit locks live in the host's memory (a restart clears them; in queue mode the limits are shared through Valkey and every main keeps the locks in step). Per-IP limits, audit addresses and webhook IP allow-lists use the address `LANDFLOW_TRUSTED_PROXIES` says to trust (default 0: the last `X-Forwarded-For` entry, which a client that reaches the host directly can still forge); behind a proxy, set the hop count. The instance MCP server is scoped to a project only through a project URL or a project token (the unscoped one sees what its user sees).
- **Integrations are tested against fakes**: every plugin's tests use local fakes of the service. The databases plugin is the exception: its integration tests run the Postgres, Postgres Trigger, Redis and MySQL nodes against the infra stack's real servers ([deployment.md](deployment.md#integration-tests-databases-plugin)). Switch and Text Classifier have a fixed set of outputs (4 plus a fallback): ports can be shown or hidden by parameters, but not repeated per rule. Stripe, Slack, GitHub and Microsoft Teams were checked against local fakes only, and Slack's Events URL is pasted into the Slack app by hand.
- **Not yet built**: webhook-based triggers for apps other than GitHub, Stripe and Slack (the others poll; the protocol and SDK signature helpers are ready, [protocol.md §12](protocol.md#12-app-webhook-triggers)), remote model/memory providers over the protocol (tools already work remotely), mDNS discovery, n8n v3-style engine-driven agent steps, file uploads in a standalone agent's test chat, and MCP subscriptions (they need a 2026-07-28 client). Telegram, WhatsApp Cloud, Twilio, SMTP and the databases have no OAuth2, so their credentials take tokens or passwords.
- **Alert triage and Landfall** ([triage.md](triage.md)): the Landfall node and trigger were built from Landfall's API and checked against a local fake (`pnpm fake-landfall`), not a live Landfall; the same goes for the seven threat intel services, tested against `httptest` fakes. The Landfall Trigger polls. Triage's quality depends on the model and the rules; that is why it starts in Shadow mode. Runbooks from closed rooms ([runbooks.md](runbooks.md#not-built)) are folded by fixed rules from a room you paste or pass in, into form-wait steps for people, not generated action nodes; nothing makes one by itself when a room ends, and the folding was checked against fixtures, not a live Landfall. Flow share pages need a signed-in member of the instance; they aren't public links.
- **Deployment and the gateway**: the KEDA worker example (`deploy/k8s/examples/keda`) has not been applied, since KEDA is not installed on the local cluster. With the identity provider accepted on a gateway route (`components/gateway-landflow-tokens-idp`), the gateway's own 401 carries no `WWW-Authenticate` challenge.
- **Dictation in Spotlight** ([assistant.md](assistant.md#spotlight)): push-to-talk only, in the editor's Spotlight; the text goes into the box to edit, and replies are not spoken. No speech-to-text server ships with Landflow: `LANDFLOW_STT_URL` must point at an OpenAI-compatible one (nothing listens on the default `http://127.0.0.1:8000/v1` until you start one), and recordings are cut at two minutes or 10 MB. Safari and Firefox record in formats some servers reject. Checked live in Chrome against a local speaches server with a stubbed `getUserMedia` (a spoken clip played into the real `MediaRecorder`), not with a real microphone.
- **Spotlight on the local model**: `qwen3-coder:30b` doesn't always follow the brevity rule (it may still write a numbered list). The guards against "it has been added" and made-up ids match common wordings and id-like parameter names ([assistant.md](assistant.md#the-builder-chat)), not every case, so a proposal card is still the thing to read before Apply. [Test and fix](assistant.md#test-and-fix) leans on the same model: a flow it drafts often has empty filter conditions or Set fields, and a fix can take a few rounds or run out at 4 (one trial spent all 4 on an Aggregate node's fields). The same prompt can pass in one session and fail in the next. Its checks are structural (a node failed, nothing reached the end, a step with no conditions or fields) plus the model's own reading of the output against the goal, so a run it calls ready is worth a look before publishing. A proposal still waiting is matched by node type and name, so the same job under another name isn't recognised, and the same goes for a node added back after a pending proposal removed it (a summary first done by a Basic LLM Chain and then by a Code node gets through; a node the latest message asks to add by that name, "remove Check and add a new Check after Code", is let through); the check against an If or Filter after a node that already branches looks only at nodes added or connected without an explicit output; Code nodes have no usable `$runIndex`, so a round counter keeps its number in a field. Adding a node `after` one that already feeds another leaves that old connection in place without a warning (a v2-to-v3 trial kept Tech Lead → Open draft PR).
- **Composite nodes** ([composites.md](composites.md#not-built)): no governance rule can require a composite yet (for example "AI calls only inside an AI step"). A frame's fallback is picked in its contract panel, not drawn as an edge. A frame's timeout is checked when each node inside starts, so a node already running isn't interrupted. Composite types saved on an instance (`local.<name>`) aren't part of Git sync or environment promotion: on another instance a frame typed by one shows the type as unknown until it is saved there too.
- **Remote agents over A2A** ([a2a.md](a2a.md#not-built)): a remote agent's tokens are recorded but don't count toward an agent's AI limits. Landflow calls agents over A2A but doesn't serve A2A itself, and uses neither push notifications nor the gRPC and REST bindings. The dialog doesn't preview the agent card. kagent 1.0.0-alpha17 drops the `landflow.*` message tags instead of copying them onto its spans, parents its MCP calls back into Landflow on a span it never exports (they show as separate roots of the same trace), marks its stream spans as errors when a stream closes, and elides message content in its logs. kagent runs in a kind cluster beside the OrbStack one, since Agent Substrate needs Kubernetes 1.37. An agent deployed to kagent ([a2a.md](a2a.md#landflow-agents-on-kagent)) gets its persona, model and tools but not cross-session memory, guardrails or usage limits; its sessions on kagent don't show in Landflow's Sessions tab, and drift from an edit made in kagent shows when the status is read, not as it happens. On kagent's Claude Code runtime ([a2a.md](a2a.md#on-claude-code)), Substrate can't fetch git or bucket plugin sources (its golden snapshot has no egress), so Landflow packs plugins into images it serves itself, from GitHub marketplaces only; the Harness image has only bash and git; and qwen3-coder through Ollama keeps calling its hand-in tool after the task is done. kagent compiles in Claude Code 2.1.285 and refuses any other version, so `landflow-claude-dev` runs the latest Claude Code behind a wrapper that answers `claude --version` with the pinned one. The landflow-harness mod ([a2a.md](a2a.md#the-landflow-harness-mod)) reports a Claude Code agent's real usage (in queue mode the main it posts to passes it on to the worker that made the call, and a batch for a worker that has gone is lost), only for new requests (an answer to a paused task is estimated), and only where the credential names a Plugin Registry and Landflow's access Role may write EgressPolicies (the mod reports through one of its own per agent); its guard is set per agent at deploy time (read-only, normal or report only; a request can only tighten it) and, in Normal mode, asks a person only about a push to main or master, a force push and deleting a remote branch (nothing else is askable, the answer is read by polling for up to 10 minutes, and an ask posted to a worker's trace that has gone is never answered until it times out), and its rules match command lines, so a script that does the same thing gets past them, read-only included. A node's live progress (`node.progress`, [a2a.md](a2a.md#the-a2a-agent-node)) is kept in memory: by the process that runs the execution and, in queue mode, by every main from the relayed events, so a main that starts mid-run shows a node's steps from its next report, and a tool sub-node that has not reported yet lights up only from its `node.started` event. The execution view's **Agent session** panel polls every 2 s (no push) and shows only sessions saved since the link was added; a running session is saved at most every 1.5 s, so the newest step can lag a moment. The **Run an Agent** node ([agents.md](agents.md#from-workflows)) refuses tools that need approval, since a workflow run has nobody to approve them, and runs every agent on Landflow's runtime, also one deployed to kagent (the A2A Agent node calls kagent, without the canvas's tools).
- **Second brain** ([second-brain.md](second-brain.md#limits)): Dead weight waits until the ledger reaches back 60 days, and the backfill only reaches as far as the executions and audit events on disk. In queue mode each process starts On Usage Event workflows for the events it recorded, so a batch holds one process's events. Ollama calls cost $0, so the AI-cost detector never suggests a smaller local model. The model writes fixes and drafts one at a time, so a study or detect run on a slow local model takes minutes (`POST /api/brain/run` waits). It proposes and never applies by itself. Custom event kinds have no UI and are shared by the instance; grouping by an attribute reads raw events (90 days). Entities are four fixed types with no relations of their own; the Brain page relates them only through the work that names them, matches work to pages by exact hints and emails, and its summaries and answers are only as good as the brain's model (a page's summary is written when it is first opened, not ahead of time). A button on a suggestion only records a decision unless a flow listens, and decisions are not retried. Slack mirroring is DMs only, started by Suggest Improvement, not retried. A declared metric is set on the nodes only. A flow backtest really runs every node of the flow once per point; only Suggest Improvement is neutralised, and Find Similar and facts ignore `asOf`. Ask a Person asks once per run, and email answers can't edit.
- **Eval gate** ([agents.md](agents.md#eval-gate)): standalone agents only (not teams, and not the AI Agent node). The check runs inside the publish request, one case after another, so a long list on a slow local model makes the publish wait (50 cases at most). Cases run with approvals denied, so a case that needs a tool's approval fails and scores 1. The judge is a model: scores wobble by a point between runs, which is why the rule allows a half-point drop. A version published before the gate existed has no baseline, so its first gated publish is held only by the 3 / 5 floor. Restore copies a version's config, not the knowledge documents or schedules' run state; a restored model that has since been removed fails at the next run.
- **Model router** ([agents.md](agents.md#model-router)): standalone agents only. The rule is length and tools, not meaning, so a short but hard question still goes to the cheap model (lower the character limit, or leave routing off for such agents). It chooses once per run, not per turn, and sends no tier header to a gateway: the cheap model is a plain model setting. Insights does not yet show what routing saved (the ledger prices each call by model, so the figure can be derived). The cheap model on another provider than the agent's needs its own credential for OpenAI; Anthropic and Ollama reuse the agent's or the default.
- **Prompt cache** ([agents.md](agents.md#prompt-cache)): Anthropic only, agents only, no switch. The breakpoints sit on the system prompt and the last tool, not on the conversation, so a long chat re-reads its history at the full price. A system prompt that changes every call (a clock or a memory note placed in it) never hits.
- **Response cache** ([agents.md](agents.md#response-cache)): exact match only (a reworded question misses), first message of a session only, and never for an agent with tools or cross-session memory. A system prompt that holds the time or other live text can serve an answer that was true when stored, so keep such agents' TTL short or the cache off. Agents deployed to kagent don't use it (kagent has no response cache either). The database adapter keeps answers in the host database, so an agent's answers are readable by anyone who can read it; don't cache answers to questions that carry personal data.
- **Tool access** ([agents.md](agents.md#tool-access)): standalone agents only (the AI Agent node and teams' tools are not filtered), decided once at the start of a run, so a role change mid-session applies from the next run. A role is known only for a person signed in to Landflow; callers from chat apps, schedules and workflows match on source or user id. The rule list has no groups and no tool-name patterns beyond `*`. The test panel ("what could this caller do?") builds the agent's tools, so an agent with an MCP server or an A2A agent contacts it to read its tools. The OPA and OpenFGA adapters were checked against a running OPA 1.22 and OpenFGA 1.18 (compose profiles and a Kubernetes example, [agents.md](agents.md#tool-access)), with the example policy and model as the only ones tried; the policy and the grants are yours to write, and the OpenFGA example keeps its store in memory. An *ask* tool in a run nobody can approve is refused.
- **Guardrails on agents** ([agents.md](agents.md#building-an-agent)): the *grounded* check judges an answer against what the agent's own knowledge bases returned in that run, not against the truth, so a wrong document grounds a wrong answer; it does not see passages from a vector store wired into a flow node's Tool port, and it is skipped for an agent with no knowledge base. The tool-result stage checks the text a tool returns, one call per result (model checks add a call each), and does not check a tool's error message or a sub-agent's reply.
- **Jev and Strands Decider as guardrail judges** ([agents.md](agents.md#building-an-agent)): they only answer yes/no questions here, so they are judges and not models an agent can chat with. Their probabilities are not calibrated (TypeSafe says to pick thresholds from your own examples). If it fails, the check fails closed; there is no fallback to the agent’s model. Their calls are not yet counted in Insights’ cost, the price table has no entry for them, and they do not yet answer the model router or the Guardrails node. Both were built from the published `systemone` shape and tested against a fake server, not a live Jev key or a running Strands server (running one downloads model weights, which has not been tried). Score and choice questions (and image input) are not used.
- **Layers checklist** ([agents.md](agents.md#layers)): it reads settings, not behaviour, so a layer shows as done when it is switched on, not when it works well (a guardrail with no checks still counts, an eval gate with one weak test case still counts). It is for standalone agents; teams and the AI Agent node have no checklist.
- **Not yet built from the "eight layers" comparison**: The **savings** are estimates (the price table, tokens as the model reported them, an average for cache answers) and count a whole session as routed once its first run was, so a long session that went back to the agent's own model overstates routing a little. The cache and routing numbers (a line on each card, and the Insights page's **Agent layers** card) are counted from the notices in each agent's newest 200 sessions, so older traffic and deleted sessions are not in them, and the card shows nothing until an agent has been asked something. The cache is shared by every caller of the agent (the key is the agent's config and the question, not who asked), so keep it off for an agent whose answers depend on who is asking. The **semantic cache** needs an Ollama embedding model (no OpenAI-compatible embeddings yet), compares a question with every stored one of the agent (at most 500) in the host, not in a vector index, and a wrong reuse is possible below a high threshold: keep it at 0.9 or more for answers that must be exact. The **LLM gateway** is an example (a compose profile and a Kubernetes manifest for a plain agentgateway), not wired into Settings: models are added in its config file, and kgateway's own AI Gateway is not used because it is deprecated ([roadmap.md](roadmap.md#eight-layers-around-a-model)).
- **Agent workspace and architect** ([agents.md](agents.md#agent-architect)): the Agent architect designs new agents only (not changes to an existing one), on the assistant's model with no picker, and a local model's drafts need checking (it may still pick odd tools). Agents and teams export as Claude Code plugins ([marketplace.md](marketplace.md#export-agents-as-plugins)), but schedules, channels, credentials and workflow tools stay behind, and Claude Code itself ignores Landflow's node, MCP and knowledge tools. A team template ([templates.md](templates.md)) holds one flow at most, makes a second slot for a credential the agents and the flow both use, drops a workflow tool that points outside the template, and copies a sub-agent only through the agents' tools and Run an Agent nodes (not through other flows). The built-in **Plugin builders** team template keeps its Claude Code members as A2A addresses of this machine's kagent (you point them at your own after using it) and the GitHub nodes' `your-org`/`your-repo` placeholders. Marketplace installs put their agents in the default project. A Missing tool suggestion's **Build it** starts the workflows that build the tool, but none ships yet: the agents and flow that write the plugin are in progress ([roadmap.md](roadmap.md#building-tools-from-suggestions-in-progress-2026-10-31)).
- **Network and toolchains on kagent** ([a2a.md](a2a.md#not-built)): the package EgressPolicy grants the package cache (`landflow-cache`: npm, Go, PyPI and Alpine, with no authentication) to every agent that references it, and `landflow-github` gives every agent that references it its token's whole reach. What an agent may push (its branch only, never main, no merges) is in its instructions, not enforced: scope the token to the repository and protect `main` with a branch rule. On `landflow-claude-dev`, Go's standard library is pre-built but a project's own packages compile on every session, and its dependencies are installed on every session (from the cache, so only the first fetch goes out). The image is loaded into Landflow's store by `claude-harness-dev.sh` (a script, not a page).
- **GitHub MCP tools for agents** ([a2a.md](a2a.md#githubs-mcp-tools-for-agents)): two access levels (read; read and review) over an allow-list of the pinned server's tools (github-mcp-server v2.0.2; a renamed tool in a later version is simply not offered until the list is updated); the token's repository scope is the only per-repository limit; a review comment is written to GitHub when the tool is called (approval is the only gate); the server runs in the OrbStack cluster only (no compose service) and takes the token from each request, which was checked against the image but not against GitHub with a real token.
- **GitHub plugin**: no delete (repositories, branches or files), no marking a draft pull request ready (GitHub's REST API can't; open it ready to merge it), no review or check-run operations, no GitHub App JWT flow (use an installation token) and no OAuth2 credential. Files: Commit adds or replaces regular files (mode 100644); it can't delete or chmod them, and it doesn't retry when the branch moved meanwhile (GitHub refuses the non-fast-forward update with 422; run it again). Its **GitHub** node shares a display name with Productivity's (`github.github` and `productivity.github`). **Compare** lists at most 300 files, with no patch for large or binary files.
- **Run Trace** ([run-trace.md](run-trace.md#not-built)): a Claude Code agent on kagent reports its usage, cost and guardrail stops through the landflow-harness mod, and its first 300 model requests per call are spans of their own; the OTLP export (`LANDFLOW_OTLP_TRACES_URL`) is JSON, sent once when a run ends, and Claude Code's own spans aren't joined by trace id yet; run search matches the stored text with `LIKE` (no ranking), reads at most 1,000 candidate runs a request and finds only runs that have a journal, and a run profile can't define measures over time of its own. **Content kept** is set per workflow, not per project. Claims come from a structured block or the profile's patterns, never from a model reading the reply. The checks see only what the journal recorded, so a tool that fails with exit code 0 passes. Models and memory sub-nodes can't report artifacts or checks. An agent's connections are what the flow and its published settings said when its span started, and a kagent agent's runtime is told from its deployment, not read from the cluster. A trace rebuilt for a run recorded before Run Trace has no progress notes, artifacts, checks or decisions. Code changes come from `Write`, `Edit` and `MultiEdit` steps only (not `sed -i` or a generator), a file over 32 KB (16,000 characters per argument from a remote agent) shows incomplete, a run recorded before 2026-10-31 shows most remote agents' files only from the branch, a run recorded before the same fix shows a flow's agent twice on the Team tab, and "pushed" is read from the agent's own `git add`/`commit`/`push`; line comments on diffs live in one browser (not shared, and they reach the agents only through a Run report's Send back), and an HTML page's own images, styles from other servers and scripts don't show in its preview. A delegating call without a `reason` still runs; members' words come only from text a later artifact follows; rounds start at the first node that ran again; fix cycles need a profile that names check commands, and their error counts are parsed from output text. A lead's claim about its team's work isn't credited with the team's steps, so it shows as a warning.
- **The new look** ([ui-review.md](ui-review.md#the-look)): a run's timeline names a step by a headline only when its team node kept one, else by a verb read from the member's title or role; members consulted by another member show as steps of their own in the order they started, so a long back-and-forth makes many steps (the card keeps the first and the latest). Run lines are read 20 runs at a time and only for runs with a journal. The analyst's chart draws a budget line only when a tool result carries a budget (none does yet), its numbers are per day or per group (the ledger has no per-run series), and it has no notebook source. Building step by step ticks a Spotlight proposal's steps on a short timer, since the proposal arrives whole; the Agent architect's dialog doesn't show steps. The team node's panel and idle node read the team's latest run anywhere (its workflow is named), not only this workflow's, and a team edited in another tab shows its old members until the editor reloads; **New team** opens the Agents page rather than making the team in place.
- **Agent teams** ([agent-teams.md](agent-teams.md)): only a Landflow agent can lead or manage (remote members are leaves). A reviewer's verdict is read from a `VERDICT:` line only (an approval in other words counts as asked, not approved), and a reviewer that manages the member it reviews isn't held to it. A remote agent that reports no usage (one without the landflow-harness mod) is budgeted on an estimate from what crossed the wire, a floor that stops it late; the lead and agent members are counted after each model call, but a remote member's usage counts against its budget when its answer comes: what its mod reports mid-task only moves its bar. A tool that needs approval pauses a team run for a person, and so does a member's question, but only in a flow (elsewhere the tool is refused and the run ends in Needs a person); the tools of a Claude Code member on kagent are still refused. Only Landflow agent members can consult a peer or hand a task over (a remote member has no tools to do it with), a chain of consults stops after two, and the model decides when to consult. A manager's answer is checked for file names, commits, test counts and pull requests nothing gave it, not for results described in words, and it is sent back once (an answer that still names them stands, with a warn check). A model that ignores the send-back keeps its invented details: the local `qwen3-coder:30b` lead did, in the Tech Review flow. A person can pause a member and take over ([run-trace.md](run-trace.md#pause-and-take-over)), but the pause is held in the memory of the process running the execution (lost on a restart, and unreachable from another process in queue mode), an agent stops between steps rather than inside a model call, and a remote member can only be stopped and redirected (its cancelled task's work may be lost). **Ask this member again** goes through the lead, which is a model told to ask only that member. The approval card's **Edit** ([run-trace.md](run-trace.md#an-approval-with-its-evidence)) exists in the new look only (the API takes an edited `input` in both looks); Slack and email approvals, the agent test chat's approvals and the MCP gateway's can't be edited; the card's evidence is what the journal already holds (no notebook facts the member cited), and the "Edited by you" badge says "you" for whoever looks, with the person's email on hover.
- **Team notebook** ([team-notebook.md](team-notebook.md#not-built)): search by meaning needs Ollama's `nomic-embed-text`; without it search matches words only. A note is embedded once, so changing the model setting does not re-embed old notes. A note counts as from outside after any web or fetch tool in the same run, whether or not the author used what it read. A remote member's note shows on the canvas only when its A2A task reports the MCP call as a step. The open calls that bind a kagent member's notes to a run live in the memory of the process running the execution, so in queue mode a worker's runs are not seen by the main that serves the MCP request. Person actions follow the team's access, with no separate permission for verifying or promoting. kagent's own runtime lists note tools only after the agent is redeployed.
- **Local telemetry stack** ([deployment.md](deployment.md#telemetry-on-kubernetes)): `landflow-lgtm` keeps everything in an `emptyDir`, so a restart loses it. The dashboard's totals use `increase()`, which can't see the first increment of a new series: after a host restart the first run, approval or call of each kind isn't counted in the stat panels (traces and logs have every one).
- **By design**: a Respond to Webhook reply built from a secret is not redacted: redaction covers what is kept, and the reply is sent, not kept ([External secrets](features/secrets-and-environments.md)).

## Production profile (2026-11)

- **The production check does not run yet**: `checkConfig()` reports development secrets and a missing public URL in the
  production profile, but nothing calls it at boot until a later backend-hardening package. Auth cookie and guard code still
  read `LANDFLOW_PUBLIC_URL` themselves.

## Security headers (2026-11)

- API responses carry no CSP; page styles allow `'unsafe-inline'` (Tailwind, React style props).
- There is no `report-uri` or `report-to`: report mode is visible only in the browser console.
- `img-src` allows any https image (markdown images, plugin icons), so image loads are not restricted by origin.

## Browser plugin and retry backoff (built 2026-11-07)

- **Browser** ([plugins/browser](../plugins/browser/README.md)) needs the `agent-browser` CLI and its Chrome on the machine that runs the plugin; it is not in `dev:all`, the compose files or the cluster images. It reads pages and runs listed steps, with no free-form scripting, uploads or downloads, and no signed-in browsing (the CLI refuses saved profiles with an allow-list). The allow-list stops the browser reaching other sites; it can't stop a page from carrying instructions to a model, so page text is fenced and cut but should still be treated as untrusted. A screenshot over 64 KiB needs a host that serves the binary store. It was checked against the real CLI on `example.com` for reading, and on a locally served form, not against a login flow, a slow page or a long run.
- **Retry backoff** doubles the wait after each failed try (up to a minute, no jitter) and applies to node retries only; the whole-run retry already backs off. Composite frames keep the wait and the backoff as well as `maxTries`; n8n has no backoff setting, so an import is always fixed-wait. A node that ran when the process stopped still runs again after recovery, so a plugin must honour the per-step idempotency key.
- **Spotlight and the Browser node** (checked 2026-11-07, building a seven-node flow that fills a form): Spotlight guessed the Browser node's output field and step names until the node declared its `outputSchema` and accepted aliases; it now reads the schema, but a small local builder model still mis-wired a flow once (an extra node from the true branch into the rejection) and once announced proposal cards that never appeared, so check a built flow's connections. The instance MCP server now returns `outputSchema` from `get_node_type` and `validate_workflow` checks field reads (see below).

## Debugging, chat with agents, Browser and Web Search (built 2026-11-07)

- **Debugging over the instance MCP server**: the expression field check reads only the top-level fields of what a node writes, from its `outputSchema` or the last five runs, so a field that appears only in some runs, or after the workflow changed, can raise a warning that does not apply. It covers JavaScript Code nodes and `{{ }}` expressions, not Python code or computed keys. `run_node` runs one node on the input you pin: `$('Other node')` reads nothing unless `fromExecution` is given. `get_plugin_logs` has nothing for plugins started with `LANDFLOW_PLUGINS`; only marketplace-installed node plugins keep logs.
- **CLI debugging** ([features/cli.md](features/cli.md)): `landflow replay` does not start a scratch host: it needs `--target` (another host with its own data directory) and prints the steps without it. It restores no credentials or `$vars` (the bundle holds none) and pins only recorded outputs of nodes before the failed node; nodes after the pins run for real, so side effects need a scratch host with fakes. It does not run a remote plugin build. `debug-bundle` reads through the MCP server with the CLI's key: a host with MCP off, or a key the MCP server does not accept, lists explain_failure, trace, node types and plugin logs as skipped (the REST parts are still written), and plugin logs need an instance admin. Redaction is by key name, known `$vars` values, bearer tokens and `"secret": "..."` pairs inside JSON text: a secret in free text under an ordinary key is not found. `claude init` writes a `${LANDFLOW_API_KEY}` reference, so the key must be in Claude Code's environment and be one the MCP endpoint accepts (instance access token, MCP token, API key). The debug token (W1c) is built; see the bullets below.
- **Chat with agents** ([features/ai.md](features/ai.md#hosted-chat-and-widget)): Run an Agent labels its chunks with the agent's id, name and avatar; Run a Team with the team's id and name (one label per team node, not per member). The AI Agent, chains and other nodes stay unlabelled. The chat route stores `agentKey` / `agentName` from the last labelled text chunk, so only Streaming Response Mode stores them (a "When Last Node Finishes" chat has no chunks). Agent faces are avatar objects; the page shows an image avatar, initials, or a letter on the face's skin tone, not the drawn face.
- **The roster and Guardrails**: a picked agent's run starts at its own node unless the flow routes to it, in which case it starts at the trigger and passes the flow's Guardrails (connect the trigger through Guardrails to a Switch or If on `agentKey`; the "Chat with a team" template does). The rule applies when a node between the trigger and the target reads `agentKey` (found by looking for the word in its parameters); a flow that routes some other way starts the target directly, and the nodes before it do not run. Validation warns on a public chat whose roster target can skip Guardrails, but a flow with a roster and no Guardrails node gets no warning. Per-agent memory works where the target reads its session key from `$json.sessionId` (the default of Run an Agent and the AI Agent): a key typed as a fixed string, or read from the trigger node by name, is not changed, but validation and the trigger panel now warn about it.
- **Voice**: browser speech only: recognition quality, languages and privacy are the browser's (Chrome sends audio to its vendor; Firefox has no `SpeechRecognition`; iOS Safari support is partial), and there is no local speech service yet (a later `/chat/<key>/transcribe`). Replies are read sentence by sentence as they stream (a sentence needs the white space after its full stop, so abbreviations such as "e.g." can split one); switching the speaker on mid-reply reads from the start of that reply; the toggle is remembered per chat in localStorage. Hold-to-talk only; no hands-free or wake word. Markdown is read as text (no table or list announcements). Push-to-talk is ignored while a reply is being written.
- **Browser node steps**: `results` hold unfenced page text (the CLI's boundary marker is removed from `getText` values), so an agent that reads `results` must treat them as untrusted; there is no option yet to keep the fence on them. A failed step stops the node, so the per-step list (`steps`) reaches the output only when every step succeeded; on failure the step is named in the error. Extract Attribute in the builder takes `name:attribute` in one text field.
- **Browser packaging**: the Browser image is built and run on arm64 only; amd64 is verified for the install step only (a Debian probe container), not the whole image. arm64 uses Debian's chromium (156) and amd64 Chrome for Testing (157 at agent-browser 0.41.2). Chrome still runs with `--no-sandbox` inside the container; Web Search needs a SearXNG URL or an API key credential before it returns anything; headed mode is desktop only; an empty `LANDFLOW_BROWSER_ALLOWED_DOMAINS` leaves each node to its own list.
- **Spotlight collections and agent wiring** ([assistant.md](assistant.md#the-builder-chat)): the option-value check covers `options` values written as plain text; expressions and dynamically loaded options are not checked. The agent-wiring warning flags every new tool-capable node placed after an agent as a normal step, including legitimate ones such as Slack, and each such proposal costs one extra round trip because it is sent back once. A builder model that is told a shape can still omit a step the user asked for (on the local model the first reply skipped an Extract step; a follow-up added it with the right `getText` action). Naming a model the editor doesn't know ("qwen3.8") is handled only in the prompt (say so), not checked in code.
- **Spotlight and agents** ([assistant.md](assistant.md#agents-and-teams)): it reads at most 30 published agents and 30 teams, chosen by the model from one line each, not by search; a new agent's design is a local model's: it may pick a tool it doesn't need or miss one, a new knowledge base starts empty (a person adds the documents), and a credential its tools need is the person's to pick; the first-draft builder never proposes a new agent.
- **Spotlight autonomous mode** ([assistant.md](assistant.md#autonomous-mode)): the switch is per browser, not per user or workflow; test runs execute every step for real once you say **Run it for real**, and that yes lasts while the page is open; which steps send is read from the HTTP method and the operation's name, so a step that writes without such an operation isn't asked about; an agent Spotlight creates is published without a person's click. *Needs you* reads credential problems from the error's words ("credential", 401/403, `invalid_auth`), not from an error code.
- **Landflow on a phone** ([mobile.md](mobile.md)): the tab bar, app bar, Executions cards, Filters sheets, tap-to-open and the full-screen node editor are in, and the editor opens on the Steps view; menus and dialogs are sheets or full screen. On a desktop, menus and dialogs (other than the Run Trace's) don't keep Tab inside them, and confirmations are the browser's own. The Steps view can't reorder or connect steps (use the canvas), adds only after the last step that doesn't go on yet, and doesn't show Spotlight's chips (*Fixing…*, *Needs you*); notes and groups appear only on the canvas. In the node editor on a phone the **{}** picker lists the input's fields only (not other steps' outputs, `$vars` or functions; type those), and the plugin's Docs link isn't offered (see [What's next](mobile.md#whats-next)). On a phone, a header's main action is its last one, whatever the page meant. An agent's page keeps the desktop's tab strip (it scrolls sideways). The More drawer is the desktop rail, so its targets are 36 px. The Workflows and Credentials lists keep their filters in place,.
- **Spotlight's panel** ([assistant.md](assistant.md#the-spotlight-panel)): the column is a fixed 360 px (no resizing), and the folded state is per browser. On a phone the open sheet hides the run logs (fold it to see them), the minimap is hidden, and the three heights are moved by dragging the header (the chevron reaches the bar and half only, so peek needs a drag). A fix bubble sits above its node and can cover the node above it in a dense flow; it closes after a minute even when you haven't read it (the timeline keeps the text), and ⌘Z of the fix doesn't close it. Fit-to-view runs only while Spotlight drafts or tests. Drafting a flow is one request, so the header counts seconds rather than naming stages, and ■ only stops the editor from waiting: the server finishes the model call it started. **Undo all fixes** is offered only until the flow changes after the session stops; after that, each fix's own row (the newest has Undo) or ⌘Z is the way back. The suggestion bubbles aren't announced as you move through them with the arrow keys (no combobox roles), and the header's buttons are 28 px.
- **Spotlight reliability** ([assistant.md](assistant.md#the-builder-chat)): the purpose check is a heuristic (shaping nodes only, with a sibling); the swallowed-error check reads code by regex.
- **Web Search** ([web-search.md](web-search.md)): it returns snippets only; it does not read pages (use the Browser node) and has no image, news or answer modes. The per-run search limit counts in the plugin process's memory: it resets when the plugin restarts and is per process when the plugin runs several replicas. Recency is day, week, month or year; SearXNG engines that ignore `time_range` return unfiltered results. The deny-list is operator-wide through an environment variable; there is no per-agent allow-list for search yet. Result text is untrusted web text: the node strips markup but cannot stop prompt injection in the words themselves.
- **Debug tokens** ([specs/19-debug-token.md](specs/19-debug-token.md)): the redaction is the debugging tools' one (credential values of the workflow's nodes, `$vars`, external secrets and secret-named keys); a secret that sits only in free text under an ordinary key is not found, and run data is still the user's data, so a token is not safe to publish. Tokens work at `/api/mcp` on the host itself, not through the bundled gateway and not at `/api/mcp/projects/<id>`. `landflow debug-bundle` needs the person's key (its REST half is refused with a debug token). Tokens are minted, listed and revoked from the Debug access button on the Run Trace page (one run at a time), REST or `landflow debug-token`; there is no instance-wide list of tokens in Settings, and no button on the classic execution detail page; dead tokens are purged on the next mint after a week. The one-node local override is not built (a design sketch is in the spec).
- **Images in tool results**: Run Trace shows an image only while the stored file exists (an execution's images go with the execution, a chat's with its session). A run from a flow uses the node's **Tool Images to Keep** over the agent's setting; a Run a Team's members use their own agent's setting, not the node's. Vision is decided by model name (an Ollama allow-list, an OpenAI-compatible deny-list); an unknown local name needs **Send Tool Images: Always**. sharp (0.35.5, exact, a direct dependency of apps/web) is native; where it can't load, only the 4 MB limit applies.
- **Spec cards (json-render)** ([research/json-render-verdict.md](research/json-render-verdict.md)): a prototype behind a setting (Settings → General, owner only; `LANDFLOW_JSON_RENDER=1` is its default). No agent produces specs, and the Approval card only names an approval and cannot decide it.
- **AI SDK plugin** ([research/ai-sdk-verdict.md](research/ai-sdk-verdict.md)): the node reports each call to the host, which counts it in AI usage and the caps and shows a `model` span in Run Trace. Only remote plugin nodes are wrapped for model records; an in-process node's `ctx.model` goes through `onRecord` and shows in Run Trace but is not metered (none exists). The plugin's own `@ai-sdk/otel` spans still reach only an OTLP backend.
- **Agent Shell is a simulated bash** ([research/just-bash-verdict.md](research/just-bash-verdict.md)): about 85 commands; no git, zip, perl, bc, uname, id or any real binary; `seq` stops at 10,000 and a loop at 10,000 commands. No network, Python or Node. Text files only. Shell state (cwd, variables) does not carry between calls, only files do, and only with Keep Files for the Run.
- **Agent Shell's isolation is in-process**: just-bash is a library inside the plugin's Node process (beta by its own README), not a VM. Run the plugin in a container, not on a host that holds secrets. It has no image or deploy entry yet.
- **Dropped: a capped deepsec scan** (W5d): the user dropped it, since there is no API key (local Ollama only).

## Integrations that report activity (built 2026-11-12)

- **Activity items** ([protocol.md §16](protocol.md#16-activity-items)) are a shape, not a pipeline: a flow records them (Record Event, Entity). `kind` is a suggestion each integration makes (`work.discussion`, `work.doc_edited`, `work.meeting_*`); the hints come from names (Slack channel prefixes, Drive folders and Notion ancestors called `Customers` / `Projects`, a shared drive's name, an attendee's domain), not from the vendor's own team model.
- **Slack** ([plugins/messaging](../plugins/messaging/README.md#slack-activity)): a bot reads only channels it is a member of (Get Many Since logs and skips the others). An app distributed outside Slack's Marketplace and installed after 29 May 2025 gets 1 history call a minute and 15 messages a call; an app the workspace creates for itself is exempt. Slack has no API to subscribe to events, so the Slack Activity Trigger's URL is pasted into the Slack app by hand. Edits and deletions are not output.
- **Google Drive and Calendar** ([plugins/google-workspace](../plugins/google-workspace/README.md#activity-items)) poll (every 5 minutes by default): their push channels expire within a week and Landflow's app webhooks have no renewal step. A Drive poll reads at most 20 pages of 1,000 changes (the rest at the next poll); a Doc's summary costs one export per changed Doc. A Calendar sync token that Google expires (410) takes a new baseline: the changes in between are not output. One Calendar Trigger watches one calendar.
- **Google Directory** reads users only (no groups or org units), and a service account must impersonate an admin with the directory scope delegated.
- **Notion** ([plugins/productivity](../plugins/productivity/README.md#notion-activity)) polls search, which lags behind edits: the trigger looks back 5 minutes and queries root databases directly, but a page outside a root database that reaches the index later than that is missed. Teamspaces are not in Notion's API, so `teamHint` stays empty; page text in a summary is the first 40 blocks; a deleted page is not output. Notion's webhooks are created by hand in its settings and carry ids only, so there is no Notion webhook trigger.
- **Linear** ([plugins/linear](../plugins/linear/README.md#limits)) lists newest first only, so Get Many Changed Since reads
  every page after Since and sorts (5,000 at most); a poll's `actorEmail` is the creator (Linear's reads don't say who
  edited), the trigger's is the real actor; creating the webhook needs an admin key or the `admin` scope; the Issue and
  Project Update payload shapes aren't documented, so the mapper fills hints from the API.
- **Attio** ([plugins/attio](../plugins/attio/README.md#limits)) has no "updated at": **Any Value Changed** scans every
  row (5,000 at most) for the newest value change, **Stage Changed** and **Created** filter on the server; events carry
  no time or diff; webhooks need HTTPS and a workspace token, and their secret is shown once, so republishing makes a
  new webhook.
- **Fathom** ([plugins/fathom](../plugins/fathom/README.md#limits-and-gaps)) has no get-by-id (Meeting → Get scans the
  list) and no documented order (the list is read and sorted); no OAuth2 credential (its authorize URL isn't documented
  and OAuth apps can't read summaries or transcripts); users are admin only. Transcripts are off unless asked.
- **Work ingest templates** ([integrations.md](features/integrations.md#work-ingest-templates)) keep customers and
  initiatives by the hint's name: `#customer-acme` and a Drive folder `Customers/Acme` meet as `acme`, but the Calendar
  and Fathom name a customer by the attendee's domain (`globex.com`), which joins nothing else until someone merges them. The
  person who did the work is the event's `actor` (an email), not an entity; the Directory template makes the people.
  Record Event keeps 200 characters of a string attribute, so the 600-character summary is cut in the ledger.
  Installing Linear, Attio or Fathom from the repository's marketplace on an instance that already runs it (`dev:all`,
  compose) starts a second copy under the same plugin id and lists its template twice (built-in and installed); install
  from the marketplace only where the plugin isn't bundled.
- **Checked against fakes only**: Slack, Google, Notion, Linear, Attio and Fathom activity were tested against local fakes of their APIs, not a real workspace.
- **Postgres mode and a rejected write** ([features/postgres-write-queue.md](features/postgres-write-queue.md)): a batch Postgres keeps rejecting (not a connection failure) blocks the store: it refuses every write (a `StoreUnavailableError` with status 503; route responses are 500/400 with its message until `handler()` maps the status) until the batch applies on a retry or the host restarts with `LANDFLOW_PG_SKIP_BATCH`. Reads keep working. The spool is fsynced at most every 100 ms by default, so a power cut can lose the last 100 ms of writes not yet in Postgres.

## Graceful shutdown (backend hardening, 2026-11)

- **`next dev`** keeps Next.js's own signal handling: the host's phased shutdown (flush, lease release) runs only where `NEXT_MANUAL_SIG_HANDLE=true` (`pnpm start`, the Docker image). Without it only the error handlers are ours.
- **Streams**: in manual mode in-flight requests are awaited, but SSE streams are not; they end when the process exits.

## Execution retention (backend hardening, 2026-11)

- **The cap can be exceeded between passes**: a finished run prunes only every `LANDFLOW_RETENTION_EVERY` runs (default
  50), so up to that many minus one finished executions above the saved maximum can be stored until the next pass (the
  hourly timer and **Prune now** prune regardless).

## Access scope of AI usage and files (2026-11)

- **Files with no execution** aren't project-scoped: an editor upload that no run has used yet, an agent's knowledge file,
  a chat upload, a file scoped to an agent run and the like have no saved or running execution or workflow to derive an
  owner from, so any signed-in caller who knows the id (random,
  unguessable) can read them. Files of executions and of evaluation datasets are checked against the workflow's project.
- **AI usage rows with no workflow or agent** (a model call outside both) are visible to owners and admins only.
- **Readiness in Postgres mode**: the `database` check runs on the in-process copy, so it cannot see Postgres go away; loss shows as `writeQueue` lag after `LANDFLOW_READY_MAX_WRITE_LAG_SECONDS` once a write is queued, a host with no pending write stays ready, and the LISTEN connection is not checked. No probe answers before boot ends, because Next holds requests until instrumentation finishes.
- **Plugin registration** ([plugins.md](plugins.md#registration-rules)): the production profile needs `LANDFLOW_REGISTRY_SECRET` on the host and every announcing plugin (or `LANDFLOW_REGISTRY_OPEN=true`). Without a secret the development registry accepts any endpoint it can reach; the full outbound address policy (beyond refusing link-local and metadata addresses) comes later.
- **Outbound address policy** ([audit-and-governance.md](features/audit-and-governance.md#outbound-requests)): `safeFetch` covers the HTTP Request node (and other in-process nodes' `ctx.http`), alert channels, HTTP SIEM destinations, remote MCP servers, RAG embeddings and rerank, and OIDC and SAML metadata. Not covered: remote plugins (their own processes, trusted through the registry secret), Postgres, Valkey, S3 and the broker clients (configured infrastructure), syslog destinations (a raw socket to a configured host), the marketplace's git (runs the git binary), the OAuth2 token flow (`credentials/oauth2-flow.ts`), audit anchoring webhooks, Slack, the A2A client, templates fetched from a URL and the Ollama model nodes' own calls: each is a follow-up. A production host that calls internal services must list them in `LANDFLOW_OUTBOUND_ALLOW`. Proxies from the environment (`HTTP_PROXY`) are not used for guarded calls.
