# Known limitations

What Landflow does not do yet, or does only partly. [roadmap.md](roadmap.md) records what each wave built and the
items still open (its "Wave 6" section); this page is the short list to check before relying on a feature.

- **Isolation**: expressions run in a sealed `node:vm` realm (no host object is reachable, code generation is off, 250 ms timeout; see [features/engine.md](features/engine.md#expressions-run-in-a-sealed-realm)). It is not a hard boundary against a V8 bug, and an expression can still use memory inside its 250 ms window. `LANDFLOW_EXPRESSION_SANDBOX=isolate` ([engine.md](features/engine.md#the-isolate-backend-optional)) runs expressions in an isolated-vm isolate with a memory cap, but it is off by default, needs the optional `isolated-vm` addon and `NODE_OPTIONS=--no-node-snapshot` in every process, and the cap exists only there. Inside it, V8 aborts the process on one allocation larger than the heap, so the builtins known to allocate from a caller's length (`Array.from`, `fill`, `join`, `repeat`, `padStart`, `padEnd`) are guarded; the list cannot be proven complete, and it refuses sizes the realm allows (`new Array(3e6).fill(0)` at 64 MB). It also aborts the process on ordinary hash-table growth (a `Set`/`Map` insert loop, sparse object keys, `Object.groupBy` over millions of items) at the default cap, where the realm survives (its 250 ms timeout ends the loop), so `isolate` is not a defence against a memory bomb taking a worker down. And the cap does not bound the process: one builtin call can take 0.5 to 2 GB resident at 64 MB before the heap limit is checked (details in [engine.md](features/engine.md#the-isolate-backend-optional)); a separate evaluation process would close both and is not built. In-process Code nodes are not sealed (their context holds host helpers): they are for trusted workflows, and the production profile runs Code nodes in the code runner unless `LANDFLOW_CODE_IN_PROCESS=true` is set knowingly. Code you don't trust belongs in the code runner's container (see [deployment.md](deployment.md#code-runner)); started with pnpm, the runner only has OS limits.
- **Expressions have no async**: `async`, `await`, `Promise`, `FinalizationRegistry`, `WeakRef`, `AsyncDisposableStack` and `import()` are not available in an expression (a rejected promise in any realm would end the host process); use the Code node.
- **Scaling out**: [queue mode](features/engine.md#queue-mode-workers-and-high-availability) runs several mains and workers, but every process keeps its in-memory copy of the database (Postgres mode: everything but the data and journal of runs older than `LANDFLOW_PG_HOT_MINUTES`, so the audit log, usage ledger, insights rows, AI usage and the other tables still grow its memory; at 50,000 runs the run data was 14 GB in memory before and is out of it now, [deployment.md](deployment.md#postgres-memory-sizing)), Valkey Sentinel and Valkey Cluster give failover but not scale-out (every queue key shares one hash tag, so the queue lives on one node), and with `LANDFLOW_CONFIG_STORE=files` the files in the shared data directory are last-writer-wins. Checkpoints add a write per node run (Postgres mode also appends it to the spool). The SQL Data Tables storage still caches a table's rows in memory when it is used (50,000 rows per table).
- **Old runs in Postgres mode**: a finished run older than `LANDFLOW_PG_HOT_MINUTES` has its record and journal in Postgres only ([architecture](architecture.md#storage)): opening it, listing its events and searching runs cost a query to Postgres, a search waits up to two seconds for the host's own queued writes and otherwise scans the in-memory copy (cold runs missing, a warning in the log; for five seconds after such a timeout the next scans go to the copy at once, so a paged search does not wait per page), and a scan runs on Postgres, whose `LIKE` is case sensitive where SQLite's is not (run search already lowers both sides; `executionsMentioningAsync` matches ids, which are lower case). The synchronous `store.getExecution` and `lastSeq` see a cold run as empty (`getExecution` finds no data, `lastSeq` says 1, `append` refuses it): the routes that retry, rerun or replay an old run, and the webhook replay, load it back first (`promoteExecution`), and an automatic retry or a waiting parent keeps its run hot. A journal rebuilt for a run recorded before Run Trace is not rebuilt for a cold one, and a queue-mode process that reloads its copy after losing its LISTEN connection drops what it had loaded back for a decision. The chat feedback, form waiting, run and execute duplicate, stop and approval handlers load a finished run on demand, so they answer for a cold run as for a hot one. What still reads synchronously is the resume lookups of runs in flight (`form-test`, `/api/waiting`, the webhook replay) and `lastRunFields`, which feeds the "last run" field hints of `validateWorkflow` (a sync function): it sees only runs from the last `LANDFLOW_PG_HOT_MINUTES`, so a workflow that has not run lately is checked against declared output schemas only. The search for a team id (`executionsMentioningAsync`) is a `LIKE` over the whole history in Postgres, a full scan when nothing matches. A queue-mode reload takes one cutoff for all tables, but the selects are not one snapshot: a run that cools or finishes between them can show data without events until the next eviction pass.
- **Sign-in**: without queue mode, sign-in rate limits and edit locks live in the host's memory (a restart clears them; in queue mode the limits are shared through Valkey and every main keeps the locks in step). Per-IP limits, audit addresses and webhook IP allow-lists use the address `LANDFLOW_TRUSTED_PROXIES` says to trust (default 0: the last `X-Forwarded-For` entry, which a client that reaches the host directly can still forge); behind a proxy, set the hop count. Harnesses that don't load MCP prompts when a session starts need the Claude Code mod or a manual `/morning-briefing`; `my_briefing` and `record_work` need a person, so the instance access token gets an error from them. The instance MCP server is scoped to a project only through a project URL or a project token (the unscoped one sees what its user sees).
- **Connect your harness**: the instance MCP server is off by default and only an owner or admin can switch it on (Settings → MCP), so a member's setup on `/connect` works once an admin has; Test connection says so when it fails. The page does not know the switch's state until then. A key made on the page keeps its scopes and label: change the ticks and you need a new key, though the snippets keep showing the old one.
- **Bounds on requests**: a JSON body over `LANDFLOW_MAX_BODY_BYTES` (16 MiB) is refused with 413, so a very large import needs the variable raised. `GET /api/executions` pages by cursor and lists the live runs on the first page only. The API rate limits (`LANDFLOW_RATE_LIMIT_API`, `LANDFLOW_RATE_LIMIT_PUBLIC`) are fixed one-minute windows, off in the development profile; without queue mode each process counts alone, and per-address limits follow `LANDFLOW_TRUSTED_PROXIES`. A request with no credential is limited only on the five public trigger groups (`/api/webhook`, `/form`, `/chat`, `/mcp`, `/api/waiting`): the instance MCP server at `/api/mcp`, the Slack and Teams endpoints, SCIM, `/api/agent-trace` and the test URLs (`/api/webhook-test`, `/form-test`, `/mcp-test`) are not, though `/api/mcp` and the chat channels can start model calls.
- **Integrations are tested against fakes**: every plugin's tests use local fakes of the service. The databases plugin is the exception: its integration tests run the Postgres, Postgres Trigger, Redis and MySQL nodes against the infra stack's real servers ([deployment.md](deployment.md#integration-tests-databases-plugin)). Switch and Text Classifier have a fixed set of outputs (4 plus a fallback): ports can be shown or hidden by parameters, but not repeated per rule. Stripe, Slack, GitHub and Microsoft Teams were checked against local fakes only, and Slack's Events URL is pasted into the Slack app by hand.
- **Not yet built**: webhook-based triggers for apps other than GitHub, Stripe and Slack (the others poll; the protocol and SDK signature helpers are ready, [protocol.md §12](protocol.md#12-app-webhook-triggers)), remote model/memory providers over the protocol (tools already work remotely), mDNS discovery, n8n v3-style engine-driven agent steps, file uploads in a standalone agent's test chat, and MCP subscriptions (they need a 2026-07-28 client). Telegram, WhatsApp Cloud, Twilio, SMTP and the databases have no OAuth2, so their credentials take tokens or passwords.
- **A plugin trigger runs only as `poll` or `appWebhook`**: the SDKs and the protocol accept the sources `webhook`, `schedule`, `chat` and `manual` on a node descriptor, but the host schedules only `poll` triggers (`apps/web/src/lib/server/poller.ts`) and registers webhooks only for `appWebhook` triggers (`apps/web/src/lib/server/app-webhooks.ts`). A plugin trigger with the source `webhook` or `schedule` is listed but never started by the host; use a core trigger node (Webhook, Schedule) in front of the plugin's action instead. `manual` and `chat` plugin triggers do run, but only by hand: Execute, the run API and MCP tools start the first `manual` trigger, and the editor chat the `chat` one (`findTrigger()` in `apps/web/src/lib/server/runner/run.ts`); nothing fires them on its own.
- **Alert triage and Landfall** ([triage.md](triage.md)): the Landfall node and trigger were built from Landfall's API and checked against a local fake (`pnpm fake-landfall`), not a live Landfall; the same goes for the seven threat intel services, tested against `httptest` fakes. The Landfall Trigger polls. Triage's quality depends on the model and the rules; that is why it starts in Shadow mode. Runbooks from closed rooms ([runbooks.md](runbooks.md#not-built)) are folded by fixed rules from a room you paste or pass in, into form-wait steps for people, not generated action nodes; nothing makes one by itself when a room ends, and the folding was checked against fixtures, not a live Landfall. Flow share pages need a signed-in member of the instance; they aren't public links.
- **Deployment and the gateway**: the KEDA worker example (`deploy/k8s/examples/keda`) has not been applied, since KEDA is not installed on the local cluster. With the identity provider accepted on a gateway route (`components/gateway-landflow-tokens-idp`), the gateway's own 401 carries no `WWW-Authenticate` challenge.
- **Queue-mode workers on the OrbStack overlay get less than the host**: `deploy/k8s/overlays/orbstack-queue` adds `components/queue-mode`, whose `landflow-worker` has no `LANDFLOW_CODE_RUNNER_URL` and `LANDFLOW_CODE_RUNNER_SECRET`, no `LANDFLOW_SMTP_*` and no `LANDFLOW_LLM_GATEWAY_URL` or key. Only the host Deployment gets them, from `overlays/orbstack/kustomization.yaml`. A run that a worker takes and that holds a Code node, a Send Email node or a gateway-priced model call has none of them. Copy the host's env block onto the worker in your own overlay until the queue overlay does it ([platform/kubernetes.md](platform/kubernetes.md)).
- **Prompt parts**: what a call's split cannot tell, and which calls have none, is under [Token spend: what it cannot do yet](#token-spend-what-it-cannot-do-yet).
- **The model Spotlight uses** ([assistant.md](assistant.md#the-model-spotlight-uses)): the header's pick is per tab and conversation, not per person or workflow (a reload goes back to the Settings default, which is one for the whole instance); a phone has no picker and uses the default; the Agent architect's dialog has none either. The list is the server's (Ollama, the gateway, the server's own `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`): a model reachable only through a member's own credential cannot be picked. The Ollama adapter caps one model call at 300 s (it is shared by every Ollama call), so a first draft whose single reply takes longer than that fails even though `LANDFLOW_BUILDER_TIMEOUT_SECONDS` (600 s) bounds the whole build (the builder says so: *did not finish the draft within 300 s (the Ollama adapter's cap …)*, and suggests a faster or other model). The brain writer's drafts and its fix enrichment are metered now too (AI usage purpose `answer`) and the same 300 s cap applies to them.
- **Dictation in Spotlight** ([assistant.md](assistant.md#spotlight)): push-to-talk only, in the editor's Spotlight; the text goes into the box to edit, and replies are not spoken. No speech-to-text server ships with Landflow: `LANDFLOW_STT_URL` must point at an OpenAI-compatible one (nothing listens on the default `http://127.0.0.1:8000/v1` until you start one), and recordings are cut at two minutes or 10 MB. Safari and Firefox record in formats some servers reject. Checked live in Chrome against a local speaches server with a stubbed `getUserMedia` (a spoken clip played into the real `MediaRecorder`), not with a real microphone.
- **Spotlight's timeline** ([assistant.md](assistant.md#spotlight)): `ChatList` re-pins to the bottom when its content resizes, not when the scroll area shrinks (the bubbles row appearing, a dock height), so the newest row can sit a few pixels under the edge until the next reply or a scroll. The step trace counts rows while the reply's footer counts model calls, so the two numbers can differ. Stopping a reply, or an error, in the middle of a step leaves that step's unchecked words as the reply.
- **Spotlight on the local model**: the staged first draft (plan, then build) works on `qwen3-coder:30b` and was checked once on a picked model (decision D4): the B1 ask with `litellm/qwen3-coder:30b` picked, on the development profile through the local gateway, planned 7 steps and built a draft whose `model` names `litellm/qwen3-coder:30b`, the gateway's log counting 4 chat calls (plan and its send-back, build and its send-back); no other picked model, and no hosted one, was tried. `qwen3-coder:30b` doesn't always follow the brevity rule (it may still write a numbered list). The guards against "it has been added" and made-up values match common wordings, id-like and destination-like parameter names (`channel`, `table`, `owner`, `email`, `url` …) and a URL's host, and a URL's literal host even when an expression follows it, but not a value under another name ([assistant.md](assistant.md#the-builder-chat)) and not every case, so a proposal card is still the thing to read before Apply. A change is checked against what the step receives ([assistant.md](assistant.md#the-builder-chat)): retries are in range and on, an expression reads a field the input has, a schedule parses and names the days asked, an Authorization header is never read from the data. The expression check sees only a field that a run sample, pinned data or an output schema names, so a step never run, with no pin and no schema, is not checked; it reads `$json.a.b` and `$('Step').item.json.a.b` and no other form (`$input`, `$node[...]`, code in a Code node), and a sample is the first 3 items clipped, so a field only a later item has can be named as missing; a step that only passes its input through is not marked stale when the proposal edits the step before it, so its run sample can be one hop out of date. [Test and fix](assistant.md#test-and-fix) leans on the same model: a first draft is checked and sent back once for empty If conditions, Set fields, Switch rules, schedule rules and table columns, but a model that leaves them empty a second time still gives a draft with them empty (listed with the draft as left); built from a plan, each step is sent back alone ([assistant.md](assistant.md#each-steps-parameters)), and a step still wrong after its one send-back is listed the same way, and a fix can take a few rounds or run out at 4 (one trial spent all 4 on an Aggregate node's fields). The same prompt can pass in one session and fail in the next. Its checks are structural (a node failed, nothing reached the end, a step with no conditions or fields) plus the model's own reading of the output against the goal (a pass after a fix is reviewed again, and a session never publishes after removing a step the flow started with), so the review is the model's judgement and a run it calls ready is still worth a look before publishing; the person's yes to a test that sends is per destination, and a destination is a scheme, a host and its port, so `https://x` and `http://x` ask apart (a yes kept as a bare `host:port` covers `http` only; an app step's destination is its type and operation, with no scheme), but a destination the host builds from an expression (`{{ … }}`) is one yes for all it may resolve to, asked again before every run (and never kept), and a URL with a backslash or one that does not parse counts as such an expression. `givenKept` (a fix may not change a URL, address, channel or id the person gave) reads only top-level string parameters of a step, so a value inside a collection (a header, a row) can still be changed by a fix, and one the person wrote differently from the step's value (a URL without its scheme, say) is not recognised. A proposal still waiting is matched by node type and name, so the same job under another name isn't recognised, and the same goes for a node added back after a pending proposal removed it (a summary first done by a Basic LLM Chain and then by a Code node gets through; a node the latest message asks to add by that name, "remove Check and add a new Check after Code", is let through); the check against an If or Filter after a node that already branches looks only at nodes added or connected without an explicit output; Code nodes have no usable `$runIndex`, so a round counter keeps its number in a field. A new agent's `tools` and `knowledge` are hints to the Agent architect, which picks the nodes (a tool whose plugin is not online comes back as "not available here"); "after X" is read from the message by name (`placedAsAsked`), so a step named another way keeps the model's own placement, and an "after X" in the same clause as the word "agent" counts (a clause split on punctuation, "also" and "then"; an "after X" the person wrote about another step in that clause still moves the agent); the agent goes between X and the one step X feeds (whether the model wrote `before` or `after` alone), and with no or several next steps after X alone; a step named by a common word ("Set") can be matched inside ordinary prose ("after set up of docs"), so short step names keep the risk; a parse error is retried once, and a second one still ends the reply. Adding a node `after` one that already feeds another leaves that old connection in place without a warning (a v2-to-v3 trial kept Tech Lead → Open draft PR).
- **Spotlight's scope of a change** ([assistant.md](assistant.md#the-builder-chat)): a request about one step changes that step and nothing the model adds or rewires beside it; the model is held to it by names, so a step named in other words ("the status call") is not found and the selection decides, two steps whose names sit inside each other's ("Slack" and "Slack alert") count as the longer name where it is written, and a step name under three letters is never matched. A new step is read from an adding word (add, insert, put, create, then, send, email, notify, post, filter, use a, follow with, next …) or from "after/before" a named step or "this"; a request for a next step in other words, with a step selected, is held to that step: lift the chip (×). A step named with a common word ("Set") matches that word in ordinary prose. The selection's own scope lets the workflow's settings change (a time limit for the whole workflow); a scope asked for with "only", @ or a new step's place keeps them out, so *only X: stop it after 5 minutes* sets no workflow time limit. Only the model's proposals are held to it: a change you make on the canvas, or a Test and fix session, is not.
- The change diff on a proposal card compares values as text: a Code step's source is shown whole, not parsed, and an expression (`{{ … }}`) is shown as written, not as it resolves. A change Spotlight applies alone (a new draft) has no waiting card, so its row keeps the one-line list, and a row from an earlier visit has no diff. When one reply holds several proposals they share one diff (they are applied together, so one card): each folded row of that reply shows the whole reply's diff, not only its own proposal's part.
- **Composite nodes** ([composites.md](composites.md#not-built)): composite governance rules are instance-wide and edited as JSON; they are checked on save and publish, not when a run starts, and have no project or workflow scope yet ([specs/14](specs/14-composite-governance-rules.md)). A frame's fallback is picked in its contract panel, not drawn as an edge. A frame's timeout is checked when each node inside starts, so a node already running isn't interrupted. Composite types saved on an instance (`local.<name>`) aren't part of Git sync or environment promotion: on another instance a frame typed by one shows the type as unknown until it is saved there too.
- **Remote agents over A2A** ([a2a.md](a2a.md#not-built)): a remote agent's tokens count toward its limits only when it runs on kagent through the LLM gateway ([llm-gateway.md](llm-gateway.md)). Landflow calls agents over A2A but doesn't serve A2A itself, and uses neither push notifications nor the gRPC and REST bindings. The dialog doesn't preview the agent card. kagent 1.0.0-alpha17 drops the `landflow.*` message tags instead of copying them onto its spans, parents its MCP calls back into Landflow on a span it never exports (they show as separate roots of the same trace), marks its stream spans as errors when a stream closes, and elides message content in its logs. kagent runs in a kind cluster beside the OrbStack one, since Agent Substrate needs Kubernetes 1.37. An agent deployed to kagent ([a2a.md](a2a.md#landflow-agents-on-kagent)) gets its persona, model and tools but not cross-session memory, guardrails or usage limits; its sessions on kagent don't show in the agent's Activity → Sessions, and drift from an edit made in kagent shows when the status is read, not as it happens. On kagent's Claude Code runtime ([a2a.md](a2a.md#on-claude-code)), Substrate can't fetch git or bucket plugin sources (its golden snapshot has no egress), so Landflow packs plugins into images it serves itself, from GitHub marketplaces only; the Harness image has only bash and git; and qwen3-coder through Ollama keeps calling its hand-in tool after the task is done. kagent compiles in Claude Code 2.1.285 and refuses any other version, so `landflow-claude-dev` runs the latest Claude Code behind a wrapper that answers `claude --version` with the pinned one. The landflow-harness mod ([a2a.md](a2a.md#the-landflow-harness-mod)) reports a Claude Code agent's real usage (in queue mode the main it posts to passes it on to the worker that made the call, and a batch for a worker that has gone is lost), only for new requests (an answer to a paused task is estimated), and only where the credential names a Plugin Registry and Landflow's access Role may write EgressPolicies (the mod reports through one of its own per agent); its guard is set per agent at deploy time (read-only, normal or report only; a request can only tighten it) and, in Normal mode, asks a person only about a push to main or master, a force push and deleting a remote branch (nothing else is askable, the answer is read by polling for up to 10 minutes, and an ask posted to a worker's trace that has gone is never answered until it times out), and its rules match command lines, so a script that does the same thing gets past them, read-only included. A node's live progress (`node.progress`, [a2a.md](a2a.md#the-a2a-agent-node)) is kept in memory: by the process that runs the execution and, in queue mode, by every main from the relayed events, so a main that starts mid-run shows a node's steps from its next report, and a tool sub-node that has not reported yet lights up only from its `node.started` event. The execution view's **Agent session** panel polls every 2 s (no push) and shows only sessions saved since the link was added; a running session is saved at most every 1.5 s, so the newest step can lag a moment. The **Run an Agent** node ([agents.md](agents.md#from-workflows)) refuses tools that need approval, since a workflow run has nobody to approve them, and runs every agent on Landflow's runtime, also one deployed to kagent (the A2A Agent node calls kagent, without the canvas's tools).
- **Work events** ([work-and-briefings.md](work-and-briefings.md)): `private`, `team` and `org` work are accepted (a new event is `private` unless it says otherwise). The briefing's `related` lists colleagues' shared work (B18), and the auto-send switch (`brain.workAutoSend`) is in Settings → MCP. `landflow work` ([cli.md](features/cli.md#recording-your-day-landflow-work)) sends private work only (team and org sharing from the CLI waits for the server), sees only repos on its allow-list whose `origin` is `owner/name`, summarises commit subjects and directory names (not what the work was, no model), puts PRs on the day `gh` says they were last updated, and its scheduling is documented, not installed. The Tomorrow sync's nodes run on a schedule only on the published version, saved by an owner or admin and published by an owner or admin (a schedule of an unpublished draft is refused with "A schedule handles people’s briefings only from the published version …"): after a member's change (or a save with nobody behind it, such as applying a suggestion from Slack without a matched person) the nightly run fails with "A member, or nobody, saved the version of this workflow that ran …" until an owner or admin saves a change of their own (saving the member's graph unchanged makes no version, so it is not enough), versions from before migration 2091 count as nobody's, and a publish request an owner or admin approved still counts as the member's who asked. They refuse a member's manual, MCP or re-run, an agent's tool call with no owner or admin behind it, and a metric's measurement run, so only owners and admins can test it by hand ([work-and-briefings.md](work-and-briefings.md#the-nightly-sync)). Deliver Briefing sends by Slack only with the server's own bot (`LANDFLOW_BRIEFING_SLACK_TOKEN`, one Slack workspace per instance, set by whoever runs the server; no per-project Slack and no credential), so without it Slack delivery is skipped with a warning; Slack delivery is a DM to the person's Slack account with the same email. A credential's "Last changed by" is informational: credentials from before migration 2092 show nobody, and a Git or environment pull counts as the person who pulled. A version's author is whoever saved it last with a change, so an owner's or admin's save over a member's draft (even a settings-only one) makes the member's graph theirs: publishing is the second check, which is why a schedule runs only a published version. The nightly briefing (the Tomorrow sync template) is prepared at 02:00 on the day it is read, so it holds yesterday and today up to that hour; the landflow-brain mod's session start does not show its text yet (it copies the lists only; B38 did not build it, so it is still open in the roadmap), and the MCP `my_briefing` tool and resources leave it out (only the `morning-briefing` prompt quotes it); on the web, Home and the Brain index show it (B37). A private event reaches no flow trigger (On Usage Event) and no flow's Landflow Usage node. Usage totals mix sources for an owner of private work: recent windows read raw events (their own private work counts), older windows read the daily rollups (it does not).
- **Second brain** ([second-brain.md](second-brain.md#limits)): Dead weight waits until the ledger reaches back 60 days, and the backfill only reaches as far as the executions and audit events on disk. In queue mode each process starts On Usage Event workflows for the events it recorded, so a batch holds one process's events. Ollama calls cost $0 unless someone prices the model in Settings, so the AI-cost detector has no cost to compare for an unpriced one. The model writes fixes and drafts one at a time, so a study or detect run on a slow local model takes minutes (`POST /api/brain/run` waits). It proposes and never applies by itself. Custom event kinds have no UI and are shared by the instance; grouping by an attribute reads raw events (90 days). Entities are four fixed types with no relations of their own; the Brain page relates them only through the work that names them, matches work to pages by exact hints and emails, and its summaries and answers are only as good as the brain's model (a page's summary is written when it is first opened, not ahead of time). A button on a suggestion only records a decision unless a flow listens, and decisions are not retried. Slack mirroring is DMs only, started by Suggest Improvement, not retried. A declared metric is set on the nodes only. A flow backtest really runs every node of the flow once per point; only Suggest Improvement is neutralised, and Find Similar and facts ignore `asOf`. The unused-tools detector reads a session's timeline as it is now, so in a backtest it may count tool calls made after the point judged (it can only under-report). Ask a Person asks once per run, and email answers can't edit.
- **Eval gate** ([agents.md](agents.md#eval-gate)): standalone agents only (not teams, and not the AI Agent node). The check runs inside the publish request, one case after another, so a long list on a slow local model makes the publish wait (50 cases at most). Cases run with approvals denied, so a case that needs a tool's approval fails and scores 1; the architect's and Spotlight's cases for a tool that asks first expect the ask rather than the send (AG15), but a case a person wrote is never rewritten, the gate still denies approvals and its judge still decides. The judge is a model: scores wobble by a point between runs, which is why the rule allows a half-point drop. A version published before the gate existed has no baseline, so its first gated publish is held only by the 3 / 5 floor. Restore copies a version's config, not the knowledge documents or schedules' run state; a restored model that has since been removed fails at the next run.
- **Model router** ([agents.md](agents.md#model-router)): standalone agents only. The rule is length and tools, not meaning, so a short but hard question still goes to the cheap model (lower the character limit, or leave routing off for such agents). It chooses once per run, not per turn, and sends no tier header to a gateway: the cheap model is a plain model setting. Insights does not yet show what routing saved (the ledger prices each call by model, so the figure can be derived). The cheap model on another provider than the agent's needs its own credential for OpenAI; Anthropic and Ollama reuse the agent's or the default.
- **Conversation history** ([assistant.md](assistant.md#conversation-history)): conversations are private to the person who had them: there is no sharing in v1, and no admin read, by design. They are deleted 90 days after the last message (a pin does not exempt one), search matches the stored JSON of your messages, so a word like `text` matches every conversation with a message, a long chat is returned whole, and removing a person leaves their conversations (until retention) and preferences, and the history button is mounted in each chat as those chats adopt it.
- **Prompt cache** ([agents.md](agents.md#prompt-cache)): Anthropic only, agents only, no switch. The breakpoints sit on the last tool, the stable part of the system prompt and the conversation's last block (the memory and the date line come after the second one). The AI Agent node's Anthropic model still asks for no cache. The conversation's breakpoint misses, and the write price is paid on the whole conversation, when the conversation's prefix changes between calls: the window slides past `MAX_USER_TURNS_IN_CONTEXT`, `hydrateToolImages` drops an older tool image, or one turn adds more than 20 blocks (many parallel tool calls). Before this change, those calls paid the plain input price. With the prompt cache on, a one-shot Anthropic call (any caller of `agentModel`, not only the agent loop) whose last message is a plain string now sends it as a text block with `cache_control`, so it pays the cache-write price on that message with nothing to read it later; the amount is small (one message).
- **Response cache** ([agents.md](agents.md#response-cache)): exact match only (a reworded question misses), first message of a session only, and never for an agent with tools or cross-session memory. A system prompt that holds the time or other live text can serve an answer that was true when stored, so keep such agents' TTL short or the cache off. Agents deployed to kagent don't use it (kagent has no response cache either). The database adapter keeps answers in the host database, so an agent's answers are readable by anyone who can read it; don't cache answers to questions that carry personal data.
- **Tool access** ([agents.md](agents.md#tool-access)): standalone agents only (the AI Agent node and teams' tools are not filtered), decided once at the start of a run, so a role change mid-session applies from the next run. A role is known only for a person signed in to Landflow; callers from chat apps, schedules and workflows match on source or user id. The rule list has no groups and no tool-name patterns beyond `*`. The test panel ("what could this caller do?") builds the agent's tools, so an agent with an MCP server or an A2A agent contacts it to read its tools. The OPA and OpenFGA adapters were checked against a running OPA 1.22 and OpenFGA 1.18 (compose profiles and a Kubernetes example, [agents.md](agents.md#tool-access)), with the example policy and model as the only ones tried; the policy and the grants are yours to write, and the OpenFGA example keeps its store in memory. An *ask* tool in a run nobody can approve is refused.
- **Guardrails on agents** ([agents.md](agents.md#building-an-agent)): the *grounded* check judges an answer against what the agent's own knowledge bases returned in that run, not against the truth, so a wrong document grounds a wrong answer; it does not see passages from a vector store wired into a flow node's Tool port, and it is skipped for an agent with no knowledge base. The tool-result stage checks the text a tool returns, one call per result (model checks add a call each), and does not check a tool's error message or a sub-agent's reply.
- **Jev and Strands Decider as guardrail judges** ([agents.md](agents.md#building-an-agent)): they only answer yes/no questions here, so they are judges and not models an agent can chat with. Their probabilities are not calibrated (TypeSafe says to pick thresholds from your own examples). If it fails, the check fails closed; there is no fallback to the agent’s model. Their calls are counted now (tokens as the service reports them, purpose “Guardrail check”), but unpriced unless you price them in Settings → AI prices, and they do not yet answer the model router or the Guardrails node. Both were built from the published `systemone` shape and tested against a fake server, not a live Jev key or a running Strands server (running one downloads model weights, which has not been tried). Score and choice questions (and image input) are not used.
- **Evaluation purpose on a worker**: in queue mode with `offloadManual` on, an evaluation run's segment runs on a worker and the `eval` purpose does not cross that hop, so its model calls read as `answer`. The default queue mode and regular mode keep manual runs in-process, where every model call of the run (agent loop steps and the AI Agent node included) is `eval`, and a guardrail or judge call inside it says `guardrail` or `judge`.
- **Rerank calls** ([llm-gateway.md](llm-gateway.md#what-each-call-was-for)): the model-based reranker's calls are counted with the purpose `rerank`. Cohere's reranker is not metered.

It is for standalone agents; teams and the AI Agent node have no checklist.

## A Run an Agent node follows its agent (wave ag4, AG17)

## Call attribution (wave 11)

- The new `ai_usage` columns (node, span, purpose, iteration, caller, duration, stop reason) show on no screen until wave 12.
- Rows imported from the gateway's spend log have none of them; neither has a call a plugin node reports in its `model` record, except `node_id`. A failed call writes no row.

## Browser plugin and retry backoff (built 2026-11-07)

- **Browser** ([plugins/browser](../plugins/browser/README.md)) needs the `agent-browser` CLI and its Chrome on the machine that runs the plugin; it is not in `dev:all`, the compose files or the cluster images. It reads pages and runs listed steps, with no free-form scripting, uploads or downloads, and no signed-in browsing (the CLI refuses saved profiles with an allow-list). The allow-list stops the browser reaching other sites; it can't stop a page from carrying instructions to a model, so page text is fenced and cut but should still be treated as untrusted. A screenshot over 64 KiB needs a host that serves the binary store. It was checked against the real CLI on `example.com` for reading, and on a locally served form, not against a login flow, a slow page or a long run.
- **Retry backoff** doubles the wait after each failed try (up to a minute, no jitter) and applies to node retries only; the whole-run retry already backs off. Composite frames keep the wait and the backoff as well as `maxTries`; n8n has no backoff setting, so an import is always fixed-wait. A node that ran when the process stopped still runs again after recovery, so a plugin must honour the per-step idempotency key.
- **Spotlight and the Browser node** (checked 2026-11-07, building a seven-node flow that fills a form): Spotlight guessed the Browser node's output field and step names until the node declared its `outputSchema` and accepted aliases; it now reads the schema, but a small local builder model still mis-wired a flow once (an extra node from the true branch into the rejection) and once announced proposal cards that never appeared, so check a built flow's connections. The instance MCP server now returns `outputSchema` from `get_node_type` and `validate_workflow` checks field reads (see below).
- **What Spotlight reads about the steps it edits** ([assistant.md](assistant.md#the-builder-chat)): the selected step and the steps in a change's scope come whole (a string up to 8 000 characters, all parameters up to 12 000 and 24 000 across all those steps in one prompt, the selected step first, so with several steps in scope the later ones may be cut short, then "… (N more characters)"); every other step in the outline is cut at 300 characters, so a request about a step the scope does not name still sees only its start, and a step the model reads through the chat's `get_run_data` tool is still cut at 2 000 characters. Output schemas now exist for Linear issue create, add link and comment create, Slack send, update and get permalink, and GitHub pull request create, get, list files and comment and issue create and comment; the other GitHub operations, the other Slack and Linear writes and the other plugins' nodes still name no output fields, and a field that exists in some items only is not marked as optional. A draft's `calls` counts the send-back as attempted (a send-back that times out still counts), not the one retry of an unparseable reply.

## Clickland (built 2026-11-14)

- **The agents' answers are not checked live yet.** On 2026-11-14 the plugin, both triggers, the webhook registration and
  its signatures, plugin knowledge search, the credential test, telemetry and the assistant's chat contract (Clickland's
  API → the published chat with Basic Auth → the lead) all ran against a live Clickland on this machine. The Landflow on
  the OrbStack cluster has no Anthropic credential, so the assistant's lead and the triage agent stopped at their model
  ("Could not resolve authentication method"): no answer, view marker, `search_clickland` call inside a conversation or
  Slack post has been seen live. Add an Anthropic credential, pick it on both flows' Anthropic Chat Model and the three
  analysts, and run the checks in [features/clickland.md](features/clickland.md#checked-live).
- **The triage flow takes every alert.** The template's Alert Trigger has no Alert ID, so every alert that fires in
  Clickland starts a triage run (and, while no Anthropic credential is picked, a failed one).
- **Alert events have no fixed shape in the contract.** The Clickland Trigger reads an event's time from the first of
  `createdAt`, `at`, `timestamp`, `changedAt`, `firedAt`, `time`, and an event without any of them is never emitted. It
  reads events for at most 25 alerts per poll (those whose states changed), so a burst across more alerts takes several
  polls. The Alert Trigger has no such limit.
- **Alert → Update reads, then writes the whole alert** (Clickland's `PUT` takes all fields), so a change made in
  Clickland between the two calls is overwritten.
- **The assistant's analysts don't stream their steps.** In the observability assistant the analysts are Run an
  Agent nodes used as the lead's tools: Clickland sees the lead's calls to them (with the `reason`) and their answers,
  not the queries each analyst runs inside its call. A node used as a tool gets no stream to write to.
- **The assistant's auth is a shared secret over Basic Auth.** The hosted chat has no token or HMAC scheme: Clickland
  sends the trigger's user and password on every call, so the password must be long and random, and the call should
  stay inside the cluster (plain HTTP there). Rotating it means changing the trigger and Clickland together.
- **Triage's Clickland severity is the default.** Clickland's alerts carry no severity, so Normalize Alert gives them
  Default Severity unless the alert has a `severity` field or label.

## Practices in Claude Code and the shell

- `landflow practices check` asks again in smaller path groups when the host omits practices that did not fit its block; any still omitted (or whose version moved mid-check) are reported and the run says the check is incomplete instead of `Passed.`. It runs machine checks only. A practice with no machine check is reported as such; a model's verdict reaches a flow only through Check Practices ([below](#checks-in-flows-wave-p2)).
- `/brain learn`'s citations are never verified: the host cannot read your checkout, so a draft from the mod or `landflow practices learn` stays unverified until a person approves it against the file.
- `/brain learn` hands Claude a prompt as a turn of its own, so it waits until the session is idle, and a model that ignores the instructions can draft fewer than asked or none. `practice_draft` and the learn route always make tainted drafts.
- The practices section is built once at session start: a practice approved later shows at the next session, or through the `practices` tool or `/brain practices`.
- `check` reads the change as `git diff <base>...HEAD` shows it: uncommitted work is not in it, and a renamed file is read as a delete and an add.

## Checks in flows (wave P2)

- Check Practices runs only the machine checks and the verdicts it is given; it has no model of its own. A practice with
  neither is `no-checks` and never blocks. A reviewer's fail blocks only with **Reviewer fails block** on.
- **On error: continue** on the Check Practices step defeats the block, as it does for any step. The editor warns about
  that setting; nothing here forbids it.
- A waiver is for one run, and for the runs that retry it. A waiver of one practice does not cover another, and a flow run
  again from the start is checked again: a waiver holds only for the failure the approver saw (the same practice failing
  on the same files and message), so a retry that breaks the practice on other files fails again, however many files fail. The waiver binds to the file
  names and messages, not the added lines: a `fileMatches` failure on the same file with different added lines, and a
  `pathExists` failure (it names no files) carry over on a retry from the start. Check Practices runs
  `fileMatches` patterns (up to 200 characters, no guard against catastrophic backtracking) inside the host process over
  up to 20,000 added lines, so an approved practice with a bad pattern can stall the host's event loop; there is no
  per-file cap or worker yet.
- **Drift counts runs, and cannot tell whether a practice concerned the work.** A Landflow agent's or team's block lists
  every practice that applies to its project, and its `delivered` row says nothing of the task or the paths touched, so an
  org practice with no repository would look "rarely followed" fast. Compliance counts distinct runs; the practice-drift
  detector counts a block's in-process deliveries a third each (30 runs, not 10, reach the floor) and a delivery that named
  a repository in full. Relevance to the run is not recorded; a precise rate needs that.
- A required practice blocks only in a flow. An agent's tool call, `landflow practices check` in a shell and the Claude
  Code mod never deny anything.
- The pull request template reads GitHub's patch of each file; GitHub leaves the patch out of very large files, so a
  `fileMatches` check sees no added lines there. It has not been run against a real repository.
- The blocked template's message is read from the failed step's error text, and its **Fix** link is the step's "Link to the
  change" option; without it the message says to push a fix. Error workflows do not start for a manual Run.

## Graceful shutdown (backend hardening, 2026-11)

- **`next dev`** keeps Next.js's own signal handling: the host's phased shutdown (flush, lease release) runs only where `NEXT_MANUAL_SIG_HANDLE=true` (`pnpm start`, the Docker image). Without it only the error handlers are ours.
- **Streams**: in manual mode in-flight requests are awaited, but SSE streams are not; they end when the process exits.

## Live streams (backend hardening, 2026-11)

- **Replay is per process**: `/api/events` keeps the last 500 events in memory; a reconnect after a restart, a longer gap, or to another main (queue mode) gets `event: reset` and has to refetch. The editor's shared EventSource (`lib/client/live.ts`) does not yet listen for `reset`, so after such a gap a tab may miss updates until its next fetch. The ring is bounded by count, not bytes: on a quiet instance 500 large `node.finished` or journal events stay in memory until newer ones push them out.
- An SSE client that stops reading for 10 s with more than 16 MiB unread is disconnected, and so is any client with more than 128 MiB unread (a run that emits more than that in a burst). A run started from the editor keeps running; the editor picks it up again.

## Execution retention (backend hardening, 2026-11)

- **The cap can be exceeded between passes**: a finished run prunes only every `LANDFLOW_RETENTION_EVERY` runs (default
  50), so up to that many minus one finished executions above the saved maximum can be stored until the next pass (the
  hourly timer and **Prune now** (Settings → General, in the ⋯ menu) prune regardless).

## Encryption key ring (backend hardening, 2026-11)

- Keys live in the environment or `encryption.key`; KMS-wrapped data keys are not built (a decision of the review). A value
  sealed with a key that is no longer in the ring can't be opened: remove an old key only after rotate reports no failures.
- Sealed strings outside credentials (alert channel, SIEM, kagent, signing keys…) are bound to a shared `secret` purpose, not
  to their row: the key id and rotation apply, a copy between two such rows is not refused. Credential blobs are bound to their id.
- Going back to an older build is one-way blocked: once this code saves a credential or refreshes an OAuth2 token (which re-seals it), the value is `v2`, and a host on an older build (or another branch) pointed at the same data directory can no longer open it.
- A rolling upgrade to the key ring in queue mode is not seamless: processes before it can't open `v2` values or verify HKDF-signed resume URLs, so upgrade every process together (or stop the workers first).
- Rotation has no page in Settings (the route and the script only) and in queue mode needs the new ring on every process first.
- The rotation route re-seals everything synchronously inside the request, so with many credentials and passphrase (scrypt) keys it blocks the host's event loop until it ends; on a large instance prefer the script with the host stopped.
- Files outside the data directory's `agents/` and `audit-anchoring.json` that hold a value sealed with `sealSecret` are not
  re-sealed (the stores are listed in `credentials/rotate.ts`).

## Assistant checkpoints (2026-11)

- **Spotlight's kept conversation** ([assistant.md](assistant.md#conversation-history)): a test-and-fix session's own turns (its runs, needs and outcome cards) are not kept, so they are missing when the conversation comes back; only what you typed, the replies and their proposals are. ## Audit reliability and observability (backend hardening, 2026-11)

- **Audit write failures** ([audit-and-governance.md](features/audit-and-governance.md#reliability-and-fail-closed-mode)): without `LANDFLOW_AUDIT_FAIL_CLOSED` a failed audit insert is only logged and counted, and the change stays; with it, only the listed high-value actions are refused (other events never block). Credential creation and SCIM user creation are compensated (deleted again) rather than transactional. Not covered, so fail-open: user deletion, SSO and JIT role assignment, credentials created outside the REST routes (OAuth connect, imports), SIEM destination changes, anchoring and key rotation. In fail-closed mode a credential update or delete records its event before the change, so a change that is then refused or fails (a validation error answered 400, a config-store write error) leaves an event for something that did not happen. The OTel log record, process log line and outbox kick for an event recorded in a transaction that later rolls back are not undone, as for project creation. Credential-use dedup is still process memory.
- **Read sampling and database spans** ([observability.md](observability.md#2-trace-context-propagation-metadata)): a read-only API request's spans (its server span and the spans that descend from it, not other spans of a trace it joined through a `traceparent`) are held until its server span ends (at most 500 spans per read). A descendant still open when the read ends follows the verdict: exported when the read was kept, dropped when it was not. Once the read and every descendant it tracked have ended, the read is freed at once, so a span started after that under the request's context (work a handler left running) is exported on its own, even for a fast read. A read still in flight after five minutes, or the oldest once 5,000 reads are in flight, is forgotten: its held spans are lost and its later spans, the server span included, are exported on their own. The `traceparent` of a fast read, and the trace ids on log lines inside it, name a trace whose host spans were dropped (a plugin may still export its own). The database histogram times each call on the process's SQLite connection (Postgres mode's in-memory copy included), not the asynchronous replay to Postgres, which `landflow.db.write_queue.*` covers. `landflow.sse.connections` is labelled by the route template each streaming route names (`/api/events`, `/api/workflows/:id/run`, `/api/executions/:id/approvals`, `/api/assistant/chat`, `/api/assistant/agent`); a stream whose route names none counts under `other`, so a new streaming route that forgets to name itself is not told apart.
- **Alert rules** ([observability.md](observability.md#alerts-and-dashboard)): the thresholds are starting points, the local backend has no Alertmanager (alerts show in Prometheus only), and no metric gives the age of the oldest queued job, so the queue alert watches depth. The exception fingerprint of a thrown non-`Error` is from its type alone. In the production bundle (minified chunks, no source maps) it groups by exception type and chunk name words (many chunks share a name), coarser than in dev; exact call-site grouping needs server source maps with `--enable-source-maps`. Only host spans failed through `failSpan` carry it; engine workflow and node spans, the `db.query` span and SDK spans do not.
- **The AI cost counter has two names** ([observability.md](observability.md#alerts-and-dashboard)): through OTLP into the LGTM pod it is `landflow_ai_cost_USD_total`; a direct scrape of `/api/metrics` names it `landflow_ai_cost_usd_total` (seen on a live scrape of a priced call, 2026-11-16), so the dashboard's "Cost by purpose" panel shows nothing against a direct scrape until its query is changed.

## Project AI budgets (wave 9)

- A budget is monthly and per project. There is no budget per goal.
- The hard stop refuses only calls Landflow makes with a model that has a price in the price table. A model only the

  never stopped. Imported spend can open a stop, which asks a person, but cannot refuse a call that already ran.
- There is no LiteLLM team budget behind it (its window is 30 days, not the calendar month, and it would count calls
  Landflow never stops).
- A resumed month stays open even after a raise: the project's priced calls are not stopped again until the month ends.
- Moving a workflow or agent to another project moves no budget; spend follows the project of the run.
- Every raise (an incident's **Raise budget…**, a higher amount in the project's settings, an approved request) settles all
  that month's open incidents, the stop and the warning alike.

## Project tasks (wave 10)

- No autonomous runs: every run of a task, from a wake-up or a click, needs a person's **Approve**. A wake-up only asks.
- The tool approvals of a task run are decided in the agent's session (Needs you opens it), not on the task.
- The agent's published version runs; an agent that is only a draft cannot be approved ("Publish it before it works on
  tasks").
- A removed member stays the assignee of a task until someone changes it.
- A task run is always the in-process runner's (`runAgent`), whatever else runs the agent (kagent).
- A task has one parent at most (no deeper trees), and a run in progress when its task is deleted finishes but saves
  nothing. The same holds when its project is deleted: the task and run rows go with the project, but the agent's
  session is not stopped; it runs to its end and stays in the agent's Sessions tab (its spend is still counted), and
  the run's later saves do nothing.
- A request whose agent was deleted is settled as `denied` ("The agent was deleted before this was approved") the next
  time anything reads it, not at the moment of deletion.
- Wake-ups use the instance time zone, not each person's; a clock change skips a wall-clock time that does not exist that
  day. They run on the leader only, so a stopped host asks for nothing until it is back (a missed wake-up is not replayed).
- A February 29 wake-up schedule can be refused as `This schedule never fires` (the search looks 366 days ahead). A request for a run that was made before a task was reassigned stays open and answers 409 on Approve until someone denies it. With more than one host process, a run with a quiet step longer than 10 minutes can be marked failed by another process, and its later result is dropped. A run whose session was deleted settles as `Landflow restarted before the run finished`.

### Counting and splitting a call

- **Prompt parts** ([llm-gateway.md](llm-gateway.md#what-a-prompt-was-made-of)): the split of a call's prompt is exact (Anthropic's count endpoint, OpenAI's encodings, an Ollama model's own vocabulary) except where it stays an estimate (characters ÷ 4 per part, `formatting` 0): a call through the LLM gateway, a call with images, an OpenAI-compatible model that is not OpenAI's, an Ollama model with another tokenizer than a byte-level `qwen2` or `llama-bpe` BPE, a count request that failed or passed `LANDFLOW_AI_PARTS_COUNT_PER_MINUTE`, and every Anthropic call that was not counted (counting is after the response, so a restart in between loses it). The Anthropic count builds the request from the draft's texts, so the real request's roles and tool framing, and the tool-use preamble (which sits with the tool definitions, as the count of the tools reports it), are not told apart from the parts around them; a count's prefix steps are limited by the per-minute budget, so a first call with a very long history can be an estimate. Only calls whose prompt Landflow builds have a split: agent runs, the AI Agent node, the chain nodes, Spotlight, the Agent architect and Ask the brain's streamed form (the one the Brain page uses: the JSON form of `POST /api/brain/ask` writes neither a split nor a purpose, seen on a live host); calls built outside Landflow (a remote agent behind the gateway, a plugin that calls a model itself) have none unless the gateway's split counts them ([llm-gateway.md](llm-gateway.md#the-gateways-split)), which stays off until the host and the gateway share a secret (on the local gateway the callback is mounted and its secret is empty, so it posts nothing). An Ollama call made by the `core.ollamaChatModel` node with its own Base URL is counted with the vocabulary of `OLLAMA_URL`'s server (the usage row holds no base URL), so a same-named model with another vocabulary there gives a wrong `tokenizer` split (the same holds for a call recorded as `ollama` through an `openAiApi` credential with its own base URL); a call on a gateway credential is recorded as `litellm` and stays an estimate. Splits are kept 30 days. `formatting` is the provider's reported input minus the counted parts, so on Ollama it holds the model's chat template, including its own tool-calling instructions: seen live on qwen3-coder:30b, it was about half of a call with tools (221 of 355 tokens). That is real input the model read, not a counting error.
- **No `knowledge` part**: passages from an agent's knowledge bases reach the model as tool results, so they count under
  `toolResults`; the screens show only the parts that are present ([llm-gateway.md](llm-gateway.md#what-a-prompt-was-made-of)).
- **A call on a gateway credential keeps Landflow's estimate** even when the gateway's split counted it exactly; which
  split wins for such a call is not decided. Two calls with the same new prefix at the same moment both send an Anthropic
  count request (each is free; the results stay right).
- **The prompt cache is measured on a fake**: the cache fixes ([agents.md](agents.md#prompt-cache)) and the cache card
  were checked against a fake Anthropic cache and on local models, never on real Anthropic cache reads (a live check needs a
  vendor key, which live checks never use). The AI Agent node asks for no cache, and the cache alert's 7-day baseline
  includes the period it fell in, so a sustained drop lifts its own baseline and the alert clears after a few days
  ([observability.md](observability.md)). A daily cap's pace line has not been seen late in a host's day.

### The AI page and the Run Trace's Spend tab

- A model step is matched to its call by model name, agent and node and a time window (1 second before the step to 2
  after), not by an id, so two parallel steps on the same model and node can match each other's call.
- The run's spend record holds its newest 500 calls; in a longer run an older step says it may be older than the record.
- A step's split is read when its sheet opens and again when the step ends or its status moves; it is not live inside one
  step.
- A Landflow agent started by Run an Agent writes its turns and tool calls to the journal but no `model` span per loop
  step, so its calls in the Spend tab show their time as plain text and have no sheet with their composition; `GET
  /api/ai-calls/:id` answers for them, and the AI page's drill sheet opens them by id
  ([run-trace.md](run-trace.md#spend)). The sheet opens for the AI Agent node's model sub-node, a plugin node's `model`
  record and the harness mod's requests.
- **Distinct runs scan the raw rows.** The rollup speeds the sums, but a count of distinct runs is read from `ai_usage`
  itself over the whole range (the report's `runs`, twice with `compare=1`, and the runs and calls lists), so a 90 or 400
  day range of a busy instance returns many rows into the server's memory. Counting them per group in SQL is open in
  [roadmap.md](roadmap.md#token-spend-wave-13).
- **Runs and calls behind a number** read `ai_usage` with plain SQL over the period (the daily rollup has no run ids),
  so a very wide range of a busy instance scans every row of it. A call with no execution and no agent session (a
  Spotlight or brain call) is a call, never a run: it is in the calls list and in no run. A run whose calls the viewer
  can open only in part is listed with those calls; the rest are in `hidden.calls` and `hidden.cost`, not `hidden.runs`.
  The key `other` (the tail past 50) can't be opened: filter by another group to reach it. A model row's
  `unpricedCalls` counts a combination's calls when it has no price and no cost, so a gateway-costed call among unpriced
  ones of one model is not told apart. After a filter changes, the previous-period request goes out once more for the old
  range (a wasted request, no wrong number).
- The AI page's cache card says why a call missed only for calls whose prompt split is still kept (30 days); over a
  longer period it says so ("Miss reasons cover the last 30 days at most"). The "below the minimum" reason uses one
  1,024-token minimum for every model, the lowest among current Claude models; a model with a higher minimum may need
  more. A call through the LLM gateway counts in the hit rate only when it reports cache tokens (it is provider
  `litellm`, so it is not counted by its provider name); a gateway call that reports none is left out, not counted as a
  miss. The card counts at most 20,000 calls of a period (the newest) and says when it left some out. "Misses in N of M
  runs" counts sessions and executions only: a gateway call with neither is no run, and a miss across the calls of one
  gateway client session is not seen.
- The forecast is a straight line from the last 7 complete days: it does not know a weekend, a launch or a plan to stop
  a flow, and a day's σ from 7 values is itself rough, which is why a month's first week says "early". The band is a
  10th to 90th percentile range of a normal approximation, not a promise; a daily cap's pace is spread evenly over 24
  hours, so it swings early in the day. It reads the call rows by day, not the daily rollup.
- A price for a local model applies from the moment it is saved. Calls recorded before keep the cost they had (usually
  $0): there is no repricing of old rows, and no "equivalent cost" for an unpriced model (decision D5). Gateway rows
  imported before wave 13 do not say which provider the gateway ran them on (`ai_usage.gateway_provider` is empty), so one
  that ran on Ollama is not listed under Local models until a new call of that model arrives; it is still priced by model
  name.
- The AI page's **You** card covers 24 hours, 7, 30 or 90 days; with a custom range on the page it is not shown, and it
  leaves out the split by purpose and by surface (the API returns them). "By agent" and "most expensive runs" are not
  built. The wave 13 parts of the page are made for desktop; on a phone it keeps its earlier row cards and never scrolls
  sideways ([llm-gateway.md](llm-gateway.md#the-ai-page)).
- Your own spend is not split by Claude Code session: one gateway key per person, which would tell a person's Claude Code
  from their other calls at the gateway, is later (decision D7, SP18).

### Forecasts, unusual spend and alerts

- **Unusual spend is checked for today and yesterday only**, every 10 minutes, against the 14 days before each. A day
  older than that is never flagged after the fact, and a host that was off for days flags nothing for the days it missed.
- **The baseline is a median over observed days, not a model**: no weekday or weekend pattern, no launch or planned
  burst. A weekly rhythm (a heavy Monday) can look unusual on Mondays; the half-the-median and score rules soften that, the
  smallest jump (`LANDFLOW_AI_ANOMALY_MIN_USD`, 100,000 tokens for unpriced keys) is the lever. There is no per-key
  setting to mute one.
- **A key is judged on tokens only when none of its 15 days has a cost.** A key that is priced on some days and unpriced
  on others is judged on cost.
- **The forecast flag is the AI page's forecast**: a straight line from the last 7 complete days, with the same
  limits. One flag per cap and month; a cap that is exceeded later in the month is the threshold alert's.
- **An acknowledged flag stays acknowledged for the day** unless the day's value doubles; there is no "snooze" and no
  per-person acknowledgement (it clears for everyone).
- **Landledger's anomalies are not read**: Landflow does not ask Landledger what it flagged, and Landledger's trigger has
  no `cost.anomaly` event. The option "Landledger alerts on agent and model spikes" is a promise the person makes about
  Landledger's own alerting, not a check.
- A member's inbox never holds a person's or a model's unusual day (the inbox names no person); they see their own in
  Needs you, and the owners and admins see everything there.
- **Left out of unusual spend**: an anomaly view on the AI page, a Landledger trigger event for `cost.anomaly`, reading
  Landledger's own flags, a weekday-aware baseline and a way to mute one key are not built
  ([roadmap.md](roadmap.md#token-spend-wave-14)). The pages are
  [llm-gateway.md](llm-gateway.md#forecasts-and-unusual-spend) and [features/landledger.md](features/landledger.md).

### The waste detectors

- Each waste detector reads at most 50,000 `ai_usage` rows (the newest, up to the moment judged); a busier instance judges the most recent calls only. They do not leave out manual (editor) runs, so a developer re-running a flow can trip `repeated-calls` or `context-bloat`. `cache-misses` judges only calls whose provider is `anthropic`: Claude through LiteLLM, Bedrock or Vertex is not judged. `repeated-calls` holds back per agent or workflow, so dismissing one repeated prompt quiets the rest of that subject. `unused-tools` skips agents whose prompt parts come from the gateway. The waste detectors read the prompt parts, which are kept 30 days: they see nothing older, and "unused tools" looks back 30 days at most. They cannot see a kagent agent's tool calls (kagent runs its own loop), so `unused-tools` skips those agents and workflows. A local model has no price, so its suggestion names a smaller local model seen on this instance in the last 30 days and gives no saving in money; with none seen there is no finding. An agent whose session can no longer be read is left out of `unused-tools` rather than guessed at.

- The landflow-brain mod's status line has been checked against fakes and the real route, not in a live Claude Code
  session, which would call a vendor ([landflow-brain-mod.md](landflow-brain-mod.md)).
- **The brain's draft workflows** ([second-brain.md](second-brain.md)): a suggestion's draft is built planned first (a plan call, one call per step and the send-backs, usually 5 to 15 calls and at most 26, on the brain's local model), so one detector pass builds drafts for at most 3 findings (`MAX_DRAFTS_PER_PASS`; the only draft detector, unmet demand, reports at most 3 anyway); a finding past that is saved without a draft and gets none until it is found again in a later pass that has room. A request whose suggestion is still open or snoozed keeps its saved draft and is not rebuilt, as long as the prompt it was built from (the request and its example requests, hashed on the suggestion as `draftPromptHash`) is the same; when the examples change as requests leave the 30-day window, or the draft was saved before the hash was kept, the next pass rebuilds it and the rebuild counts against the cap. Dismissing a suggestion does not get a new draft: it holds the request back (see [second-brain.md](second-brain.md)).

## Agent knowledge from a folder (wave ag3)

- Keyword search finds the words in a question, not their meaning ("how much journal" finds a passage that says "journal"; "how much log space" may not). With an embeddings model on the host, or an OpenAI-compatible credential, a knowledge base can search by meaning; Spotlight picks keyword search only when the host has none.
- Indexing a folder replaces a file's chunks before it adds the new ones, so a file whose load or embedding fails is left with none; files removed from the folder keep their old chunks until the knowledge base is cleared. Read live on Claude in ag3's live pass (the `runbooks` folder, 4 files); not read live: re-indexing a folder whose files changed or were removed, and a vector search through an embeddings model (Ollama stays off).
- A keyword knowledge base needs the SQLite or in-memory store: Postgres PGVector needs real vectors and refuses it.
- A folder is indexed once, when Create runs (and again on the agent page's route call): it is not watched for changes. At most 200 files of 25 MB are indexed from a folder, and only under the files directory (`LANDFLOW_FILES_DIR`); the card lists at most 50 of them.
- Spotlight's ask reads a folder only as a relative path in English words ("in the folder runbooks"); an absolute path, `..`, `~`, a URL or a drive letter gives none and the card asks for a folder.

## What a tool call's target cannot say

- A target says where the host sent the call, not what the system then reached: an MCP server's own downstream systems
  and a plugin that does not say where it connects show only the server's or the plugin's host (or its name).
- A credential that keeps its address in a secret field (a made-up type with a secret `url`) gives no endpoint; the row
  shows the credential's name and type alone.
- A run from before wave ag3 has no target, so its calls show no via line and no Reached row. The AI Agent node reads a
  sub-node's credential from the saved workflow in manual and chat runs (the published one in production runs), so an unsaved edit shows the saved credential. The public Chat trigger and webhook streams drop a tool's target.
- A knowledge search's passages come from the chat's output text, which is cut at 12,000 characters for a standalone agent's
  knowledge base (2,000 for other tools); a longer answer shows its raw text.
- A credential whose URL holds a user and password (a Grafana URL `http://admin:pw@…`) cannot be used by a plugin that
  calls it through the host's HTTP client: fetch refuses a URL with credentials, so the call fails before it leaves and
  says so (the URL redacted); the target still names the host and port only (found by the ag3 join tests).

## What the canvas's agent bubbles do not show

The bubbles on a Run an Agent node (AG16, replacing AG12's band) draw the agent's own model, memory, tools and knowledge bases. They do not show an A2A Agent node's remote agent, a Run a Team node's members other than its lead, the agent's skills, or what a tool call reached (that is on the Run Trace). Edits through them change the agent's draft only and are live after Publish; *Pick a credential* and an MCP or A2A tool's *Change…* open the agent's page rather than a dialog on the canvas, and a knowledge base is picked only from those other agents the caller can read already have (there is no tenant list of them). Spotlight's placement and the store's Tidy up assume five bubbles before an agent has been read. The project's settings and the agent's data are read from the saved workflow and agent, so a workflow never saved shows the agent without its project's settings. A version preview and a run's canvas draw the pinned agent version's bubbles read-only (a chip "<name> v1") only where AG21's pins route (`/api/workflows/:id/versions/:versionId/pins`) or a run's `versions` answer; otherwise they draw the plain node. A saved agent reaches every open tab (BroadcastChannel), so a Spotlight Apply in the editor tab reloads, and drops unsaved edits in, an agent page open in another tab.

Once a team node has run, its summary, budgets and ribbon make the tile taller than the idle one (which ends near 140 px). MCP agent writes (`create_agent`, `update_agent`, `test_agent`, `publish_agent`) use the existing API-key scopes (`workflows:write` and `run`), the default the person kept on 2026-11-18; an `agents:*` scope is a possible later change. `list_knowledge_bases` shows the top level of the files directory as the folders a new base could come from (names and file counts only), not nested folders. The count reads at most 5000 directory entries, 4 levels deep and 50 folders, so a very large folder's count can be lower than the real number without the listing saying so. A tool node counts as one that *writes* by the run check's wording rule (an operation that sends, posts, creates…, or an email or SMTP node), so a read-only node with such a name (Parse Email) is listed as writing and its tool asks first.

## Agent versions in workflows (ag4, AG21)

- Team membership is not versioned: a pinned team keeps its lead's version, but the members come from the team's published config.
- Delegated sub-agents (an agent calling another) run the published version, not a pin.
- Deleting an agent stops the workflow versions that pin it (the node says it no longer exists).
- The executions list shows the workflow version only; the per-agent versions are on the run's header.
- A scheduled publish (`at`) and a Git sync publish carry no `agents` choice, so an agent draft that differs refuses them (publish the agent first); with four-eyes on, `agents: 'as-published'` is refused too (`publish-first` settles the agents before the request is made).
- A test-update run is recorded like a production run of that version, so its line reads "workflow v4 · Alert triager v3" without saying it was a test.
- Import always makes a new workflow id (`wf_…`): the id inside the imported file (a fixture's `legacy-ag4`) is ignored, so a file imported twice makes two workflows and links between exported files by workflow id do not survive. This is on purpose (an id from a file could collide with, or take over, an existing workflow); look the workflow up by name after an import.
- Manual-mode runs (`POST /api/workflows/:id/execute`, evaluation runs and MCP manual runs, not only the editor's Run) run each agent's **draft**, as the editor does; only a published workflow runs the pinned version. With four-eyes on, a plain publish of an unchanged workflow still re-pins and so makes an approval request.
- A scheduled publish of a workflow whose agent the start pass moved wiring into fails with 409 `agent_changes_unpublished` until that agent is published ([agents.md](agents.md#from-workflows)): publish the agent from its page (the smoke test and the gate run), then publish the workflow again.

## Spotlight fixes from the run's log (wave ag4, AG20)

- An agent fix always waits for your **Apply** and **Publish**, also in autonomous mode: a saved agent is never a brand-new draft (lesson 23), so the session cannot repair an agent by itself, and a held eval gate stops it. The session's panel header does not yet say *Needs you: apply the fix?* while the agent's change card waits (it does for a flow fix).
- The run log holds clipped items only: at most three input and output items per node, strings and nested values cut (`clip`), the response body's first 400 characters, 20 plugin lines and the agent's reply's first 400 characters. A cause past those (the 401st character of a body, the fourth item) is not seen; the logs panel and the Run Trace hold the whole.
- "The same failure" is compared by the step, the error text with numbers and ids taken out, and the response body; a failure whose text changes every run (a timestamp in words, a random request id in a word) is not recognised as the same, so the bound of four fixes ends it.
- A Run an Agent step's tool calls in the run log are redacted by the workflow's redactor, which catches secret-named keys and the workflow's own credential values; the values of the agent's own tool credentials are not in that set, so a tool that echoes one back in its output is not masked by name.
- When a reply carries both an agent fix and flow proposals, the session takes the agent path and the flow proposal cards stay in the chat, unapplied; a click on one still applies it.
- The session's fix turns do not show their own tool rows ("Read the run log") in the timeline: the timeline shows `Run n · <node> · HTTP 400`, `Fixed · <change>` and the stop line. Only a typed chat turn shows its tool rows. After a reload the session's stop line is gone and the chat's last line may be an older answer.
- The panel header does not yet say "Needs you: apply the fix?" while the agent change card waits.

## Read tools and changes to an agent's tools (wave ag4, final run)

- A SQLite tool counts as a read only for the plugin's Select or one read-only `SELECT`. `WITH`, `PRAGMA` and `EXPLAIN` queries, and every Postgres or MySQL Execute Query, ask first, even when they only read; there is no read-only credential check for them yet.
- A tool set up as a read holds a call that is not one for a person (an unattended run refuses it); its tool schema does not offer `operation` and its SQLite file is opened read-only, so an approved write from it fails at the plugin and has to be made through a tool that writes.
- A change never moves a parameter or credential onto a kept tool: a bare duplicate is dropped, and anything else is its own tool with its own **Pick it** row, so a credential for an existing credential-less tool is picked on that tool.
