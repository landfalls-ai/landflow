# Notes for the integrator: P20 `collections` (C21)

- `docs/limitations.md`:
  - **Close** the limitation at lines 113-114, "A project's knowledge base names a collection that is global, as an agent's own is: another project that names the same collection reads the same data." Collections now have an owner project and grants.
  - Add: a collection nobody has written and no saved configuration names stays open to every project until a project writes it (it is then claimed by that project); the upgrade adopts only names written literally in an agent's knowledge base (draft or published), a project's knowledge setting or a workflow's Vector Store node (current definition): a name built by an expression (`{{ … }}`) is not adopted, listed in the report as not found, and if another project wrote that collection first the project that builds the name lost access (C21-D2 strict).
  - Add: a project that lost access in the upgrade has no access until an admin of the owner grants it back; the notice lives on the owner's card; "Find owners again" lists a dismissed notice again while the project still names the collection.
  - Add: a pgvector collection is keyed by the connection (host, port, database), the table and the name, not by credential, so two credentials to one database and table are one collection; a name differing only in case is one collection for access (the stores compare names exactly, so this can only refuse more).
  - Add: the knowledge-base picker does not offer a pgvector collection that another project shared (it carries that project's credential); name it by hand with a credential of your own.
  - Add: the dialog's "your project can't use this name" check covers the SQLite and in-memory stores and an agent's knowledge dialog (project knowledge's dialog says it when saving, with a 400); a Postgres name is checked when the base is saved or used.
  - Add: the instance-wide collections list and "Find owners again" are API only (`/api/settings/collections`); instance owners and admins see every project's card.
  - Add: deleting a project leaves the collections it owned owned by it (nobody can use them until an instance owner or admin moves them with `/api/settings/collections`) and the grants it held or gave (stale rows that match nothing).
  - Add: a granted write keeps the grantee's Upsert-by-Key keys apart from the owner's; the key stored for a grantee is `<project id>\u001f<key>`, so the grantee's chunks of one key can't replace the owner's. Other metadata (a plain insert) is not scoped.
  - Add: the adoption marker is decided per process on SQLite and by the first process to see no marker in queue mode; two processes starting together on the first start after the upgrade can both run it (idempotent: the same owners, the notices created once per database row, at worst a duplicate audit line).
- `docs/roadmap.md`: C21 (access per vector collection: owner project, read/write grants, claim on first write, strict adoption with the lost-access notice, the Notion read switch): built. Open: an instance-wide collections page; deleting a project's grants with the project; per-document access.
- `docs/README.md`: no new page (the Collections card is a section of `projects-and-goals.md`).
- `docs/development.md`: test list gains `collection-access.test.ts` (the queue-mode claim race runs under `LANDFLOW_INTEGRATION=queue`), `vector-store-access.test.ts` (its pgvector case under `LANDFLOW_INTEGRATION=postgres`), `agent-knowledge-access.test.ts`, `collection-adoption.test.ts`, `collection-routes.test.ts`. `notion-knowledge-nb06.test.ts` is unchanged (its runtime-brain path still passes; the FR-7 cases are in `vector-store-access.test.ts`).
- Settings with no new variable: nothing in `docs/reference/configuration.md`.
- Deviations from the plan: the key of a pgvector collection is the connection and table, not the credential id (a node does not know its credential's id); reads come from the host's own database copy (a primary-key read, replicated like every table) so there is no separate cache or `onTablesChanged` hook; the lost-access notice is a `vector_collection_grants` row of level `lost` (no third table); a collection's owner is claimed through `direct` Postgres only for the claim, while grants and adoption go through the replicated writes.
