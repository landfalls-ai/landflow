# Notes for the integrator: P28 `runners` (C29)

- `docs/limitations.md`:
  - Add: network runners serve the HTTP Request node only; database nodes and every other plugin node keep the plugin-on-a-broker path (`transports.md`), and Code nodes and agent tools never go through a runner.
  - Add: no relay for a host that is itself private, and no mTLS or instance CA: a runner proves itself with a bearer token (stored hashed, shown once, optional connect-from list).
  - Add: a call's request and response are buffered, 10 MiB each; at most 1,000 queued calls per network.
  - Add: a runner that is revoked or lost mid-call fails that call (never retried: the request may have reached the service); a revoked runner finishes nothing in flight.
  - Add: the runner routes (`/api/runner`) are public paths with no rate limit of their own (the token is checked first; the public limiter's per-address bucket would throttle a busy runner); a production server's request timeout must be above 25 s.
  - Add: the Run In menu lists every network by name to anyone who can edit a workflow (the project rule is checked when the node runs, not when it is picked).
- `docs/roadmap.md`: C29 slice 1 (network runners for the HTTP Request node: Settings → Networks, the `@landflow/network-runner` service and image, Run In): built. Open: slice 2 (a relay for private hosts, mTLS with an instance CA), database nodes and plugins over the runner channel, Code nodes and agent tools on a runner, a Helm chart and a `landflow-dev` manifest, a per-address rate bucket for `/api/runner`.
- `docs/README.md`: a feature-map row for the new page: **Network runners** (run the HTTP Request node inside a private network: runners, tokens, allow-lists, Run In) → [network-runners.md](network-runners.md).
- `docs/published.json`: add `network-runners.md` if the integrator publishes it (it links `transports.md`, which is already listed; `pnpm check:docs` fails on a published page linking an unpublished one).
- `docs/development.md`: test list gains `networks-store.test.ts`, `networks-calls.test.ts`, `networks-http-node.test.ts`, `networks-routes.test.ts`, `networks-ui.test.ts`, `networks.postgres.test.ts` (`LANDFLOW_INTEGRATION=postgres`), the browser spec `e2e/networks.spec.ts`, and the runner package's own suite (`pnpm --filter @landflow/network-runner test`, node built-ins only; it runs in `pnpm test`).
- Settings with no new host variable: nothing in `docs/reference/configuration.md` (the runner's variables are the runner's, in its README and `network-runners.md`).
- Deviations from the plan: a fourth table `network_runner_seen` in migration 2934 (what a runner last reported, apart from its row, so a poll can never rewrite a revoke; two mains share the table); the `network_calls` statements run past the in-memory copy (a statement on SQLite, `database.direct` on Postgres) so a claim has one winner across mains; a runner at capacity sends `{ max: 0 }` polls so a long call is never mistaken for a lost runner; `/^\/api\/runner\//` joined the audit SKIP list in `audit/http.ts` (a poll is not an event); no `PUBLIC_GROUPS` rate bucket for `/api/runner` (see limitations); the compose project of the live check is `landflow-runner-check` (the file keeps the plan's name `deploy/compose.network-check.yml`).
